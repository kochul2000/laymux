# 0123. 원격 위젯은 데스크톱 배치의 미러이며 표면은 한 줄 스트립 하나다

- Status: Accepted
- Date: 2026-08-03
- Source: 사용자 요구("리모트에서 위젯 확인할 수 있으면 좋겠다. 리모트만의 위젯은 필요없고 PC 설정 따라서 보여주면 된다"); `docs/architecture/api-contracts.md` §10 Settings·§13 Remote UI API; [ADR-0013](0013-direct-remote-mode.md), [ADR-0015](0015-remote-terminal-state-ownership.md), [ADR-0102](0102-claude-usage-probe-headless-pty.md), [ADR-0104](0104-codex-usage-app-server-probe.md)
- Extends: [ADR-0105](0105-widget-slots-and-status-line.md) — "원격 웹 클라이언트로의 위젯 노출"이라는 비목표를 해제하고, 그 ADR 이 재검토 조건으로 남긴 "슬롯 이름 일반화"를 **하지 않는 쪽으로** 결론 낸다. 배치 계약(네 슬롯 배열)과 소유권은 그대로 유지한다.

## Context

사용량·알림·CWD 는 상시 곁눈질하는 값인데 데스크톱에서만 보인다. 원격 브라우저로 접속해 있는 동안에는 같은 지표를 볼 방법이 없어, PC 앞으로 돌아가야만 한도 소진 정도를 알 수 있다.

원격 클라이언트는 데스크톱 UI 와 코드를 공유하지 않는다. `src-tauri/src/remote_server/page.html` 한 파일에 담긴 vanilla JS 이고, 데스크톱 위젯은 React 컴포넌트와 zustand store 에 묶여 있다. 따라서 "위젯을 원격에도 보여준다"는 말은 자동으로 **표시 로직을 두 벌 갖는다**는 뜻이 되며, 무엇을 어디까지 복제할지 정하지 않으면 같은 계정의 같은 한도가 두 화면에서 다른 숫자·다른 색·다른 실패 문구로 보이게 된다.

원격 표면의 물리적 제약은 데스크톱과 반대 방향이다. 상단 바에서 경쟁하는 것은 창 드래그 영역이었지만([ADR-0105](0105-widget-slots-and-status-line.md)), 휴대폰에서 경쟁하는 것은 **세로 픽셀**이다. 기존 크롬(header·keyBar·footer)이 이미 화면 높이를 먹고 있고 남는 것은 터미널 행 수다. 또 원격 헤더·푸터의 가로 폭은 status 텍스트와 키 버튼이 이미 다 쓰고 있어 위젯을 그 안에 끼워 넣으면 대부분 접힌 채로만 존재하게 된다.

결정이 필요한 지점은 다섯 가지다. (1) 원격 배치의 SoT 를 어디에 두는가. (2) 데스크톱의 네 슬롯을 원격의 어떤 표면에 어떻게 사상하는가. (3) 표시 데이터를 누가 계산하는가. (4) 폭이 모자랄 때의 정책이 데스크톱과 같아야 하는가. (5) 위젯이 원격에 노출되면서 probe 수요와 조작 권한(lease)에 무엇이 추가되는가.

제약과 force:

- 원격 페이지는 lease 를 잡지 않아도 열람은 가능한 표면이 이미 있다(`/remote/v1/navigation` 은 `remote_guard` 만 통과하면 응답한다). 위젯을 lease 뒤에 두면 "보기만 하려는" 접속에서 지표가 사라진다.
- Claude 사용량은 backend probe 가 수요를 세고([ADR-0102](0102-claude-usage-probe-headless-pty.md)), Codex 사용량은 호출마다 app-server 를 새로 띄우는 단발 읽기를 프론트 단일 폴러가 공유한다([ADR-0104](0104-codex-usage-app-server-probe.md)). 원격이 자기 수요를 새로 등록하면 수요 수명이 lease·폴 타임아웃에 얽히고, Codex 는 표면 수만큼 프로세스가 뜬다.
- 표시 실패를 마지막 성공값으로 대체하지 않는다는 불변식은 위젯에도 적용된다([ADR-0105](0105-widget-slots-and-status-line.md)).
- `settings.json` 은 사용자가 의도적으로 편집·공유하는 구성만 담는다([ADR-0004](0004-settings-vs-ui-state-separation.md)).

범위는 원격 표면 한 개, 그 표면의 데이터 계약, 표시 게이트 하나다. 비목표: 원격 전용 위젯 종류, 원격 전용 배치·옵션, 원격에서의 위젯 편집, 위젯을 통한 호스트 조작.

## Decision

**원격 위젯은 데스크톱이 그리고 있는 위젯의 미러다. 배치·옵션·표시 데이터의 SoT 는 모두 데스크톱에 있고, 원격은 표시용 모델을 받아 한 줄 스트립에 그리기만 한다.**

### 배치 소유

- 원격은 배치 설정을 갖지 않는다. `settings.widgets` 네 슬롯이 유일한 SoT 이며 원격용 슬롯 이름을 새로 만들지 않는다. [ADR-0105](0105-widget-slots-and-status-line.md) 가 재검토 조건으로 적어 둔 "슬롯 이름의 일반적 영역 이름화"는 **하지 않는다** — 이름을 일반화하는 순간 슬롯이 데스크톱 표면과 1:1 이 아니게 되어, 사용자가 상단 바에 놓았다는 사실과 화면에 그려지는 자리가 갈라진다.
- **원격에 그려지는 것은 데스크톱이 그리고 있는 것뿐이다.** `statusLine.enabled` 가 꺼져 있으면 그 두 슬롯의 위젯은 데스크톱에 없으므로 원격에도 없다. 미등록 `type` 도 같다 — 데스크톱이 렌더를 건너뛰면 원격도 건너뛴다. 원격이 데스크톱에서 보이지 않는 위젯을 되살리는 경로는 존재하지 않는다.
- 원격 표시 자체의 on/off 는 `settings.remote.widgets`(기본 `true`) 하나가 갖는다. 이것은 배치가 아니라 **원격 표면의 존재 여부**이며, 꺼도 배치는 그대로 보존된다. 세로 픽셀이 희소한 기기에서 스트립을 통째로 포기할 수단이 필요해 두지만, 원격만의 배치를 여는 문은 아니다.

### 표면 사상

- 원격 표면은 header 바로 아래 **한 줄 스트립 하나**다. 데스크톱의 두 표면(topBar·statusLine)을 원격에서 위·아래 두 줄로 재현하지 않는다 — 휴대폰에서 줄 하나는 터미널 행 하나이며, 두 표면의 구분은 원격에서 아무 의미도 만들지 않는다.
- 네 슬롯은 좌우로만 접어 넣는다. 스트립 왼쪽은 `topBar.left` + `statusLine.left`, 오른쪽은 `topBar.right` + `statusLine.right` 이며 각 슬롯 안의 배열 순서는 그대로 보존한다. 좌·우 붙임은 데스크톱과 같은 뜻을 유지하고, 위·아래 구분만 사라진다.
- 스트립은 기존 크롬(header·footer·keyBar)의 폭을 잠식하지 않는다. 그릴 위젯이 없으면 스트립은 DOM 에서 빠지고 높이 0 이다 — 위젯을 배치하지 않은 사용자에게 원격 화면 비용은 없다.

### 표시 데이터 소유

- **표시 모델은 데스크톱 프론트가 만든다.** 원격은 `GET /remote/v1/widgets` 로 이미 계산된 항목 배열을 받고, 행 선택·색·퍼센트·실패 문구·툴팁 텍스트를 스스로 계산하지 않는다. 이 경계가 없으면 `usage-rows.ts`·`usage-status.ts` 의 규칙이 vanilla JS 로 복제되어 같은 한도가 화면마다 다르게 읽히는 상태가 만들어진다.
- 원격이 소유하는 것은 **그리기뿐**이다. 항목은 `kind` 로 그리는 방식만 구분한다(`usage`·`activity`·`notifications`·`text`). 새 위젯 타입이 추가돼도 기존 `kind` 중 하나에 사상되면 원격 코드는 바뀌지 않는다.
- 데이터 경로는 기존 프론트 브리지(`query` / `widgets` / `snapshot`)를 쓴다. 원격 서버는 브리지 응답을 그대로 전달하는 얇은 라우트이며, 위젯 데이터를 Rust 에서 다시 조립하지 않는다.
- **원격은 probe 수요를 만들지 않는다.** 폴링은 데스크톱이 이미 갖고 있는 스냅샷을 읽을 뿐이므로 Claude probe 구독도, Codex app-server 기동도 추가되지 않는다. 데스크톱이 그 위젯을 그리고 있다는 사실이 곧 수요이고, 그리고 있지 않으면 원격에도 없다.
- 실패는 데스크톱과 **같은 문자열로** 전달되고 마지막 성공값으로 대체되지 않는다. 상세 사유는 데스크톱 툴팁과 같은 텍스트를 `title` 로 실어 보낸다.
- 갱신 주기는 원격 클라이언트가 소유하며 사용량 probe 의 `refreshSeconds` 와 무관하다. 원격 폴은 수요가 아니라 열람이므로 probe 간격 정책에 관여하지 않는다. 그릴 항목이 없으면 주기를 늦추되 **멈추지는 않는다** — 배치는 데스크톱에서 언제든 늘어날 수 있고 그것을 알아차릴 표면은 이 폴뿐이다.

### 폭 부족 시의 정책

- 원격 스트립은 접지 않고 **가로 스크롤**한다. `widgets.overflow` 의 `collapse` 는 데스크톱 표면의 정책으로 남으며 원격에는 적용되지 않는다.
- 근거는 두 표면의 경쟁 상대가 다르다는 데 있다. 데스크톱 상단 바에서 접힘은 창 드래그 영역을 지키기 위한 것이었지만, 원격 스트립은 자기 줄을 통째로 갖고 있어 양보할 상대가 없다. 그리고 접힘의 대안 표면인 팝오버는 휴대폰에서 터미널 위를 덮으므로, 지표를 보려다 작업 화면을 가리는 교환이 된다.
- 가로 스크롤은 스트립 자기 줄 안에서만 일어나며 터미널의 제스처를 건드리지 않는다.

### 조작과 권한

- 위젯 스트립은 **호스트를 조작하지 않는다.** 따라서 controller lease 를 요구하지 않고 `remote_guard`(토큰·IP·Origin) 만 통과하면 응답한다. 열람만 하려는 접속에서도 지표는 보인다.
- 상호작용 위젯의 동작은 원격 자신의 표면으로 사상한다 — 알림 위젯 탭은 원격 알림 패널을 열고, CWD 위젯 탭은 브라우저 클립보드에 복사한다. 데스크톱의 패널을 원격에서 여는 식으로 호스트 UI 를 움직이지 않는다.
- `settings.remote.widgets` 가 꺼져 있으면 라우트는 위젯 없는 응답을 돌려준다. 게이트 판정은 서버가 하며 클라이언트의 선의에 맡기지 않는다.

## Alternatives Considered

- **원격 전용 위젯 설정 신설(`remote.widgets.left/right`).** 기기별 최적 배치가 가능하지만 배치 SoT 가 둘이 되고, 사용자는 같은 위젯을 두 곳에서 관리하게 된다. 사용자 요구 자체가 "PC 설정 그대로"였다.
- **데스크톱 두 표면을 원격에서도 두 줄로 재현.** 사상이 가장 정직하지만 휴대폰에서 터미널 행을 두 줄 뺏는다. 위·아래 구분은 데스크톱 창 레이아웃의 의미이지 원격 화면의 의미가 아니다.
- **기존 header/footer 안에 위젯을 끼워 넣기.** 새 표면을 만들지 않아 세로 픽셀 비용이 없지만, 두 줄 모두 이미 폭이 포화라 대부분의 위젯이 상시 접힌 상태가 된다. 보이지 않는 기능을 켠 것과 같다.
- **서랍(navigation panel) 안에만 노출.** 폭·높이 경쟁이 전혀 없지만 서랍을 열어야 보인다. 사용량 위젯의 존재 이유가 곁눈질인데 그 값이 사라진다. 다만 이 안은 폐기가 아니라 **범위 밖**이다 — 스트립이 있는 지금도 상세 표면을 서랍에 추가하는 것은 별개 결정으로 가능하다.
- **원격이 원시 스냅샷을 받아 직접 행을 계산.** 페이로드가 작고 원격이 자기 표시를 통제할 수 있지만, 행 선택·색·실패 문구 규칙이 두 벌이 되어 같은 계정이 화면마다 다르게 읽힌다. [ADR-0105](0105-widget-slots-and-status-line.md) 가 행 선택 SoT 이중화를 기각한 이유가 그대로 적용된다.
- **원격 서버(Rust)가 usage probe 를 직접 읽어 페이로드를 조립.** 데스크톱 WebView 상태와 무관해져 견고하지만, Claude 행 계산을 Rust 에 복제해야 하고 Codex 는 원격용 폴러가 하나 더 생겨 app-server 기동이 표면 수만큼 늘어난다. 원격이 자기 probe 수요를 갖게 되면서 수명 규칙(lease 만료·폴 중단 시 회수)도 새로 만들어야 한다.
- **원격에서도 `collapse` + 오버플로 팝오버.** 데스크톱과 정책이 같아 설명이 하나로 끝나지만, 팝오버가 터미널을 덮고 접힘 순서 규칙(가장자리에서 먼 쪽부터)이 좌우 정렬만 남은 원격 스트립에서는 근거를 잃는다.
- **위젯 데이터를 lease 뒤에 두기.** 제어 API 와 게이트가 통일되지만, 열람 접속에서 지표가 사라진다. 위젯은 호스트를 바꾸지 않으므로 제어 권한을 요구할 근거가 없다.
- **`remote.widgets` 게이트 없이 항상 표시.** 설정이 하나 줄지만, 스트립은 데스크톱과 달리 터미널 행을 직접 깎으므로 배치를 지우지 않고 표면만 포기할 수단이 필요하다.

## Consequences

- 원격에 새 상시 표면과 새 read-only 엔드포인트가 생긴다. `/remote/v1/widgets` 는 `remote_guard` 뒤, lease 밖에 있는 두 번째 열람 라우트다.
- 위젯 표시 모델이 **외부 계약**이 된다. `kind` 값과 항목 필드는 원격 클라이언트가 의존하므로 이름 변경은 새 결정으로 다룬다. 반대로 데스크톱 위젯 종류가 늘어나는 것은 계약 변경이 아니다 — 기존 `kind` 로 사상되는 한 원격은 그대로 동작한다.
- 원격 표시는 데스크톱 프론트가 살아 있고 그 위젯을 그리고 있을 때만 값을 갖는다. 데스크톱이 값을 갖지 못한 상태(probe 실패·미기동)는 같은 문구로 원격에 전달되며, 브리지가 응답하지 않으면 스트립은 마지막 값을 계속 보여주지 않고 실패를 드러낸다.
- 원격 폴이 브리지 요청을 주기적으로 발생시킨다. 그릴 항목이 없는 동안에는 주기를 늦춰 비용을 줄이지만 폴 자체를 멈추지는 않으므로, 원격 클라이언트 하나당 상시 요청이 하나 늘어난다. `settings.remote.widgets` 가 꺼져 있으면 이 요청은 브리지에 닿지 않고 호스트에서 즉시 답한다.
- `settings.remote` 에 `widgets` 가 추가된다. 기본값 `true` 이므로 위젯을 이미 배치해 둔 사용자는 별도 조작 없이 원격에서도 보게 된다.
- 후속 문서 작업: `api-contracts.md` §10 의 `remote` 블록에 `widgets` 를 추가하고, §13 Remote UI API 에 `/remote/v1/widgets` 계약과 표시 모델을 기술한다. §10 위젯 섹션의 "편집 UI 는 Settings 한 곳"이라는 서술은 원격이 편집 표면이 아니라는 점에서 그대로 유효하다.
- 재검토 조건: 원격에서 위젯 배치를 편집하고 싶어지거나 기기별로 다른 배치가 필요해지면 배치 SoT 단일화 전제가 깨지므로 새 결정이 필요하다. 원격이 데스크톱 프론트와 무관하게 지표를 보여야 하는 요구(데스크톱 WebView 가 잠든 상태에서의 열람)가 생기면 데이터 소유를 Rust 로 옮기는 대안을 다시 검토한다.
