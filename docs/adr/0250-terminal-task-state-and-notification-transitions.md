# 0250. 터미널 작업 상태와 확인 알림은 공통 전이로 판정한다

- Status: Proposed
- Date: 2026-09-16
- Source: 사용자 v1.0.3 Astra 모래시계 제보와 상태·알림 단순화 합의 및 설계 리뷰, [PR #1046](https://github.com/kochul2000/laymux/pull/1046), [PR #1047](https://github.com/kochul2000/laymux/pull/1047), [architecture/data-flow.md §9](../architecture/data-flow.md), [architecture/api-contracts.md §15.6](../architecture/api-contracts.md)

## Context

v1.0.3은 앱 종류, 출력 활동, 작업 상태, 표시와 알림에 서로 다른 판단 경로를 사용한다. Codex의 `completed`를 확인하면 출력과 무관하게 완료를 표시하지만, 턴 조회가 미확인으로 돌아가면 셸의 출력 기반 판정으로 fallback한다. 유휴 입력부를 다시 그리는 Astra 반짝이도 이 경로에서 모래시계를 유지할 수 있다. 사용자는 비-Astra에서는 완료 체크나 완료 알림 없이 모래시계만 사라진다고 확인했다. 이는 출력 타이머의 해제와 실제 완료 확인을 구분해야 하는 사례다. 제보 pane의 실제 턴 관측 실패 원인은 아직 확정하지 않았다.

현재 `—`에는 작업 없음·중단·미확인이, `✓`에는 성공 완료·입력 대기가 섞여 있다. 알림은 아이콘과 별도로 발생하며, 조회 실패가 이전 관측을 삭제하면 같은 세션의 완료를 다시 확인해도 최초 관측으로 취급되어 알림이 생략된다. 절전은 아이콘을 역으로 읽고 실제 clear 보호는 다른 busy 규칙을 읽으므로 같은 터미널의 의미도 소비자마다 달라진다.

ADR-0147의 출발점은 사용자 요구인 “shell에 출력이 계속되고 있으면 working이어야 한다”였다. 이를 단순히 폐기하지 않고 **출력 활동을 별도 배지로 유지하는 안**을 선택한다. 다만 출력만으로 ⏳를 띄우던 계약은 부분 대체하며, 볼륨이 작업 경계의 증거는 아니라는 ADR-0147의 제약은 유지한다. 통합 없는 셸·임의 TUI는 작업이 미확인이어도 출력 활동은 보이고, 그 활동이 끝났다고 종료 알림을 만들지는 않는다. 출력 감지 자체를 없애는 결정이 아니다.

Claude는 현재 타이틀 스피너·`✳` 및 승인 프롬프트를, Grok은 작업 타이틀과 출력 fallback을 사용한다. 이 리포에는 두 앱의 턴 종료·결과를 모두 읽는 구조화 lifecycle 관측기가 없다. 문자 목록을 새 권위처럼 선언하거나 없는 JSONL·hooks 경로를 가정하지 않고, 기존 타이틀의 인정 범위와 미지원 관측을 명시해야 한다. 특히 Grok은 ADR-0156에서 선언 유휴 신호가 없다고 정했다.

범위는 셸·Claude·Codex·Grok이 제공할 수 있는 관측을 공통 작업 상태로 해석하고, 표시·자동 알림·절전·clear 보호와 Desktop/Remote/Automation이 이를 공유하는 것이다. 모든 앱이 네 상태와 종료 결과를 전부 관측할 수 있다고 보장하지 않는다. 앱 종류를 판정하는 프로세스 liveness, PTY 전송·터미널 렌더링, 에이전트 실행 방식 변경·hooks 설치·새 transcript reader와 외부 의존성 도입은 범위 밖이다. 기존 앱별 관측 경로를 활용하며, 이 ADR만으로 제보의 런타임 원인이 수정됐다고 주장하지 않는다.

## Decision

**작업은 네 상태로 판정하고 종료 결과·관측 상태·출력 활동을 분리하며, 최초 복원이 아닌 입력 대기 진입과 작업 종료에서만 확인 알림을 한 번 발생시킨다.**

### 작업 상태와 결과

- **작업 상태**는 작업 없음·진행 중·입력 대기·종료, **종료 결과**는 성공·실패·중단이다. 결과는 관측한 경우에만 채우며, 종료만 알면 결과는 비워 둔다. “완료”는 성공을 말할 때만 쓰고 공통 경계는 “종료”로 부른다.
- **관측 상태**는 확인(현재 대상에 대한 유효한 관측), 미확인(유효한 관측 없음), 관측 지연(stale: 이전 관측은 있지만 현재 유효성을 확인하지 못함)이다. 미확인·관측 지연은 작업 상태가 아니며, 아래에서는 이 세 용어만 사용한다.

| 작업 상태 | 의미                    | 표시                                           | 알림            |
| --------- | ----------------------- | ---------------------------------------------- | --------------- |
| 작업 없음 | 현재 작업이 없음을 확인 | —                                              | 없음            |
| 진행 중   | 작업을 수행 중          | ⏳                                             | 없음            |
| 입력 대기 | 사용자 응답·승인 필요   | 입력 대기 전용 표시                            | 진입할 때 한 번 |
| 종료      | 작업이 끝남             | 성공 ✓ / 실패 ✗ / 중단·결과 미관측은 각각 구별 | 종료할 때 한 번 |

표의 알림에는 아래의 최초 복원·중복 제거 규칙을 적용한다. 성공·실패·중단이나 결과 부재를 별도의 작업 상태·알림 종류로 늘리지 않는다. 결과 부재를 성공·실패·중단으로 채우지 않으며, 나중에 결과만 확인해도 종료 알림을 다시 만들지 않는다. 입력 대기는 작업 종료가 아니며 성공 체크를 사용하지 않는다. 종료와 그 결과는 다음 작업 시작이나 관측 대상 변경 전까지 유지하고, 무출력 타이머로 작업 없음으로 되돌리지 않는다. Codex의 종료는 현재 턴의 종료이며 전체 목표 달성이나 Codex 프로세스 종료를 뜻하지 않는다.

미확인에는 작업 상태를 채우지 않고, 관측 지연에는 마지막 작업 상태와 지연 표시를 함께 둔다. 출력 활동 배지는 네 상태와 독립적으로 표시하며, 미확인인 비통합 셸도 출력 여부는 알 수 있어야 한다. 배지의 이름은 “출력 활동”이고 ⏳·성공 체크·확인 알림과 구별한다. 입력 대기·중단·결과 미관측·미확인·관측 지연·출력 활동의 구체적인 아이콘·색상·접근성 문구는 후속 구현 PR에 위임하되, 서로 다른 의미를 같은 표시로 합치지 않는다. 아이콘·색상·표시 메시지 문자열은 작업 상태의 근거가 될 수 없다.

### 관측과 상태 소유권

앱 종류, PTY 출력 활동, 앱별 작업 관측은 각각 원시 상태로 저장한다. 입력 대기 관측은 작업 식별자·순서·해소 여부를 가진 어댑터 입력이며, 표시 메시지와 분리한다. 화면·알림 소비자가 읽는 입력 대기 여부는 공통 작업 상태에서만 도출하고 별도의 가변 boolean을 함께 소유하지 않는다. 메시지 문자열에 내부 마커를 넣어 상태를 전달하지 않는다. 프론트엔드의 한 상태 계산 경로가 앱별 관측을 공통 작업 상태·관측 상태로 해석하고, 표현과 동작은 그 결과에서 파생한다. 이 상태는 메모리 전용이며 세션 복원 데이터에 이전 작업의 현재 상태를 저장하지 않는다.

같은 작업의 유효한 입력 대기 관측은 진행 중 관측보다 우선한다. 그 대기를 해소하는 후속 관측은 다시 진행 중으로 바꾸며, 같은 작업을 닫는 후속 종료 관측은 이전 대기를 무효화한다. 닫힌 작업의 늦은 대기 관측은 종료를 되돌리지 못한다. 이 순서·대상 검증은 공통 계산 경로가 소유한다. ADR-0248의 `CodexActivityHandler`와 다른 앱 핸들러는 신호 해석·앱별 clear 입력을 제공하는 어댑터로 남고, 최종 표시·알림·절전·clear 보호를 각각 결정하지 않는다.

### 앱별 신호의 인정 범위

| 앱      | 이번 결정에서 사용하는 관측                                                                                                                         | 해석하지 않는 것                                                                                         |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 통합 셸 | OSC 133 C의 명령 시작, D의 종료·종료 코드, 명령이 없는 프롬프트 경계                                                                                | OSC 133 없는 셸을 무조건 작업 없음으로 간주하거나 무출력으로 종료 추정                                   |
| Codex   | ADR-0248·0249의 현재 세션 턴 기록과 기존 승인·응답 프롬프트 감지                                                                                    | 타이틀·출력 fallback, 이전 셸 종료 코드, 단순 프롬프트 재출력                                            |
| Claude  | 확인된 Claude 세션의 OSC 0/2 작업 스피너 → 진행 중, `✳` → 작업 중이던 구간의 종료 또는 관측 시작 시 작업 없음, 기존 승인·응답 모달 감지 → 입력 대기 | `✳`만으로 성공·중단 구분, 타이틀 이탈만으로 성공 합성, 일반 입력 프롬프트를 승인 요청으로 취급           |
| Grok    | 확인된 Grok 세션의 OSC 0/2 Braille 작업 접두사 또는 Grok 타이틀의 `- Running:` → 진행 중                                                            | 작업 접두사 소멸·단독 `grok`·출력 정지를 종료로 해석. 현재 경로에는 종료 결과·입력 대기 관측 지원이 없음 |

Claude·Grok은 **타이틀 호환 어댑터**로 한정한다. 수신한 타이틀을 기존 앱별 파서로 해석하되 앱 식별은 프로세스 liveness의 권위를 유지한다. 같은 작업 스피너의 반복은 새 작업이 아니며, 턴 ID가 없는 경로는 PTY generation·앱 세션·관측한 작업 구간의 로컬 순서로 묶는다. 타이틀 비활성화·rename·알 수 없는 새 접두사·관측 채널 단절은 유휴나 성공이 아니라 미확인 또는 관측 지연이다. 회전 타이틀은 새로 수신·해석한 신호만 갱신으로 인정하고, 마지막 문자열을 다시 읽어 유효 시간을 연장하지 않는다. 타이틀 회전 신호가 6초 동안 갱신되지 않으면 관측 지연으로 전환한다. OSC 133의 명령 실행처럼 종료까지 유효한 lifecycle은 조용하다는 이유로 지연시키지 않는다.

Claude의 작업 구간 뒤 `✳`는 입력 가능 상태로 돌아왔다는 관측이지 성공 결과의 증명이 아니다. 종료 결과를 비운 채 한 번 알리며, 최초 `✳`에는 종료 알림을 만들지 않는다. 유효한 모달 관측이 있는 동안은 타이틀보다 입력 대기가 우선하며, 모달 해소 후 새로 받은 `✳`에만 종료 해석을 적용한다. Grok의 종료 경계와 두 앱의 정확한 성공·실패·중단을 지원하려면 세션에 귀속된 structured lifecycle 관측을 별도로 설계·검증해야 한다. transcript JSONL·hooks는 이번 결정의 암묵적 전제가 아니다.

일반 PTY 출력량, DEC 2026 프레임, 장식 애니메이션과 무출력 시간은 작업 시작·종료의 증거가 아니다. ADR-0147의 볼륨·프레임 검출과 임계·2초 해제는 출력 활동 배지에 계속 사용하지만, 이 값만으로 네 작업 상태를 변경하거나 작업 알림을 만들지 않는다. 현재 `outputActive`에 섞인 OSC 133 실행 상태와 타이틀 작업 신호는 앱별 작업 관측으로 분리하며, 이 신호만으로 출력 활동 배지의 타이머를 연장하지 않는다. 따라서 타이틀 문자가 바뀌어도 지속 출력은 배지에 남고, 작업 상태만 미확인 또는 관측 지연이 될 수 있다. Codex의 관측 지연을 셸 핸들러나 타이틀 스피너 추정으로 대체하지 않는다. 이전 셸 성공 코드를 다른 앱의 성공으로 재사용하지 않는다.

### 조회 실패와 관측 대상 변경

일시적인 조회 실패·시간 초과·불완전한 기록은 마지막 유효 관측과 알림 이력을 삭제하지 않는다. 같은 관측 대상의 마지막 상태를 보존하고 관측 지연으로 표시한다. 이전 유효 관측이 없으면 미확인으로 남는다. 관측 지연 자체는 진행 중·종료·입력 대기로의 전이가 아니다.

관측과 알림 이력은 terminal의 PTY generation, 실행 앱·세션, 해당 명령 또는 턴에 귀속한다. 프로세스 재시작·세션 전환·새 작업 시작이 확인되면 이전 작업의 상태를 새 작업에 상속하지 않는다. 대화형 입력 제출은 재관측과 진행 중 요청의 유효성 재검사를 유발하지만, `/status` 같은 로컬 명령을 새 작업으로 합성하지 않는다. 현재 작업에 속하지 않는 늦은 응답, 종료 이벤트와 낡은 입력 대기 마커는 현재 상태를 덮지 못한다.

조회 복구 시에는 대상 식별자가 일치하는지 먼저 확인한다. 같은 대상이면 보존한 이전 관측에서 전이를 이어가고, 다른 대상이면 새 관측으로 초기화한다. 관측 지연 표시는 과거 값임을 드러내기 위한 것이며 새 대상의 현재 상태를 확인했다는 의미가 아니다.

### 확인 알림의 단일 기준

알림의 의미는 **사용자가 다시 확인할 차례가 되었다** 하나다. 현재 작업이 입력 대기에 들어가거나 종료됐다는 유효한 관측에서 한 번 발생시킨다. 종료의 성공·실패·중단과 대기 이유는 알림 내용과 기존 표현 속성에 담는다. 알림 여부를 아이콘 전환이나 출력 정지 여부에서 다시 추론하지 않는다.

- 같은 작업의 같은 입력 대기 진입 또는 종료 관측을 반복해서 받아도 알림은 한 번이다. 입력에 응답하고 작업이 진행된 뒤 다른 입력 대기에 들어가는 것은 새 진입이다.
- 최초 조회·앱 재시작·세션 전환 및 이력을 잃은 재연결에서는 종료와 입력 대기를 모두 표시만 복원하고 알리지 않는다. 입력 대기의 최초 관측 예외는 두지 않는다. 현재 요청은 입력 대기 표시로 드러내되 pane N개의 복원으로 N개 알림을 만들지 않는다. 같은 전이 이력을 유지한 재연결은 최초 조회가 아니라 아래의 관측 복구 규칙을 적용한다.
- 이미 관측하던 같은 작업이 `진행 중 → 관측 지연 → 종료`로 확인되면 종료 알림을 한 번 만든다. 관측 지연으로 중복 제거 이력을 지우거나 복구를 무조건 최초 조회로 취급하지 않는다.
- 최초 복원 이후 관측 중인 작업에 새 입력 대기가 발생하면 한 번 알린다. 관측 지연 뒤 새 입력 대기를 확인해도 같은 규칙이다. 이미 입력 대기였던 작업을 다시 확인하거나 작업 종료 뒤 프롬프트를 재출력한 것은 새 진입이 아니다.
- 마지막 진행 중 상태의 출력만 멎거나 조회가 실패한 경우에는 종료 알림을 만들지 않는다. 중단 키를 보냈다는 사실만으로 중단을 확정하지도 않는다.

자동 작업 알림을 발행하는 주체는 프론트엔드의 공통 전이 처리 한 곳이다. 앱별 관측기와 화면 컴포넌트는 상태의 근거를 제공하고 같은 작업 알림을 별도로 발행하지 않는다. 사용자가 명시적으로 보낸 `lx notify`는 독립 알림으로 유지한다. 입력 대기 알림의 도착 시점 보호, 읽음 처리와 OS 알림의 포커스·워크스페이스 조건은 기존 정책을 따른다.

### 소비자와 외부 표면

Desktop selector, Remote, Automation/MCP의 상태 투영은 공통 작업 상태·종료 결과·관측 상태·출력 활동을 읽고 같은 의미를 표시한다. 아이콘은 이 의미의 표현이며 Remote나 API 소비자가 아이콘으로 작업 상태를 재구성하지 않는다. 구체적인 필드와 이벤트 계약은 구현 PR에서 living doc과 함께 갱신한다.

**자동 절전 억제**는 확인된 진행 중 상태를 근거로 한다. 관측 지연이면 마지막 유효한 진행 중 관측부터 **최대 60초까지만** 그 pane의 자동 억제를 유지한다. 실패한 재시도·캐시 재읽기·출력 활동은 이 기한을 연장하지 못하며, 이후 유효한 진행 중 관측을 받으면 다시 억제한다. 기한 만료는 작업 상태나 알림을 바꾸지 않고, 다른 pane의 근거와 수동 `power.keepAwake`는 해제하지 않는다. 마지막 상태가 입력 대기·종료·작업 없음이면 지연 중에도 자동 억제하지 않는다. 예외적으로 lifecycle이 없는 비통합 셸·미지원 TUI는 출력 활동 배지가 켜진 동안 자동 억제를 유지하고 기존 2초 해제로 끝낸다. 이 출력 활동 예외는 Claude·Codex·Grok의 미확인·관측 지연에 적용하지 않는다. 따라서 Codex 조회가 계속 실패하면서 Astra가 출력해도 자동 억제를 무한 연장할 수 없다. 해제 사유는 절전 tooltip에 드러낸다.

**실제 clear**는 확인된 작업 없음·종료에서 제출하고, 진행 중·입력 대기·관측 지연에는 ADR-0158의 `busyPolicy`를 적용한다. **OSC 133을 아직 관측하지 못한 셸의 기본값은 미확인**이지만, PTY 준비가 끝났고 현재 generation의 liveness 조회가 성공했으며 기존 activity 판정이 셸이고, 관측된 실행 중 명령·입력 대기·TUI·출력 활동이 없는 경우에는 기존 셸 clear 제출을 허용한다. 이는 명시적으로 요청한 clear에 대한 best-effort 예외이지 작업 없음의 증거가 아니다. liveness 미확인·관측 지연이나 출력 활동 중이면 `busyPolicy`를 적용하고, 한 번 시작을 관측한 명령의 종료를 놓친 경우에도 이 예외로 보호를 풀지 않는다. 기존 liveness는 알려진 앱의 존재를 판정할 뿐 모든 전경 작업의 부재를 증명하지 않으므로, 조용한 명령·미검출 TUI에 입력이 섞일 수 있는 위험은 남는다. 미확인인 지원 에이전트는 보호하며 전용 handler가 없는 것으로 식별된 TUI는 항상 skip한다. 앱별 clear 입력·`busyPolicy`의 선택지·워크스페이스 Ctrl+L 동작은 유지한다.

절전과 clear의 예외도 공통 상태 계산·정책 경로 한 곳에서 산출한다. 소비자가 원시 신호를 다시 해석하거나 “아이콘이 ⏳인가”로 동작을 정하지 않는다. 같은 상태를 읽되 목적에 따라 다른 정책을 적용한다는 결정이며, 특히 절전의 60초 만료를 clear 허용으로 재사용하지 않는다.

Windows·Linux와 native·WSL은 같은 상태·알림 의미를 사용한다. 파일 접근과 프로세스별 세션 귀속은 기존 플랫폼 경로를 유지하고 관측 실패를 명시적으로 전달한다. 다른 pane의 세션이나 CWD 유사성으로 누락된 근거를 채우지 않는다.

## Alternatives Considered

- **출력 기반 작업 fallback과 임계값 조정 유지.** 반짝이와 실제 작업이 같은 출력 경로를 사용하므로 모델·프레임 주기가 바뀔 때 다시 오판한다. 종료 알림과 출력 타이머의 불일치도 남는다. 출력은 버리지 않고 별도 배지로 유지한다.
- **출력 활동 표시까지 제거.** ADR-0147의 사용자 요구를 통째로 잃고 비통합 셸의 빌드 로그도 보이지 않게 된다. 작업 상태와 출력 활동을 분리하는 안을 택한다.
- **Claude·Grok도 타이틀 목록만으로 완전한 lifecycle을 보장하거나 새 hooks·transcript 수집을 전제.** 전자는 문자 변경에 따른 결함과 결과 오판을 감추고, 후자는 설치·세션 귀속·형식 검증 범위를 늘린다. 기존 신호의 제한적 의미와 미지원 범위를 먼저 고정한다.
- **조회 실패를 미확인으로 덮거나 작업 없음으로 처리.** 이미 확인한 결과와 전이 이력을 잃거나, 진행 중인 작업을 유휴로 보이게 한다. 관측 지연으로 분리하고 마지막 유효 상태를 보존한다.
- **조회 실패 시 아무 표시 없이 기존 값만 유지.** 구현은 짧지만 오래된 진행·성공 표시를 현재 관측으로 오해할 수 있다. 마지막 값은 유지하되 관측 지연을 함께 표시한다.
- **성공·실패·중단·미확인을 모두 작업 상태와 알림 종류로 확장.** 종료 결과와 관측 문제까지 같은 축에 넣어 사용자와 소비자가 불필요하게 많은 조합을 다루게 된다. 작업 상태 네 가지와 종료 결과·관측 상태를 분리한다.
- **관측 지연 중 자동 절전 억제를 무기한 유지.** 고장 난 관측기가 오래된 진행 중 값 하나로 머신을 영원히 깨워 둘 수 있다. 60초를 재관측 유예로 두되, 그 뒤에도 보호가 필요하면 기존 수동 스위치를 사용한다.
- **최초 입력 대기만 알림 예외로 허용.** 재시작·재연결 때 N개 pane이 N개 알림을 재생한다. 입력 대기도 종료와 같이 최초에는 표시만 복원한다.
- **미확인 셸을 작업 없음으로 합성하거나 무조건 skip.** 전자는 알지 못하는 작업을 안전하다고 말하고 후자는 비통합 셸의 Alt+L을 영구 no-op으로 바꾼다. 상태는 미확인으로 유지하고 clear에만 좁은 기존 동작 예외를 둔다.
- **모래시계가 사라지면 알림.** 조회 실패, 타이머 만료와 실제 작업 종료를 구분하지 못한다. 확인된 입력 대기·종료 전이만 알림 근거로 삼는다.
- **Codex의 표시 조건만 수정.** 입력 대기와 성공 체크의 혼용, 중복 알림 발행과 아이콘 기반 절전 판정이 남는다. 공통 상태 계약을 먼저 정하고 앱별 감지 방법은 재사용한다.

## Consequences

- 같은 작업 관측에는 Astra 반짝이 유무와 출력량에 관계없이 같은 상태·알림이 나온다. 출력 활동 배지는 별개다. 성공·실패·중단은 종료 결과로 설명하고 `—`·입력 대기·결과가 없는 종료를 성공처럼 사용하지 않는다.
- 통합 없는 셸·미지원 TUI는 작업 미확인과 출력 활동 배지를 함께 표시할 수 있다. 기존의 출력만으로 ⏳를 띄우던 계약은 사라지지만 출력 표시와 해당 앱의 출력 기반 자동 절전 억제는 남는다. 조용한 작업을 놓치는 한계와 셸 clear의 best-effort 위험은 숨기지 않는다.
- Claude·Grok 타이틀이 바뀌면 작업 미확인·관측 지연이 될 수 있지만 지속 출력 배지는 유지한다. 타이틀만으로 두 앱의 정확한 결과를 제공하지 않으며, 특히 Grok의 종료를 못 읽으면 마지막 진행 중·관측 지연 표시와 기본 clear skip이 이어질 수 있다. 지원 확장은 새 관측 계약이 필요한 후속 작업이지 이 ADR에서 이미 해결한 기능이 아니다.
- 실제 종료 관측이 계속 실패하면 마지막 진행 중 표시는 남지만 그 pane의 자동 절전 억제는 60초 상한으로 끝난다. 타이틀의 6초 갱신 기한과 절전의 60초 유예는 제품 정책값이며 실측으로 입증한 회복 시간은 아니다. 이때 실제 작업이 계속된다면 OS가 잠들 수 있고 수동 `keepAwake`가 필요한 비용을 받아들인다. 지연을 드러내는 것과 관측기 결함을 고치는 것은 모두 필요하며, UI 정리만으로 제보 해결을 완료했다고 판단하지 않는다.
- 같은 작업에서 관측 복구 후 놓쳤던 종료를 한 번 알리는 동작과 실패·중단·결과 미관측 종료의 확인 알림이 추가된다. 최초 종료·입력 대기 복원과 반복 관측은 알리지 않는다. 그 대가로 재시작 전에 이미 입력을 기다리던 pane은 사용자가 상태 표시를 직접 확인해야 한다.
- 기존 핸들러의 표시 반환, 입력 대기 문자열 마커, 자동 알림 직접 발행과 아이콘을 역으로 읽는 소비자를 함께 정리해야 한다. 기존 Lucide 아이콘과 앱별 관측기를 사용하며 별도 상태 머신 라이브러리나 이벤트 저장소는 도입하지 않는다.
- 후속 구현은 TDD로 네 상태·결과 부재·관측 상태 조합, 입력 대기와 종료의 순서·귀속, `진행 중 → 관측 지연 → 종료`의 단일 알림, 최초 성공·실패·중단 종료와 N개 입력 대기의 무알림 복원, 반복 전이 중복 방지, 세션 변경·PTY 교체·늦은 응답 격리, `/review` 부모 턴·`/status` 로컬 명령을 검증한다. Claude·Grok의 정상·변경·비활성 타이틀과 6초 갱신 만료, 장식 출력·비통합 셸의 출력 배지, 60초 절전 상한·출력에 의한 기한 연장 금지·수동 override, 비통합 셸 clear 예외·liveness 미확인·미지원 TUI skip도 고정한다. Desktop/Remote 의미 일치와 실제 제보 원인의 진단·dev 실기 검증은 별도로 남긴다.
