# 0250. 터미널 작업 상태와 확인 알림은 공통 전이로 판정한다

- Status: Proposed
- Date: 2026-09-16
- Source: 사용자 v1.0.3 Astra 모래시계 제보와 상태·알림 단순화 합의, [PR #1046](https://github.com/kochul2000/laymux/pull/1046), [PR #1047](https://github.com/kochul2000/laymux/pull/1047), [architecture/data-flow.md §9](../architecture/data-flow.md), [architecture/api-contracts.md §15.6](../architecture/api-contracts.md)
- Amends: [ADR-0147](0147-output-volume-activity-and-app-declared-idle.md)의 출력 기반 작업 활성 추론, [ADR-0248](0248-codex-turn-lifecycle-activity.md)의 미확인 fallback·조회 복구 알림 정책, [ADR-0114](0114-sleep-prevention-mode.md)의 아이콘 기반 busy 판정, [ADR-0158](0158-activity-aware-single-pane-clear.md)의 실제 clear 보호 판정 근거
- Preserves: [ADR-0005](0005-display-state-raw-separation-compute.md)의 원시 상태 분리, [ADR-0249](0249-codex-review-parent-turn-boundaries.md)의 리뷰 부모 턴 귀속, [ADR-0010](0010-notification-dismiss-on-program-focus-entry.md)·[ADR-0012](0012-focus-entry-clears-requires-action.md)의 알림 읽음 처리

## Context

v1.0.3은 앱 종류, 출력 활동, 작업 상태, 표시와 알림에 서로 다른 판단 경로를 사용한다. Codex의 `completed`를 확인하면 출력과 무관하게 완료를 표시하지만, 턴 조회가 미확인으로 돌아가면 셸의 출력 기반 판정으로 fallback한다. 유휴 입력부를 다시 그리는 Astra 반짝이도 이 경로에서 모래시계를 유지할 수 있다. 사용자는 비-Astra에서는 완료 체크나 완료 알림 없이 모래시계만 사라진다고 확인했다. 이는 출력 타이머의 해제와 실제 완료 확인을 구분해야 하는 사례다. 제보 pane의 실제 턴 관측 실패 원인은 아직 확정하지 않았다.

현재 `—`에는 작업 없음·중단·미확인이, `✓`에는 성공 완료·입력 대기가 섞여 있다. 알림은 아이콘과 별도로 발생하며, 조회 실패가 이전 관측을 삭제하면 같은 세션의 완료를 다시 확인해도 최초 관측으로 취급되어 알림이 생략된다. 절전은 아이콘을 역으로 읽고 실제 clear 보호는 다른 busy 규칙을 읽으므로 같은 터미널의 의미도 소비자마다 달라진다.

범위는 셸·Claude·Codex·Grok의 공통 작업 상태, 그 상태에서 파생되는 표시·자동 알림·절전·clear 보호와 Desktop/Remote/Automation의 일치다. 앱 종류를 판정하는 프로세스 liveness, PTY 전송·터미널 렌더링, 에이전트 실행 방식 변경과 새 외부 의존성 도입은 범위 밖이다. 기존 앱별 관측 경로를 활용하며, 이 ADR만으로 제보의 런타임 원인이 수정됐다고 주장하지 않는다.

## Decision

**작업은 작업 없음·진행 중·입력 대기·종료의 네 상태로 판정하고, 종료 결과와 관측 가능 여부를 분리하며, 확인된 입력 대기 진입과 작업 종료에서만 확인 알림을 한 번 발생시킨다.**

### 작업 상태와 결과

| 작업 상태 | 의미                  | 표시                             | 알림            |
| --------- | --------------------- | -------------------------------- | --------------- |
| 작업 없음 | 아직 시작한 작업 없음 | —                                | 없음            |
| 진행 중   | 작업을 수행 중        | ⏳                               | 없음            |
| 입력 대기 | 사용자 응답·승인 필요 | 입력 대기 전용 표시              | 진입할 때 한 번 |
| 종료      | 작업이 끝남           | 성공 ✓ / 실패 ✗ / 중단 전용 표시 | 종료할 때 한 번 |

성공·실패·중단은 종료 결과다. 별도의 작업 상태나 알림 종류로 늘리지 않는다. 입력 대기는 작업 완료가 아니며 성공 체크를 사용하지 않는다. 종료 결과는 다음 작업 시작이나 관측 대상 변경 전까지 유지하고, 무출력 타이머로 작업 없음으로 되돌리지 않는다. Codex의 종료는 현재 턴의 종료이며 전체 목표 달성이나 Codex 프로세스 종료를 뜻하지 않는다.

미확인은 다섯 번째 작업 상태가 아니라 유효한 작업 관측이 아직 없다는 뜻이다. 이 경우 작업 없음으로 단정하지 않고 미확인임을 표시한다. 아이콘·색상·메시지 문자열은 작업 상태의 근거가 될 수 없다.

### 관측과 상태 소유권

앱 종류, PTY 출력 활동, 앱별 작업 관측은 각각 원시 상태로 저장한다. 입력 대기 여부와 표시 메시지도 별도 필드로 유지하며, 메시지 문자열에 내부 마커를 넣어 상태를 전달하지 않는다. 프론트엔드의 한 상태 계산 경로가 앱별 관측을 공통 작업 상태로 해석하고, 표현과 동작은 그 결과에서 파생한다. 이 상태는 메모리 전용이며 세션 복원 데이터에 이전 작업의 현재 상태를 저장하지 않는다.

앱별 어댑터는 의미가 확인된 시작·종료·입력 대기 신호를 제공한다. 셸은 명령 lifecycle과 종료 코드를, Codex는 현재 세션의 턴 기록과 해당 작업의 입력 대기 관측을 사용한다. 다른 지원 앱은 그 앱에서 의미가 정의된 lifecycle 신호를 해석한다. 특정 앱의 명시적 작업 타이틀을 해석하는 것과 임의의 화면 갱신을 활동으로 세는 것은 구분한다.

일반 PTY 출력량, DEC 2026 프레임, 장식 애니메이션과 무출력 시간은 작업 시작·종료의 증거가 아니다. `outputActive`는 독립적인 출력 활동 정보로 남으며, 이 값만으로 네 작업 상태를 변경하거나 작업 알림을 만들지 않는다. Codex의 관측 실패를 셸 핸들러나 타이틀 스피너 추정으로 대체하지 않는다. 지원하는 신호가 없는 앱에는 미확인을 허용하고, 이전 셸 성공 코드를 다른 앱의 성공으로 재사용하지 않는다.

### 조회 실패와 관측 대상 변경

일시적인 조회 실패·시간 초과·불완전한 기록은 마지막 확정 관측과 알림 이력을 삭제하지 않는다. 같은 관측 대상의 마지막 상태를 보존하고, 현재 관측이 지연됐다는 사실을 별도로 표시한다. 이전 확정 관측이 없으면 미확인으로 남는다. 조회 실패 자체는 진행 중·종료·입력 대기로의 전이가 아니다.

관측과 알림 이력은 terminal의 PTY generation, 실행 앱·세션, 해당 명령 또는 턴에 귀속한다. 프로세스 재시작·세션 전환·새 작업 시작이 확인되면 이전 작업의 상태를 새 작업에 상속하지 않는다. 대화형 입력 제출은 재관측과 진행 중 요청의 유효성 재검사를 유발하지만, `/status` 같은 로컬 명령을 새 작업으로 합성하지 않는다. 현재 작업에 속하지 않는 늦은 응답, 종료 이벤트와 낡은 입력 대기 마커는 현재 상태를 덮지 못한다.

조회 복구 시에는 대상 식별자가 일치하는지 먼저 확인한다. 같은 대상이면 보존한 이전 관측에서 전이를 이어가고, 다른 대상이면 새 관측으로 초기화한다. 관측 지연 표시는 과거 값임을 드러내기 위한 것이며 새 대상의 현재 상태를 확인했다는 의미가 아니다.

### 확인 알림의 단일 기준

알림의 의미는 **사용자가 다시 확인할 차례가 되었다** 하나다. 현재 작업이 입력 대기에 들어가거나 종료됐다는 유효한 관측에서 한 번 발생시킨다. 종료의 성공·실패·중단과 대기 이유는 알림 내용과 기존 표현 속성에 담는다. 알림 여부를 아이콘 전환이나 출력 정지 여부에서 다시 추론하지 않는다.

- 같은 작업의 같은 입력 대기 진입 또는 종료 관측을 반복해서 받아도 알림은 한 번이다. 입력에 응답하고 작업이 진행된 뒤 다른 입력 대기에 들어가는 것은 새 진입이다.
- 최초 조회와 세션 전환에서 발견한 과거 종료는 표시만 복원하고 알리지 않는다. 종료를 이미 알린 작업의 재관측도 알리지 않는다.
- 이미 관측하던 같은 작업이 `진행 중 → 관측 지연 → 종료`로 확인되면 종료 알림을 한 번 만든다. 관측 지연으로 중복 제거 이력을 지우거나 복구를 무조건 최초 조회로 취급하지 않는다.
- 아직 응답이 필요한 현재 입력 대기를 처음 확인한 경우에는 입력 대기 진입으로 취급한다. 작업 종료 뒤 남은 프롬프트 재출력은 새 진입이 아니다.
- 마지막 진행 중 상태의 출력만 멎거나 조회가 실패한 경우에는 종료 알림을 만들지 않는다. 중단 키를 보냈다는 사실만으로 중단을 확정하지도 않는다.

자동 작업 알림을 발행하는 주체는 프론트엔드의 공통 전이 처리 한 곳이다. 앱별 관측기와 화면 컴포넌트는 상태의 근거를 제공하고 같은 작업 알림을 별도로 발행하지 않는다. 사용자가 명시적으로 보낸 `lx notify`는 독립 알림으로 유지한다. 입력 대기 알림의 도착 시점 보호, 읽음 처리와 OS 알림의 포커스·워크스페이스 조건은 기존 정책을 따른다.

### 소비자와 외부 표면

Desktop selector, Remote, Automation/MCP의 상태 투영은 공통 작업 상태·종료 결과·관측 신선도를 읽고 같은 의미를 표시한다. 아이콘은 이 의미의 표현이며 Remote나 API 소비자가 아이콘으로 작업 상태를 재구성하지 않는다. 구체적인 필드와 이벤트 계약은 구현 PR에서 living doc과 함께 갱신한다.

절전의 작업 중 판정은 진행 중 상태를 읽는다. 관측이 지연되면 마지막 확정 판정을 유지하고, 관측한 적 없는 터미널을 출력만으로 작업 중이라고 합성하지 않는다. 입력 대기는 작업 중으로 보지 않는다. 실제 clear 제출은 신선하게 확인한 작업 없음·종료에서만 안전하다고 판단하며, 진행 중·입력 대기·관측 지연·미확인에는 기존 보호 정책을 적용한다. 앱별 clear 입력, 미지원 앱의 skip과 사용자가 선택한 busyPolicy는 ADR-0158을 유지한다. 이 차이는 각 동작의 목적에 따른 명시적 정책이고 원시 상태를 각자 다시 해석하는 경로를 만들지 않는다.

Windows·Linux와 native·WSL은 같은 상태·알림 의미를 사용한다. 파일 접근과 프로세스별 세션 귀속은 기존 플랫폼 경로를 유지하고 관측 실패를 명시적으로 전달한다. 다른 pane의 세션이나 CWD 유사성으로 누락된 근거를 채우지 않는다.

## Alternatives Considered

- **출력 기반 fallback과 임계값 조정 유지.** 반짝이와 실제 작업이 같은 출력 경로를 사용하므로 모델·프레임 주기가 바뀔 때 다시 오판한다. 완료 알림과 출력 타이머의 불일치도 남는다.
- **조회 실패를 미확인으로 덮거나 작업 없음으로 처리.** 이미 확인한 결과와 전이 이력을 잃거나, 진행 중인 작업을 유휴로 보이게 한다. 실패는 관측 가능 여부로 분리하고 마지막 확정 상태를 보존한다.
- **조회 실패 시 아무 표시 없이 기존 값만 유지.** 구현은 짧지만 오래된 진행·성공 표시를 현재 관측으로 오해할 수 있다. 마지막 값은 유지하되 관측 지연을 함께 표시한다.
- **성공·실패·중단·미확인을 모두 작업 상태와 알림 종류로 확장.** 종료 결과와 관측 문제까지 같은 축에 넣어 사용자와 소비자가 불필요하게 많은 조합을 다루게 된다. 작업 상태 네 가지와 종료 결과·관측 가능 여부를 분리한다.
- **모래시계가 사라지면 알림.** 조회 실패, 타이머 만료와 실제 작업 종료를 구분하지 못한다. 확인된 입력 대기·종료 전이만 알림 근거로 삼는다.
- **Codex의 표시 조건만 수정.** 입력 대기와 성공 체크의 혼용, 중복 알림 발행과 아이콘 기반 절전 판정이 남는다. 공통 상태 계약을 먼저 정하고 앱별 감지 방법은 재사용한다.

## Consequences

- 같은 작업 관측에는 Astra 반짝이 유무와 출력량에 관계없이 같은 상태·알림이 나온다. 성공·실패·중단은 종료 결과로 설명하고 `—`와 입력 대기를 성공 완료처럼 사용하지 않는다.
- 출력량만 보던 통합 없는 셸이나 지원하지 않는 TUI는 작업 상태가 미확인으로 남을 수 있다. 그 앱의 의미 있는 신호를 지원하는 비용을 받아들이며 무출력 timeout으로 완료를 합성하지 않는다.
- 실제 종료 관측이 계속 실패하면 마지막 진행 중 표시와 절전 억제가 유지될 수 있다. 지연을 드러내는 것과 관측기 결함을 고치는 것은 모두 필요하다. 이 ADR의 UI 정리만으로 제보 해결을 완료했다고 판단하지 않는다.
- 같은 작업에서 관측 복구 후 놓쳤던 종료를 한 번 알리는 동작과 실패·중단 종료의 확인 알림이 추가된다. 과거 종료 복원과 반복 관측은 알리지 않아 재시작·재연결 알림 폭주를 막아야 한다.
- 기존 핸들러의 표시 반환, 입력 대기 문자열 마커, 자동 알림 직접 발행과 아이콘을 역으로 읽는 소비자를 함께 정리해야 한다. 기존 Lucide 아이콘과 앱별 관측기를 사용하며 별도 상태 머신 라이브러리나 이벤트 저장소는 도입하지 않는다.
- 후속 구현은 TDD로 네 상태·종료 결과·관측 지연 조합, `진행 중 → 조회 실패 → 종료`의 단일 알림, 과거 완료 무알림, 반복 입력 대기·완료 중복 방지, 세션 변경·PTY 교체·늦은 응답 격리, `/review` 부모 턴·`/status` 로컬 명령, 장식 출력의 유무, Desktop/Remote·절전·clear 정책 일치를 검증한다. 실제 제보 원인의 진단과 dev 실기 검증도 별도로 남긴다.
- 이번 PR은 Proposed ADR과 인덱스만 변경한다. 방향 승인 후 Accepted로 전환하며, 런타임 코드·외부 필드 계약과 `docs/architecture/`는 후속 구현 PR에서 함께 갱신한다. Accepted된 선행 ADR 본문은 이 제안 단계에서 수정하지 않는다.
- 관측 가능한 앱 신호가 사라지거나 새로운 작업·입력 대기 구조가 이 네 상태로 표현되지 않을 때 결정 범위를 재검토한다. 렌더링 변화만으로 작업 상태나 알림 종류를 추가하지 않는다.
