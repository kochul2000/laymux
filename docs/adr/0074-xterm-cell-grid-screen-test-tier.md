# 0074. 화면 주장은 mock 이 아니라 실제 xterm 셀 격자로 검증한다

- Status: Proposed
- Date: 2026-07-27
- Source: issue #605 · [ADR-0072](0072-terminal-output-gap-sequence-exact-repair.md) Consequences 마지막 두 항목 · issue #600 · issue #602 · issue #596 · [dev-repro-methodology.md](../dev-repro-methodology.md) §4·§5
- Relation: ADR-0072 가 "현 harness 로 검증할 수 없다"고 명시하고 #605 로 분리한 두 주장 중 (a) 를 검증 가능하게 만든다. ADR-0058 의 단일 셀 폭 provider 를 테스트 표면에도 적용한다.

## Context

데스크톱 터미널의 상당수 주장은 **"이 바이트를 흘리면 화면 셀이 이렇게 된다"** 형태다.
그런데 `TerminalView.test.tsx` 는 xterm 을 mock 하고, 그 mock 의 `write` 는 문자열을 기록할 뿐
VT 파서에 닿지 않으며 `reset` 은 버퍼를 비우지도 `onScroll` 을 쏘지도 않는 `vi.fn()` 이다.
컴포넌트 배선(무엇을 몇 번 호출했나)에는 충분하지만, 셀 격자에 대한 주장은 **표현 자체가 불가능**하다.

그래서 미검증으로 남은 것들이 실제로 있다.

- ADR-0072 Consequences (7) — "차분 렌더 프레임 시퀀스가 복구 뒤 원래 화면과 셀 단위로 같아진다."
  sequence-exact 복구가 존재하는 이유 그 자체인데, 그 ADR 스스로 이 항목이 추론임을 적어두고 있다.
  반대편 주장(재부착은 화면을 잃는다)도 같은 이유로 실행된 적이 없다 — issue #596 의 근거는
  사용자 캡처 PNG 를 픽셀 디코딩한 1회성 측정이었다.
- issue #602 — `reset()` 이 동기 `onScroll` 을 발행해 조합 앵커를 scrollback 높이만큼 민다.
  mock 이 이벤트를 안 쏘므로 재현 테스트를 쓸 수 없다.
- issue #596 계열 — overlay caret 열, 전각 경계, 조합 프리뷰 배치.

`dev-repro-methodology.md` 는 이 계층의 진단을 dev 실기 + 계측으로 처리하라고 정해 두었고 그것은 유효하다.
그러나 실기 측정은 **반복 가능한 회귀 테스트가 아니다.** 같은 문서 §5 가 요구하는 사보타주 검증
("수정을 되돌리면 그 테스트가 정말 실패하는가")을 화면 주장에 대해서는 지금 수행할 수단이 없다.

제약: 기존 데스크톱 스위트는 3,199개이고 25초 안에 끝난다. 실제 xterm 인스턴스를 세워 바이트를
흘리는 테스트는 그보다 무겁고, 목적도 다르다. 범위는 프론트엔드 테스트 계층 구성이며,
Rust 테스트·e2e(Playwright)·실기 검증 절차는 비목표다.

## Decision

**셀 격자에 대한 주장은 mock 이 아니라 `open()` 하지 않은 실제 `@xterm/xterm` 인스턴스에
바이트를 흘려 검증하고, 그 테스트는 `*.screen.test.ts` 라는 별도 vitest 스위트에 둔다.**

- **표면**: `ui/src/test/screen/xterm-screen.ts` 가 유일한 진입점이다. `new Terminal()` 후
  `terminal.open()` 을 호출하지 않는다 — 렌더러·캔버스·레이아웃 없이 VT 파서와 버퍼만 쓴다.
  주장이 사는 계층이 거기이고, 렌더러를 붙이면 jsdom 이 흉내 내지 못하는 것들이 딸려 온다.
- **폭 계약은 프로덕션과 같다**: 하니스는 첫 write 보다 앞에서 `activateTerminalUnicodeProvider`
  를 호출한다(ADR-0058, `TerminalView` 와 같은 순서). 하지 않으면 셀 폭이 xterm 기본값이 되어
  출하되는 것과 다른 격자를 검증하게 된다.
- **비교 단위는 셀이다**: `chars`·`width`·fg/bg·속성 플래그와 커서를 함께 본다. 행 문자열만 비교하면
  SGR 손실과 전각 continuation 붕괴를 놓친다.
- **역방향 단정을 1급으로 지원한다**: 비교 함수는 던지지 않고 차이를 문자열로 돌려준다.
  "이 경로로는 복원되지 않는다"(결함의 존재 증명)가 이 계층에서 가장 중요한 단정 중 하나이기 때문이다.
  결함 증명에는 **대조군을 실행 가능한 상태로 유지**한다 — 폐기된 복구 전략(재부착)을 하니스가
  선택지로 들고 있는 이유이며, 그래야 "현재 코드가 무언가와 다르다"가 아니라 "옛 경로는 이렇게 잃는다"를 보인다.
- **스위트 분리**: `vitest.screen.config.ts` + `npm run test:screen`. 기본 `vitest.config.ts` 는
  `*.screen.test.*` 를 exclude 하므로 `npx vitest run` 의 구성과 실행 시간은 그대로다. 화면 스위트는
  React 플러그인·i18n·jest-dom·ResizeObserver shim 을 쓰지 않는다 — 컴포넌트를 렌더하지 않으므로 필요 없다.
- **경계**: 화면 테스트는 컴포넌트를 렌더하지 않는다. 프로덕션 코드(coordinator, unicode provider,
  anchor 기하)를 직접 구동하고, `TerminalView` 가 그 순서로 배선했는지는 계속 `TerminalView.test.tsx`
  가 소유한다. 두 스위트는 같은 주장의 서로 다른 절반을 덮으며, 화면 스위트가 컴포넌트 배선을
  검증한다고 주장하지 않는다.
- **백엔드 대역은 계약만 흉내 낸다**: `output-ring.ts` 는 `record`/`attach`/`resume` 세 연산과
  clamp 하지 않는 `null` 계약만 재현한다. Rust ring 의 진실은 계속 `src-tauri` 테스트가 소유한다.

## Alternatives Considered

- **mock 의 `reset` 을 실제 시맨틱(버퍼 비움 + 동기 `onScroll`)으로 보강한다** — #602 재현에는
  도움이 되지만 파서가 없다는 근본 한계는 그대로다. "바이트 → 셀" 주장은 여전히 못 쓴다. 게다가 mock 을
  실물에 가깝게 키우는 것은 실물의 2차 구현을 만드는 길이고, 어긋나는 날 조용히 틀린 답을 준다.
  (열린 PR #608 이 같은 파일을 손대고 있어 충돌 비용도 실재한다.) 기각 — 다만 #602 수정 PR 이
  컴포넌트 계층 재현을 위해 mock 을 보강하는 것은 이 결정과 상충하지 않는다.
- **`@xterm/headless` 를 새 의존성으로 추가한다** — 출하되는 번들이 아니다. 이 리포는 `@xterm/xterm`
  6.0.0 을 고정하고 postinstall 로 두 군데를 패치한다(reflow, `disableStdin` gate). headless 패키지는
  그 패치를 받지 않으므로 "출하되는 것과 같은 파서"라는 성질을 잃는다. jsdom 에서 `open()` 없는
  `Terminal` 이 이미 파싱·버퍼 접근·동기 `onScroll` 을 모두 제공한다는 것을 실측으로 확인했다. 기각.
- **화면 테스트를 기본 스위트에 섞는다** — 지금은 11개라 3초지만, 이 계층은 시나리오당 수십 프레임을
  파싱하므로 늘어나는 방향이 명확하다. 무엇보다 두 스위트는 질문이 다르다. 섞으면 "터미널 화면
  테스트만 돌린다"는 선택지가 사라진다. 기각.
- **e2e(Playwright)로 실브라우저에서 검증한다** — 실제 렌더러까지 덮지만 프레임 시퀀스 하나당 앱
  기동이 필요하고, 셀 격자를 읽으려면 결국 같은 buffer API 를 쓴다. 비용 대비 추가로 얻는 것이
  렌더러뿐이며, 렌더러 결함은 `/screenshot`·실기 절차의 몫이다. 기각.
- **사용자 캡처 PNG 픽셀 디코딩을 자동화한다**(#596 에서 실제로 쓴 방법) — 폰트·DPI·테마에 묶이고
  재현하려면 headful 앱이 필요하다. 진단 도구로는 유효했지만 회귀 테스트로는 부적합하다. 기각.

## Consequences

- ADR-0072 Consequences (7) 이 실행되는 단정이 됐다. 같은 프레임 시퀀스를 무손실 경로와 gap+복구
  경로로 흘려 셀·커서까지 동일함을 비교하고, 복구가 아무것도 적용하지 않도록 되돌리면 그 테스트가
  실패한다는 것(사보타주)을 확인했다.
- 그 반대편, 즉 **`reset()` + truncated replay 는 복원하지 못한다**가 처음으로 실행 가능한 형태로
  기록됐다. 프로그램이 한 번만 칠하고 다시 쓰지 않는 행은 재생 뒤 영구히 빈 채로 남는다.
- 대조군을 정직하게 유지하기 위해 ring 절단을 프레임 경계에서 한다. 실제 ring 은 바이트 예산으로
  자르므로 보통 escape 중간에서 끊기고, 그러면 화면이 깨지는 이유가 둘("재칠하지 않는 셀" + "깨진
  시퀀스")로 섞여 무엇을 증명했는지 흐려진다. 하니스의 `evictTo(seq)` 는 이 목적 전용이다.
- 새 계층이 하나 늘었으므로 **어느 스위트에 쓸지 판단**이 필요해진다. 기준: 셀 격자·커서·폭·`reset()`
  같은 xterm 실동작이 주장의 일부면 화면 스위트, 컴포넌트가 무엇을 호출하는지가 주장이면 기존 스위트다.
- `npx vitest run` 은 그대로다(3,199개 / 25초, 이 PR 전후 동일). 화면 스위트는 11개 / 3.2초이며
  `/full-test` 1단계에 한 줄이 늘어난다.
- 하니스의 `output-surface-driver.ts` 는 `TerminalView` 의 gap→복구 흐름을 30줄 남짓 재현한다.
  **이것은 중복이고 표류할 수 있다.** 표류의 대가는 "화면 스위트가 통과하는데 실제 배선은 다르다"이며,
  그 위험을 줄이려고 coordinator·에러 분류·카운터 이름은 프로덕션 것을 그대로 쓴다. 복구 흐름의
  단계 자체가 바뀌면 이 드라이버도 같은 PR 에서 따라가야 한다.
- 남은 것: issue #602 의 **컴포넌트 계층** 재현(하니스는 `reset()` 이 동기 `onScroll` 로 baseY 를
  무너뜨린다는 선행 사실만 고정한다)과 issue #596 의 overlay caret **DOM** 배치(하니스는 버퍼 커서
  열과 앵커 픽셀 오프셋까지만 고정한다). 둘 다 각 이슈에서 다룬다.
- 재검토 조건: 화면 스위트가 수십 초대로 커지거나(그때는 프레임 스크립트를 공유 fixture 로 접는다),
  xterm 을 `open()` 해야만 표현되는 주장이 필요해지면(그때는 e2e 로 승격) 이 결정을 다시 본다.
