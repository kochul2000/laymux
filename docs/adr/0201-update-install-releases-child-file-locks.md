# 0201. 업데이트 설치기를 부르기 전에 앱이 자기 자식 프로세스를 정리한다

- Status: Proposed
- Date: 2026-08-25
- Source: 사용자 보고(업데이트마다 NSIS `Error opening file for writing: ...\OpenConsole.exe`), [ADR-0174](0174-github-signed-desktop-self-update.md) 확장, [ADR-0066](0066-bundled-conpty-runtime.md)·[ADR-0067](0067-bundled-conpty-output-and-staging-contract.md)·[ADR-0102](0102-claude-usage-probe-headless-pty.md)

## Context

Windows 설치본은 ConPTY 재배포본(`conpty.dll` + `OpenConsole.exe`)을 실행 파일 옆,
즉 설치 디렉터리에 둔다(ADR-0066/0067). 터미널을 열 때마다 `conpty.dll` 이 그
`OpenConsole.exe` 를 콘솔 호스트 프로세스로 띄우므로, 터미널이 하나라도 살아 있는
동안 설치 디렉터리의 실행 이미지가 프로세스에 매핑돼 있다.

자체 업데이트는 서명된 NSIS 설치기를 내려받아 실행한다(ADR-0174). 그런데 설치기를
띄우는 쪽은 앱 자신이고, 앱은 그 직후 즉시 사라진다 — updater 는 설치기를
`ShellExecuteW` 로 띄운 뒤 `std::process::exit(0)` 한다. `process::exit` 는 소멸자를
돌리지 않으므로 앱이 소유한 PTY 자식들을 정리하는 경로가 통째로 건너뛰어진다.
그 결과:

1. 앱 프로세스만 사라지고 셸과 `OpenConsole.exe` 는 살아남는다.
2. NSIS 템플릿은 메인 바이너리 이름 하나만 확인하므로, 이미 죽은 그 프로세스를 보고
   곧바로 파일 쓰기에 들어간다.
3. 매핑된 `OpenConsole.exe` 는 쓰기 공유를 거부하므로 설치기가 공유 위반(오류 32)을
   만나 Abort/Retry/Ignore 대화상자를 띄운다.
4. 몇 초 뒤 고아가 된 셸이 끊긴 파이프를 보고 죽으면 콘솔 호스트도 따라 죽어 락이
   풀리므로, 사용자가 "다시 시도"를 누르면 성공한다.

즉 재현이 100%에 가깝고 회피책이 "몇 초 기다렸다 다시 시도"뿐인, 타이밍에 좌우되는
설치 실패다. 앱이 자기 자식을 정리하지 않은 채 설치기를 부른 것이 원인이며 설치기
쪽 결함이 아니다.

범위는 자체 업데이트 설치 직전의 자식 프로세스 정리와 그 완료 확인이다. 일반 종료·
크래시 경로의 고아 자식 문제, 번들 런타임의 배치 방식, 설치기 템플릿 자체는 비목표다.

## Decision

**자체 업데이트는 설치기를 띄우기 전에 앱이 소유한 모든 자식 프로세스를 끝내고, 설치
대상 파일이 실제로 쓰기 가능해질 때까지 유계 대기한 뒤에만 설치기로 넘어간다.**

- **정리 책임은 앱에 있다.** 설치기는 자기 대상 파일을 쥔 남의 프로세스를 추적하지
  않는다. 자식을 만든 쪽이 자식을 끝낸다.
- **정리 시점은 `on_before_exit` 훅이다.** 다운로드가 끝나고 설치기를 띄우기 직전,
  `process::exit(0)` 보다 앞선 유일한 동기 지점이다. 여기서 블로킹하는 것은 설치를
  그만큼 늦추는 것이며, 이 지연이 이 결정이 사는 목적이다.
- **정리 대상은 레지스트리 PTY 와 probe PTY 둘 다다.** probe PTY 는 의도적으로
  `pty_handles` 밖에 있으므로(ADR-0102) 따로 종료하지 않으면 남는다. 앱 종료 시
  하던 정리와 같은 대상·같은 순서를 쓰고, 그 절차는 한 곳이 소유한다.
- **완료 판정은 "프로세스가 사라졌나"가 아니라 "파일을 쓰기로 열 수 있나"다.**
  설치기가 실패하는 조건이 곧 판정 조건이어야 한다. 프로세스 목록·이름 대조는
  같은 이름의 남의 콘솔 호스트를 오탐할 수 있고, 락의 주체를 다 열거했다는 보장도
  없다.
- **대기는 유계이고 실패해도 설치를 막지 않는다.** 제한 시간 안에 풀리지 않으면
  경고만 남기고 설치기를 띄운다. 사용자는 지금과 같은 대화상자를 보게 되지만,
  업데이트 자체를 앱이 거부하는 것보다 낫다.
- **자식 정리는 모든 플랫폼에서, 파일 잠금 대기는 Windows 에서만 한다.** 업데이트는
  어차피 재시작을 뜻하므로 실행 중 터미널을 끝내는 것은 플랫폼 공통으로 옳다.
  실행 중 이미지의 쓰기 거부는 Windows 고유 제약이다.

## Alternatives Considered

- **설치기(NSIS) 훅에서 잠긴 파일을 rename 후 진행.** Windows 는 실행 중 실행 파일의
  rename 을 허용하므로 락과 무관하게 덮어쓸 수 있다. 기각: 원인이 아니라 증상을 가린다.
  고아 셸과 콘솔 호스트는 그대로 남아 사용자의 다음 세션과 섞이고, 설치기 템플릿에
  플랫폼 트릭을 얹는 부채가 생긴다. 앱 정리를 먼저 세운 뒤에도 남는 잔여 위험이
  관측되면 그때 별도 결정으로 다시 검토한다.
- **설치기 쪽에서 이름으로 `OpenConsole.exe` 를 죽인다.** 기각: 같은 이름의 프로세스는
  Windows Terminal 등 남의 것도 있다. 남의 콘솔을 죽이는 설치기는 받아들일 수 없다.
- **고정 시간(예: 3초) 슬립.** 기각: 짧으면 못 고치고 길면 매번 손해다. 실제 조건을
  재는 대신 운을 재는 방식이다.
- **updater 를 포크해 `process::exit` 를 제거하고 정상 종료 경로를 타게 한다.**
  기각: 공급망 비용이 훅 하나보다 훨씬 크고, 훅으로 같은 결과를 얻는다.
- **터미널을 죽이지 않고 파일만 기다린다.** 기각: 자식이 살아 있는 한 락이 풀리지
  않는다. 대기만으로는 영원히 실패한다.

## Consequences

- 업데이트 설치가 대화상자 없이 한 번에 끝난다. 설치 직전 수 초의 정리 지연이 생기며,
  이는 사용자에게 이미 "설치 중" 상태로 보이는 구간이다.
- 업데이트를 누르면 실행 중이던 터미널의 자식 프로세스가 강제 종료된다. 재시작을
  동반하는 동작이므로 손실 자체는 새로 생기지 않지만, 지금까지 고아로 살아남던
  프로세스가 이제 확실히 죽는다는 점은 동작 변화다.
- 자식 정리 절차의 소유자가 한 곳으로 모여 종료 경로와 업데이트 경로가 갈라지지
  않는다.
- 대기 상한을 넘기면 기존과 같은 실패로 되돌아간다. 상한을 넘겼다는 사실은 로그로
  남기며, 실제로 관측되면 설치기 훅 대안을 다시 연다.
- 일반 종료·크래시 시의 고아 자식 문제는 이 결정이 다루지 않는다. 같은 정리 함수를
  재사용할 수 있는 자리가 생겼을 뿐이다.
