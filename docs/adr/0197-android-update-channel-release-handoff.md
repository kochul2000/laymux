# 0197. Android 앱은 기기-로컬 채널 설정으로 릴리스 채널을 따라가고 업데이트는 GitHub 릴리스 페이지로 넘긴다

- Status: Accepted
- Date: 2026-08-24
- Source: 사용자 요구("안드로이드로 똑같이 채널을 stable 과 beta 따라가게 pc 랑 똑같이 해줘. 그래서 해당 github 릴리즈 페이지까지 이동하도록") · [ADR-0190](0190-update-release-channels.md) · [ADR-0174](0174-github-signed-desktop-self-update.md) · [ADR-0172](0172-android-e2e-compat-version-gate.md)
- Extends: ADR-0190 — ADR-0190 이 후속 ADR 로 분리한 "Android 앱의 자체 업데이트와 그에 필요한 Android 채널 설정"을 확정한다. ADR-0190 의 결정(채널 두 개, 채널 매니페스트가 SoT, versionCode 슬롯 인코딩, 게시 게이트)은 정정하지 않는다.

## Context

ADR-0190 은 데스크톱에 stable·beta 두 채널을 만들고 `release-channels` 브랜치의 채널 매니페스트를 "지금 최신"의 단일 진실원으로 정했다. 같은 결정에서 Android 는 beta APK 발행과 versionCode 슬롯 확보까지만 하고, 앱이 채널을 따라가는 부분은 **명시적으로 비목표**로 남겼다. 이유는 신뢰 경계였다 — APK 다운로드·해시 검증·`PackageInstaller` 설치·설치 권한은 Tauri updater 의 서명 검증과 전혀 다른 경로이고, Play 배포로 전환하면 그 경로 자체가 폐기된다.

그 결과 지금 폰은 자기 버전에 대해 아무것도 모른다. APK 는 GitHub 릴리스에 올라가지만 앱 안에는 버전 비교도, 채널 개념도, 릴리스로 가는 링크도 없다. 사용자는 데스크톱이 업데이트된 사실을 통해서만 폰도 갱신해야 함을 추측하고, 릴리스 페이지 주소를 손으로 찾아 들어간다. ADR-0172 의 compat version 이 올라간 릴리스에서는 이 무지가 더 아프다: 폰은 연결 거부만 보고, 왜 거부됐는지도 무엇을 설치해야 하는지도 앱 안에서 알 수 없다. ADR-0190 은 이 구간을 "Android 자체 업데이트가 생기면 사라진다"고 적어둔 채 남겼다.

이번 요구는 그 구간을 없애되 설치까지는 가지 않는다. 폰이 채널을 따라가고, 새 버전을 발견하면 **해당 릴리스 페이지로 보내는 것**까지가 요구다. 즉 ADR-0190 이 미룬 것 중 "매니페스트 조회"만 가져오고 "APK 다운로드·설치"는 여전히 두지 않는다. 이렇게 자르면 앱이 새로 얻는 권한이 없다 — 공개 URL 하나를 GET 하고 브라우저를 여는 것뿐이므로, 서명·설치 신뢰 경계는 그대로 닫힌 채다.

작용하는 force 는 네 가지다.

첫째, **폰은 데스크톱과 독립적으로 존재한다.** 앱은 페어링 없이도 켜지고, 페어링이 끊긴 상태로도 켜지며, 데스크톱이 꺼져 있어도 켜진다. 업데이트 확인이 데스크톱 연결에 의존하면 "갱신이 필요한 상태"와 "확인할 수 없는 상태"가 자주 겹친다. 반면 채널을 데스크톱에서 상속하면 PC 에서 채널을 바꾸는 것만으로 폰이 따라온다는 편의가 있다.

둘째, **폰에는 `settings.json` 이 없다.** ADR-0190 이 채널을 설정 스키마에 둔 이유는 Automation·MCP 가 읽고 쓸 수 있어야 했기 때문인데, 폰에는 그 표면이 없다. 반대로 폰에는 페어링 자료를 담는 `PairingVault` 가 있지만 그것은 Keystore 로 감싸고 생체 인증 게이트가 걸릴 수 있는 저장소다 — 채널은 비밀이 아니고, 잠금 해제 전에도 읽혀야 한다.

셋째, **앱에 네이티브 크롬이 없다.** 화면은 사실상 두 WebView(클라우드 대시보드·Remote)와 네이티브 다이얼로그 몇 개다. 상시 노출되는 설정 진입점이 없고, 유일한 네이티브 설정 표면은 클라우드 대시보드가 브리지로 여는 인스턴스별 "연결 설정" 다이얼로그다.

넷째, **버전 문자열 계약이 이미 두 곳에 있다.** `scripts/release/release-version.mjs` 와 `src-tauri/src/app_update.rs` 가 같은 `x.y.z`·`x.y.z-beta.N` 문법을 각각 검사한다. Android 가 세 번째 사본을 만드는 것은 피할 수 없지만(플랫폼이 다르다), 계약이 갈라지면 폰만 후보를 놓치거나 폰만 잘못된 후보를 받는다.

범위는 Android 앱의 채널 설정, 채널별 Android 매니페스트 발행과 검증, 앱의 확인 주기와 판정, 그리고 발견을 알리고 릴리스 페이지로 넘기는 표면이다. 비목표: APK 다운로드·해시 검증·설치(`PackageInstaller`), 시스템 알림과 백그라운드 워커, Play in-app update, 데스크톱→폰 채널 동기화, 다운그레이드 제안, 강제 업데이트(연결 차단).

## Decision

**Android 앱은 기기-로컬 설정이 지정한 채널의 `android-<channel>.json` 매니페스트를 스스로 조회해 자기 `versionName` 보다 높은 버전만 후보로 삼고, 사용자에게 제시하는 유일한 종결 동작은 그 릴리스의 GitHub 릴리스 페이지를 브라우저로 여는 것이다.**

### 채널 선택

- 폰이 따라갈 채널은 **기기-로컬 앱 설정**이며 값은 `"stable"` 또는 `"beta"`, 기본값 `"stable"`, 저장소는 앱-프라이빗 `SharedPreferences` 다. 데스크톱의 `settings.json` 을 상속하지 않는다.
- 알 수 없는 값은 런타임에서 stable 로 해석한다. ADR-0190 과 같은 방향의 편향이다 — 오독이 사용자를 테스트 계열로 올리는 쪽으로 기울면 안 된다.
- 채널은 비밀이 아니므로 `PairingVault` 에 넣지 않는다. 생체 게이트 뒤에 두면 잠금 해제 전에는 확인 자체가 불가능해진다.
- 채널을 바꾸면 즉시 1회 확인을 트리거한다. 주기 확인만으로는 채널을 바꾼 사용자가 다음 확인까지 "후보 없음"만 본다.
- 데스크톱과 폰의 채널은 서로를 구속하지 않는다. 두 설정이 어긋난 상태는 오류가 아니라 정상이며, compat version 이 올라간 beta 데스크톱에 stable 폰이 붙는 조합에서는 ADR-0172 의 거부가 그대로 일어난다. 이 결정은 그 거부를 없애지 않고, 거부를 만난 사용자가 앱 안에서 해결 경로를 찾을 수 있게만 한다.

### 채널 매니페스트

- Android 채널 매니페스트는 `release-channels` 브랜치의 `android-stable.json`·`android-beta.json` 이다. 데스크톱 매니페스트와 **같은 브랜치, 같은 커밋**으로 발행한다. 앱은 `https://raw.githubusercontent.com/kochul2000/laymux/release-channels/android-<channel>.json` 을 고정 endpoint 로 삼으며, host·저장소·브랜치·파일명은 바이너리에 고정하고 설정으로 바꿀 수 없다.
- Android 매니페스트는 Tauri updater manifest 가 아니다. 스키마는 이 결정이 정의하며, 필수 필드는 `version`(발행 버전 문자열), `versionCode`(ADR-0190 인코딩 결과), `releaseUrl`(그 릴리스의 GitHub 릴리스 페이지), `apkUrl`(서명된 APK asset), `apkSha256Url`(그 APK 의 체크섬 asset), `pubDate` 다. `notes` 는 선택이다.
- **매니페스트 내용은 발행 tag 에서 파생한다.** `version`·`versionCode` 는 `scripts/release/android-version-code.mjs` 가 인코딩한 값이고, 세 URL 은 tag 와 APK 파일명 규칙에서 만든다. 릴리스 job 이 손으로 채우는 필드는 없다 — 버전과 URL 이 어긋난 매니페스트를 만들 수 있는 자유도를 두지 않는다.
- `apkUrl`·`apkSha256Url` 은 이번 클라이언트가 쓰지 않는다. 그럼에도 매니페스트에 두는 이유는 발행 시점에만 확실히 알 수 있는 사실(그 릴리스의 asset 이름)을 기록해 두는 편이 낫고, 자체 설치를 붙이는 후속 ADR 이 매니페스트 스키마를 다시 바꾸지 않아도 되기 때문이다. 클라이언트는 없거나 형식이 어긋난 이 두 필드 때문에 확인을 실패시키지 않는다.
- 검증·전진성·쓰기 계획은 데스크톱과 **같은 규칙, 같은 코드**를 쓴다. stable 파일에는 `x.y.z` 만 올릴 수 있고, beta 채널은 항상 stable 이상을 가리키며, 두 채널 모두 전진만 허용하고 같은 버전 재실행은 no-op 이다. Android 파일과 데스크톱 파일의 쓰기 계획은 각 계열의 현재 파일 버전을 각각 읽어 독립적으로 계산한다 — 한쪽 계열만 뒤처진 브랜치 상태에서 다른 쪽의 no-op 판정이 뒤처진 쪽을 영구히 방치하면 안 된다.
- 네 파일은 한 커밋으로 원자적으로 올린다. 부분 갱신은 "데스크톱은 새 버전, 폰은 옛 버전"을 채널이 주장하는 상태를 노출한다.
- **Android 파일 시딩도 게시보다 먼저 성공해야 한다.** 부트스트랩 job 의 조건은 "브랜치가 있는가"가 아니라 "네 파일이 모두 있는가"다. 이 결정 이전에 시딩된 브랜치에는 Android 파일이 없으므로, 조건을 브랜치 존재로 두면 채널을 아는 앱이 나간 뒤 다음 릴리스까지 고정 endpoint 가 404 를 준다.
- 매니페스트를 못 읽으면(404·네트워크 실패·파싱 실패) 업데이트 없음이 아니라 **확인 오류**로 취급한다. 배포 경로가 끊긴 것과 최신 상태를 같은 표시로 접으면 아무도 알아차리지 못한다.

### 클라이언트 판정

- 현재 버전은 `BuildConfig.VERSION_NAME` 이다. 이 값이 `x.y.z`·`x.y.z-beta.N` 으로 파싱되지 않으면(로컬 개발 기본값 등) 확인을 **비활성**으로 다루고 오류로 만들지 않는다.
- debug 빌드는 확인을 비활성으로 시작한다. ADR-0174 가 데스크톱 self-update 에 둔 것과 같은 선이다. 실기 검증을 위해 빌드 시점 환경 변수로 활성화할 수 있게 하되, 그 스위치는 release 빌드의 기본 동작을 바꾸지 않는다.
- 채널별 버전 문법은 데스크톱과 같다. stable 채널 파일은 `x.y.z` 만, beta 채널 파일은 `x.y.z` 또는 `x.y.z-beta.N` 만 받는다. 다른 prerelease 라벨과 build metadata 는 거절한다.
- 비교는 semver 순서이고 **후보는 현재 버전보다 엄격히 높을 때만** 만든다. 다운그레이드는 제안하지 않는다. beta 에서 stable 로 채널을 되돌린 사용자는 stable 이 자기 버전을 넘어설 때까지 후보가 없으며, 이 상태는 오류가 아니라 정상으로 표시한다.
- **`releaseUrl` 은 매니페스트가 준 대로 열지 않는다.** 클라이언트는 그 값이 `https://github.com/kochul2000/laymux/releases/tag/` 하위이고 경로 마지막 성분이 매니페스트 `version` 에 대응하는 tag(`v<version>`)와 정확히 같은지 검사한다. 어긋나면 후보를 만들지 않고 확인 오류로 남긴다. `ACTION_VIEW` 는 이 기능의 유일한 외부 효과이므로, 변조·오발행된 매니페스트가 임의 주소로 사용자를 보내는 경로를 문법 단계에서 끊는다.
- 확인 주기는 데스크톱과 같은 6시간이며, 앱 콜드 스타트와 전면 복귀에서 마지막 확인 시각을 보고 트리거한다. 백그라운드 워커·시스템 알림·주기 알람은 쓰지 않는다 — 앱을 켜지 않은 사용자에게 알릴 필요가 없는 등급의 정보이고, 그 경로는 권한과 배터리 정책을 새로 들여온다.
- `raw.githubusercontent.com` 은 짧은 캐시를 가지므로 요청은 캐시를 우회한다. 확인은 UI 스레드에서 하지 않고, 앱이 파괴된 뒤 도착한 응답은 버린다.

### 표면

- **배너**: 후보가 있을 때만 화면 상단에 네이티브 오버레이로 나타난다. 발견된 버전과 따라가는 채널을 함께 말하고(어느 계열인지 모르면 사용자는 자기가 받은 버전을 해석할 수 없다), 기본 동작은 릴리스 페이지 열기, 보조 동작은 닫기다. 닫기는 **그 버전에 대해서만** 기억한다 — 다음 버전에서는 다시 나타나고, 같은 버전으로 매번 다시 묻지도 않는다.
- 배너는 Remote 표면에서는 나타나지 않는다. 터미널 화면 위에 겹치는 오버레이는 입력 대상을 가리며, 그 시점의 사용자는 업데이트가 아니라 세션에 붙어 있다. 후보는 유지되고 표시만 미룬다.
- 확인 오류는 배너로 올리지 않는다. 네트워크 실패를 배너로 알리면 배너의 의미가 "새 버전 있음"에서 흐려진다. 오류는 설정 표면에만 남긴다.
- **설정 섹션**: 연결 설정 다이얼로그에 앱 업데이트 섹션을 둔다. 현재 버전, 따라가는 채널 선택(beta 경고 포함), 수동 확인과 마지막 확인 시각, 발견된 버전, 릴리스 페이지 열기, 마지막 오류를 한자리에 모은다. 이 다이얼로그가 앱의 유일한 네이티브 설정 표면이므로 새 진입점을 만들지 않고 여기에 붙인다.
- 설정 섹션의 수동 확인은 주기 throttle 을 무시한다. 사용자가 명시적으로 물었을 때 "아직 확인할 시간이 아니다"로 답하지 않는다.
- 표시 상태는 원시 상태(설정 채널·현재 버전·마지막 확인·후보·오류·닫은 버전·보이는 표면)에서 계산하는 순수 함수로 도출한다([ADR-0005](0005-display-state-raw-separation-compute.md)와 같은 방향). 배너와 설정 섹션은 같은 계산의 두 투영이며, 그 계산은 Android 프레임워크 없이 단위 테스트한다.
- 확인 결과를 화면 없이 트리거·관측할 수 있어야 하므로, debug 빌드는 후보를 주입해 배너와 설정 섹션을 결정적으로 띄우는 미리보기 경로를 갖는다(기존 네이티브 표면 미리보기와 같은 등급).

## Alternatives Considered

- **채널을 페어링된 데스크톱에서 상속한다.** PC 에서 채널을 바꾸면 폰이 자동으로 따라오고 설정이 한 곳에 모인다. 그러나 폰은 미페어링·미연결 상태로도 켜지므로 "채널 미정" 구간이 생기고, 여러 데스크톱과 페어링하면 어느 채널을 따를지 결정할 근거가 없다. 무엇보다 업데이트 확인이 데스크톱 가용성에 묶이면, 정작 갱신이 절실한 상태(compat 거부로 연결이 안 되는 상태)에서 채널을 읽을 수 없다. 사용자도 로컬 설정을 택했다.
- **데스크톱 설정을 기본값으로 쓰고 폰에서 수동 오버라이드한다.** 편의와 독립성을 모두 얻는 대신, "지금 이 채널이 상속된 것인지 내가 고른 것인지"를 설명하는 표면이 추가로 필요하고 상태 조합이 늘어난다. 폰 하나가 자기 설치본의 채널을 소유하는 단순한 규칙을 택했다.
- **APK 다운로드·설치까지 붙인다.** 사용자 손이 가장 덜 간다. 그러나 `REQUEST_INSTALL_PACKAGES` 와 `PackageInstaller` 경로는 서명 검증 책임을 앱이 새로 지는 일이고, Play 배포로 전환하면 그 코드 전체가 폐기된다. ADR-0190 이 같은 이유로 미뤄둔 것을 이번 요구가 요구하지도 않았다. 릴리스 페이지로 넘기면 설치는 OS 의 패키지 설치기가 하고 서명 대조는 Android 가 한다.
- **시스템 알림(POST_NOTIFICATIONS)과 WorkManager 주기 작업.** 앱을 켜지 않아도 알 수 있다. 그러나 알림 권한 요청과 주기 작업 스케줄링이 들어오고, 업데이트 유무는 앱을 켰을 때 알면 충분한 등급의 정보다. 사용자도 앱 내 배너를 택했다.
- **데스크톱 매니페스트(`desktop-<channel>.json`)의 `version` 만 읽는다.** 새 파일을 만들지 않아도 되고, 게시 게이트가 두 job 을 함께 묶으므로 그 버전의 APK 는 존재한다. 그러나 파일 이름과 스키마가 데스크톱 번들 계약이므로 Android 가 그것을 읽는 순간 데스크톱 매니페스트의 형태를 바꿀 자유가 사라지고, 폰이 실제로 필요한 것(릴리스 페이지·APK asset 이름)은 그 안에 없어 클라이언트가 추측으로 URL 을 조립해야 한다. 계열별 파일을 택했다.
- **매니페스트 없이 버전만 어딘가에서 읽고 릴리스 URL 은 클라이언트가 조립한다.** 파일이 하나 줄지만, "릴리스가 어디 있는가"를 바이너리에 굳히게 되어 저장소 이동·릴리스 배치 변경이 앱 갱신 없이는 반영되지 않는다. 매니페스트가 URL 을 말하고 클라이언트가 그 문법을 검사하는 쪽이, 유연성과 방어선을 둘 다 남긴다.
- **앱이 GitHub API 로 최신 릴리스를 직접 조회한다.** 브랜치가 필요 없다. 그러나 인증 없는 API rate limit 이 확인 주기에 얹히고, 최신 prerelease 를 가리키는 안정된 alias 가 없어 beta 채널을 API 만으로는 정의할 수 없다. ADR-0190 이 데스크톱에서 같은 이유로 기각한 방향이다.
- **Play in-app update API.** Android 가 표준 경로를 제공한다. 그러나 이 앱은 Play 에 배포되지 않으며(사이드로드 APK), 그 전환은 서명·배포·심사 정책을 새로 들여오는 별개 결정이다.
- **배너를 Remote 표면에서도 띄운다.** 발견을 놓칠 확률이 줄어든다. 그러나 그 화면은 픽셀 하나가 입력 대상인 터미널이고, 상단 오버레이는 세션 중 가장 방해가 큰 자리다. 표시를 미루는 비용(다음 대시보드 복귀까지)이 훨씬 낮다.
- **닫기를 영구 무시로 만든다.** 한 번 닫으면 다시 묻지 않는다. 그러나 그러면 그 뒤 나온 새 버전도 묻지 못한다. 버전별 무시가 "이 버전은 지금 안 받는다"와 "앞으로 아무것도 알리지 마라"를 구분한다.

## Consequences

- 폰 사용자는 앱 안에서 새 버전을 알고 릴리스 페이지까지 한 번에 갈 수 있다. compat version 이 올라간 릴리스에서 연결이 거부되는 구간이 사라지지는 않지만, 그 구간에서 무엇을 해야 하는지가 앱 안에서 보인다. ADR-0190 이 "Android 자체 업데이트가 생기면 사라진다"고 적은 구간은 설치가 붙는 후속 결정까지 남는다.
- 설치는 여전히 손으로 한다. 다운로드·설치 실패, 사이드로드 차단, 알 수 없는 출처 허용은 모두 OS 와 사용자 몫이며 앱은 그 결과를 알지 못한다. 따라서 배너는 "받았는지"가 아니라 "새 버전이 있는지"만 말하고, 설치가 끝나면 다음 실행의 `versionName` 이 후보를 자연히 없앤다.
- 채널이 기기별로 갈라진다. PC 를 beta 로 옮긴 사용자가 폰을 stable 로 두면 폰은 beta APK 를 영구히 보지 못하고, compat 이 올라간 시점에 연결이 끊긴다. 이 조합은 정상 상태로 표시되므로, 설정 섹션이 현재 채널을 항상 보여주는 것이 이 혼동을 푸는 유일한 수단이다.
- `release-channels` 브랜치의 계약이 두 파일에서 네 파일로 늘어난다. 브랜치·파일 삭제나 변조는 이제 폰의 확인까지 오류로 만든다. 브랜치 보호와 workflow 외 쓰기 금지는 ADR-0190 이 남긴 운영 후속 작업 그대로이며 범위가 넓어졌다.
- 부트스트랩 조건이 "브랜치 존재"에서 "네 파일 존재"로 바뀌므로, 이 결정을 담은 릴리스의 부트스트랩 job 이 현재 latest stable tag 로 Android 파일을 시딩한다. 그 tag 의 APK asset 이 없으면 시딩은 실패해야 한다 — 존재하지 않는 릴리스를 가리키는 매니페스트는 404 보다 나쁘다.
- 버전 문법 계약의 사본이 셋(node·Rust·Kotlin)으로 늘었다. 세 곳이 갈라지면 폰만 후보를 놓치거나 폰만 잘못된 후보를 받으므로, 각 사본은 같은 경계값(라벨 거절, 선행 0 거절, build metadata 거절, stable 채널의 prerelease 거절)을 자기 테스트로 고정한다.
- `ACTION_VIEW` 로 나가는 URL 이 하나 늘어난다. 그 값은 매니페스트에서 오지만 문법 검사가 저장소 릴리스 경로로 좁히므로, 매니페스트 변조로 얻을 수 있는 최대치는 같은 저장소의 다른 릴리스 페이지다.
- 앱이 처음으로 정기적인 외부 네트워크 요청을 자기 주기로 만든다(기존 요청은 사용자 행동이나 세션에 딸린 것뿐이었다). 6시간 throttle 과 앱 전면 상태 조건이 그 빈도를 묶는다.
- 업데이트 섹션이 인스턴스별 "연결 설정" 다이얼로그에 얹히므로, 페어링이 없는 폰은 채널을 바꿀 표면이 없고 기본 stable 을 따른다. 앱이 네이티브 크롬(대시보드 상단 메뉴 등)을 갖게 되면 전용 화면으로 옮기는 것이 후속 작업이다.
- 문서 후속 작업: `docs/architecture/overview.md` 의 Android 앱 서술과 `docs/architecture/api-contracts.md` 의 채널 매니페스트 절차에 Android 파일과 스키마를 같은 PR 에서 반영한다.
- 자동 검증은 매니페스트 스키마 검증과 전진성·쓰기 계획(node), 버전 문법·비교·채널 계약·`releaseUrl` 문법·주기 판정·표시 계산(Kotlin 단위 테스트), 그리고 debug 미리보기로 띄운 배너·설정 섹션의 실기 확인을 포함한다. 실제 endpoint 가 후보를 성사시키는지는 이 결정을 담은 첫 릴리스에서 실측해야 한다.
