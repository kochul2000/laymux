## Context

터미널 선택 경로 링크(#363)는 검증된 경로를 좌클릭했을 때 파일이면 통합 뷰어를 열고 디렉터리면 SyncGroup CWD 를 전파한다. 두 동작 모두 laymux 내부에서 끝나므로, 사용자가 그 경로를 OS 파일 관리자에서 보거나 OS 연결 프로그램으로 열려면 경로를 복사해 탐색기 주소창에 손으로 붙여넣어야 한다. WSL 셸이 찍는 `/home/...`, `/mnt/d/...` 경로는 Windows 탐색기가 그대로 받지 못하므로 사용자가 UNC/드라이브 표기로 손수 바꿔야 해 특히 비싸다.

경로 해석 자체는 이미 해결돼 있다. `path_utils::resolve_address_path_following_symlinks` 가 `stat_path`·`list_directory`·`read_file_for_viewer` 와 같은 규칙으로 `/home/... → \\wsl.localhost\<distro>\...`, `/mnt/c/... → C:\...` 를 만들고 Windows 가 따라가지 못하는 WSL 심볼릭 링크까지 실체화한다. 없는 것은 "그 호스트 경로를 OS 에 넘기는 동작"과 "그 동작을 어떤 입력으로 트리거하고 어떤 조건에서 확인받을 것인가"라는 결정이다.

결정을 강제하는 force 는 다섯 가지다.

1. **의미의 모호성.** WSL 셸에서 뿌려진 경로를 "연다"는 말은 게스트 맥락 실행(WSL 내부 `xdg-open`/직접 실행)일 수도, 호스트 맥락 실행(Windows 연결 프로그램)일 수도 있다. 두 해석은 서로 다른 결과를 낳으므로 한쪽을 계약으로 고정해야 한다.
2. **수정자 키와 마우스 이벤트가 이미 점유돼 있다.** xterm 은 선택이 있는 상태의 shift+mousedown 을 선택 확장으로 처리하고, 마우스 리포팅이 켜진 TUI 에서는 shift 를 선택 강제 수정자로 예외 처리한다. 여기에 #352 TUI 우회가 wrapper 엘리먼트의 capture `mousedown` 에서 shift **또는** alt 좌클릭을 링크 활성화로 가로채며 Ctrl 여부를 보지 않는다. 즉 `Ctrl+Shift`·`Ctrl+Alt` 는 비어 있는 조합이 아니라 이미 두 주체가 나눠 갖고 있다. 새 동작은 이 소유권을 명시적으로 재배치해야만 성립한다.
3. **실행은 되돌릴 수 없다.** 터미널 출력에 찍힌 이름을 드래그해 클릭하는 것만으로 호스트에서 임의 프로그램이 실행될 수 있다. Windows 에서 `.js` 는 편집기가 아니라 Windows Script Host 로 실행되므로, node 프로젝트에서 소스 파일을 열려던 클릭이 스크립트 실행이 된다.
4. **권한 경계.** 파일 존재 확인·내용 읽기 권한과 "호스트에서 프로세스를 띄우는" 권한은 급이 다르다. Remote FileViewer 는 이미 "remote 파일 읽기가 새 호스트 프로세스 실행 권한으로 확장되어서는 안 된다"는 이유로 `extensionViewers` 매핑을 의도적으로 무시한다(ADR-0045). 새 동작이 그 경계를 우회해서는 안 된다.
5. **설정은 원격에서 쓰기 가능하다.** `update_settings` MCP 툴과 Automation `/settings` 는 release 표면에서도 임의 설정 patch 를 허용한다. 따라서 "설정 하나로 완전히 사라지는 안전장치"는 실질적으로 안전장치가 아니다.

범위는 데스크톱 `TerminalView` 의 검증된 path-link 선택에 대한 OS 열기·OS 파일 관리자에서 보기, 그 확인 정책, 대응 설정 키, 그리고 그에 필요한 마우스 이벤트 소유권 재배치와 발견성 보강이다. 게스트(WSL) 맥락 실행, Remote 표면 대응, File Explorer 뷰·FileViewer 오버레이의 OS 열기 확장은 비목표다.

## Decision

**path-link 의 OS 열기는 항상 호스트 데스크톱 맥락에서 수행하고, 밑줄 사각형 안의 Ctrl(열기)·Ctrl+Shift(파일 관리자에서 보기) 클릭을 path-link 가 배타적으로 소유하며, 실행으로 이어지는 경로는 기본적으로 매번 사용자 확인을 받고 직접 실행 계열은 설정과 무관하게 항상 확인한다.**

1. **호스트 맥락이 유일한 의미다.** 선택 경로가 WSL 안의 파일이어도 OS 열기는 호스트(Windows) 의 연결 프로그램으로 연다. 게스트 배포판 안에서 무언가를 실행하는 동작은 이 계약에 포함하지 않는다. 프론트엔드는 셸 문자열을 만들지 않고 원본 경로를 구조화 인자로 넘기며, 호스트 경로 산출은 ADR-0031 과 같이 Rust 가 소유한다 — `resolve_address_path_following_symlinks` 를 재사용하고 path-link 전용 변환 규칙을 새로 만들지 않는다. **밑줄을 켠 `stat_path` 호출과 OS 열기 호출은 같은 `(path, wsl_distro)` 인자 쌍을 사용한다**(현재 path-link 는 distro 를 넘기지 않아 기본 distro 폴백을 상속한다 — ADR-0031 의 distro 일치 요구보다 느슨하며, 그 차이는 아래 Consequences 에 비용으로 남긴다).

2. **수정자 계약은 Ctrl 계열로 고정하고, 그 클릭의 소유권을 path-link 가 갖는다.**
   - 수정자 없는 좌클릭은 기존 동작(파일=뷰어, 디렉터리=CWD 전파)을 그대로 유지한다.
   - `Ctrl`+좌클릭은 열기(`open`) — 파일은 호스트 연결 프로그램, 디렉터리는 호스트 파일 관리자.
   - `Ctrl+Shift`+좌클릭은 보기(`reveal`) — 대상의 부모 폴더를 열고 대상을 선택 상태로 표시한다. 부모가 없는 대상(드라이브 루트, UNC 공유 루트)은 `open` 과 동일하게 대상 자체를 연다.
   - **소유권 불변식:** `hitTest` 가 참인 밑줄 사각형 안에서 위 조합이 성립하면 path-link 가 그 `mousedown` 을 `preventDefault` + `stopImmediatePropagation` 으로 종결한다. xterm 의 선택 확장, TUI 로의 마우스 리포팅 전달, #352 우회 중 어느 것도 같은 클릭을 함께 처리하지 않는다. 마우스 리포팅 활성 여부는 이 판정에 영향을 주지 않는다. `Alt` 나 `Meta` 가 함께 눌린 조합은 소유하지 않는다.
   - **발견성:** 수정자 클릭은 스스로를 알리지 못하므로, 밑줄 위에 포인터가 있는 동안 무엇을 할 수 있는지 힌트 라벨로 노출한다. 라벨은 `pointer-events: none` 이며 기능이 꺼져 있으면 표시하지 않는다.
   - **#352 계약 정정:** `isModifierLinkClick` 은 Ctrl 이 눌린 조합을 더 이상 TUI 링크 활성화로 취급하지 않는다. #352 는 Ctrl 없는 Shift/Alt 좌클릭만 소유한다.
   - 밑줄 사각형 **밖**에서는 어떤 수정자 조합도 가로채지 않는다. 기존 선택·드래그·TUI 전달은 그대로다.

3. **기본 확인은 확장자 판별에 의존하지 않는 전량 확인이고, 사용자가 완화했을 때만 좁혀진다.** 확인 정책은 두 층이다.
   - **하드 클래스(설정과 무관, 항상 확인):** 목록은 코드 상수로 고정하고 설정으로 비활성화할 수 없다. 판정 기준은 "확장자가 실행 파일처럼 보이는가"가 아니라 **"연결 프로그램에 넘기면 그 자체가 실행되거나 시스템이 변경되는가"** 다. 따라서 직접 실행·설치 관리자·레지스트리 병합에 더해, Windows 가 Script Host 로 실행하는 `.js`/`.jse`/`.vbs`/`.wsf`, 연결 프로그램이 인터프리터인 `.py`/`.pyw`, `xdg-open` 이 실행하는 `.sh`/`.desktop`/`.appimage`/`.run` 을 포함한다.
   - **사용자 층:** 설정 `terminal.pathLinkOsOpenConfirm`(기본값 **켬**)이 켜져 있으면 파일을 연결 프로그램으로 여는 모든 `open` 을 확장자와 무관하게 확인한다. 사용자가 끄면 하드 클래스만 확인한다.
   - `reveal` 과 디렉터리 `open` 은 파일 관리자를 띄울 뿐 대상을 실행하지 않으므로 확인하지 않는다.
   - `terminal.pathLinkOsOpenEnabled`(기본값 **켬**)로 기능 전체를 끌 수 있다. 두 키 모두 데스크톱 Settings UI 의 Terminal 섹션에 노출한다. 위험 확장자 목록은 설정 키로 만들지 않는다.

4. **확인 판정은 프론트엔드가, 실행은 백엔드가 소유한다.** 어떤 액션이 확인 대상인지 결정하는 것은 설정과 하드 클래스를 읽는 프론트엔드의 순수 함수이고, 백엔드 커맨드는 확인 여부를 알지 못한 채 요청받은 동작만 수행한다. 같은 정책을 두 계층에 중복 구현하지 않는다.

5. **OS 열기 커맨드는 데스크톱 프론트엔드 전용이며, 원격은 이 경로를 트리거할 수 없다.** 새 Tauri 커맨드는 Automation API, MCP 툴, Remote 라우트 어디에도 노출하지 않는다. 원격 주체는 `update_settings` 로 `pathLinkOsOpenConfirm` 을 끌 수 있지만, 그렇게 해도 (a) 실행에는 데스크톱 사용자의 밑줄 위 Ctrl+클릭이라는 로컬 제스처가 여전히 필요하고, (b) 하드 클래스 확인은 설정으로 사라지지 않는다. 이 두 성질이 ADR-0045 의 경계를 유지하는 실질 근거다.

6. **크로스플랫폼 실행 정책.** 외부 프로세스는 `crate::process::headless_command` 로만 띄우고 셸을 경유하지 않는다 — 사용자 선택에서 유래한 경로가 셸 메타문자 해석 표면에 노출되지 않는다(대상 프로그램 자체의 인자 파싱까지 안전해진다는 뜻은 아니다). **`explorer.exe` 의 `/select,` 는 표준 인자 이스케이프로 전달하지 않는다** — explorer 는 `CommandLineToArgvW` 를 쓰지 않아 `/select,<path>` 전체가 따옴표로 묶이면 스위치를 인식하지 못하고 조용히 기본 폴더를 연다(Windows 11 실기 확인). 따옴표가 **경로만** 감싸도록 raw 커맨드라인으로 넘긴다. 단 이 형식은 경로 자체에 `"` 가 없을 때만 쓴다 — 네이티브 Windows 경로에는 들어갈 수 없지만 WSL 경로에는 들어갈 수 있고(Linux 파일명은 `/` 와 NUL 만 금지), 그런 대상은 따옴표 구간이 조기에 끝나 나머지가 explorer 의 자체 파서로 넘어간다. 해당 경우 `reveal` 은 선택 표시를 포기하고 부모 폴더 열기로 낮춘다. Windows 는 `explorer.exe` 를 두 모드 모두에 사용한다 — 연결 프로그램이 없는 확장자에서 OS 의 "앱 선택" 대화상자가 그대로 뜨는 것이 기대 동작이고, 이를 막거나 대체하지 않는다. Linux 는 `xdg-open` 을 사용하며 `reveal` 은 부모 디렉터리 열기로 낮춘다(대상 선택 표시는 보장하지 않는다). **`explorer.exe` 는 성공해도 0 이 아닌 종료 코드를 반환하므로 종료 코드를 실패 판정에 쓰지 않는다.** 커맨드는 프로세스 spawn 실패만 오류로 보고하고, 그 이후의 결과는 OS 에 위임한다.

7. **존재 검증은 기존 게이트를 재사용한다.** OS 열기는 이미 `stat_path` 로 검증돼 밑줄이 그려진 선택에만 적용된다. 별도의 존재 확인 경로를 새로 만들지 않으며, 검증과 실행 사이의 TOCTOU 는 OS 에 위임한다.

## Alternatives Considered

- **게스트(WSL) 맥락에서 실행**: `wsl.exe -d <distro> -- xdg-open <path>` 로 리눅스 기본 앱을 띄우는 방안. 사용자가 명시적으로 호스트 맥락 실행을 기대한다고 확정했고, WSLg 유무·배포판별 `xdg-open` 설치 여부에 따라 결과가 갈려 계약으로 삼기 어렵다. 게스트 실행이 필요하면 해당 pane 에 명령을 주입하는 별개 동작이 더 정직하다.
- **Shift 또는 Alt + 클릭에 매핑**: 다수 터미널이 링크 활성화에 쓰는 관례라 학습 비용이 낮다. 그러나 shift 는 xterm 선택 확장과 마우스 리포팅 중 선택 강제에 묶여 있고, shift/alt 는 #352 우회가 소유한다. path-link 는 선택이 항상 떠 있는 모델이라 이 충돌이 예외가 아니라 상시 조건이다. 기존 두 기능을 재배치하는 비용이 새 기능의 이득보다 크다.
- **Ctrl 조합도 #352 가 계속 소유하게 두고 우선순위만 조정**: 계약 정정이 없어 diff 는 작다. 그러나 같은 클릭에서 "URL 을 브라우저로 연다"와 "파일을 호스트에서 연다"가 동시에 성립할 수 있고, 어느 쪽이 이기는지는 리스너 등록 순서라는 우연에 의존한다. 소유권을 문서화된 계약으로 나누는 편이 안정적이다.
- **밑줄 위 우클릭 컨텍스트 메뉴로 노출**: 수정자 조합보다 발견성이 높고 모든 액션을 한눈에 보여준다. **채택하지 않는다** — 터미널의 우클릭은 이미 "선택 있으면 복사, 없으면 붙여넣기"가 소유하고 있어(§8.6) 그 즉시성을 메뉴로 바꾸는 비용이 크다. 발견성은 밑줄 hover 힌트 라벨로 해결하고, 이 방향은 보류가 아니라 기각이다.
- **확인 없이 위험 확장자만 차단**: 클릭 한 번으로 끝나 가볍다. 그러나 터미널에 찍힌 문자열을 드래그해 클릭하는 것만으로 실행이 일어나는 경로이고, 위험 목록은 본질적으로 불완전하다(핸들러가 등록된 임의 확장자, 확장자와 실제 동작의 불일치). 되돌릴 수 없는 동작의 기본값은 확인이어야 한다.
- **위험 확장자 목록을 설정 키로 노출**: 사용자가 자기 워크플로에 맞게 좁힐 수 있다. 그러나 목록을 비우면 사용자가 명시적으로 요구한 "직접 실행 파일 경고"가 완전히 사라지고, 그 설정은 원격 patch 로도 바뀔 수 있다. 하드 클래스를 코드 상수로 두면 이 소거 경로가 없어지고 설정 표면도 줄어든다.
- **백엔드가 확인 정책을 강제**: 프론트엔드를 우회하는 호출까지 막을 수 있다. 그러나 커맨드가 데스크톱 프론트엔드 전용이라 우회 호출자가 없고, 같은 정책이 두 계층에 중복되면 설정 변경 때 서로 어긋난다. 원격 설정 쓰기라는 실제 위험은 정책 중복이 아니라 하드 클래스와 로컬 제스처 요구로 막는다(Decision 5).
- **기존 `shell:allow-open` / `openExternal`(tauri-plugin-shell `open`) 재사용**: 이미 권한이 부여돼 있고 실패를 `Result` 로 받을 수 있어 관측성이 낫다. 그러나 프론트엔드는 호스트 경로를 알지 못한다 — WSL 게스트 경로를 그대로 넘기면 열리지 않고, 호스트 경로를 얻으려면 백엔드 왕복이 한 번 더 필요해 "경로 변환은 Rust 소유"(ADR-0031)라는 경계도 흐려진다. 게다가 `reveal` 은 이 API 로 표현할 수 없어 두 모드가 서로 다른 메커니즘·다른 실패 정책으로 갈린다. 한 커맨드·한 정책을 택한다.
- **Windows 에서 `cmd /C start` 사용**: 기존 `open_settings_file` 이 쓰는 방식이라 일관적이다. 그러나 사용자 선택에서 유래한 경로를 셸 파서에 통과시키게 되고, `start` 의 첫 인자 제목 처리 같은 함정이 붙는다. 셸을 경유하지 않는 `explorer.exe` 직접 spawn 이 같은 결과를 더 좁은 표면으로 얻는다.
- **Windows 에서 `ShellExecuteW`/`SHOpenFolderAndSelectItems` 직접 호출**: 성공·실패를 정확히 구분할 수 있고 `reveal` 도 정식 API 를 쓰며 `explorer.exe` 의 비표준 인자 파싱을 피한다. 대신 COM 초기화와 전용 스레드 관리가 따라오고, 연결 프로그램이 없을 때 `SE_ERR_NOASSOC` 를 받아 "앱 선택" 대화상자를 별도 verb 로 다시 띄워야 한다. 이번 요구에는 얻는 정확도보다 비용이 크다고 보고 미뤘다.

## Consequences

- 사용자는 WSL 경로든 Windows 경로든 같은 제스처로 호스트 탐색기·연결 프로그램에 도달한다. 경로 표기 변환을 손으로 하지 않아도 된다.
- `stat_path`, `list_directory`, `read_file_for_viewer`, OS 열기가 모두 같은 경로 해석 함수를 공유하므로 WSL 심볼릭 링크·UNC 표기 처리가 한 곳에서만 바뀐다.
- **#352 의 입력 계약이 좁아진다.** Ctrl+Shift/Ctrl+Alt 로 TUI 안의 URL 을 열던 사용자가 있었다면 그 조합은 더 이상 링크를 열지 않는다. Shift/Alt 단독은 그대로다. 이 변화는 living doc §8.6 에 반영한다.
- **밑줄 위 수정자 클릭에서 마우스 리포팅이 TUI 로 전달되지 않는다.** TUI 안에서 Ctrl+클릭을 자체 기능으로 쓰는 앱이 있다면, 검증된 경로 밑줄 위에서만 그 입력을 잃는다. 밑줄은 사용자가 드래그로 만든 선택에만 생기므로 노출 면적은 작다.
- 기본값이 "항상 확인"이므로 OS 열기를 자주 쓰는 사용자는 대화상자를 매번 본다. 설정으로 낮출 수 있음을 UI 문구에서 알린다. 확인을 끈 상태에서도 하드 클래스는 계속 확인한다.
- 원격 주체가 `pathLinkOsOpenConfirm` 을 끌 수 있다는 사실은 남는다. 실행에는 여전히 로컬 사용자의 Ctrl+클릭이 필요하고 하드 클래스 확인이 남지만, 설정 표면 전반의 원격 쓰기 정책을 다시 볼 필요가 생기면 별도 결정으로 다룬다.
- Windows 에서 성공/실패를 종료 코드로 알 수 없다(성공해도 1 을 반환한다 — 실기 확인). 잘못된 경로나 연결 프로그램 없음은 OS 대화상자로만 드러나고 앱은 조용하다. spawn 자체가 실패한 경우에만 오류를 보고한다. 또한 `explorer.exe` 의 비표준 인자 파싱에 raw 커맨드라인으로 대응했으므로, 그 형식이 바뀌면 조용히 깨질 수 있다(경로에 포함될 수 있는 쉼표도 같은 파서에 노출된다). 이 부채가 실제로 문제가 되면 `ShellExecuteW`/`SHOpenFolderAndSelectItems` 로 옮기는 것을 재검토한다.
- path-link 는 distro 를 명시하지 않아 기본 WSL distro 폴백을 상속한다. 여러 distro 를 동시에 쓰는 환경에서는 다른 distro 의 동명 경로가 열릴 수 있다 — ADR-0031 이 extension viewer 에서 거부하기로 한 상황과 의도적으로 다르다. 이는 OS 열기가 새로 만든 위험이 아니라 기존 `stat_path` 검증이 이미 가진 성질이며, 고치려면 path-link 검증 경로 전체에 distro 를 흘려야 하므로 별도 작업으로 둔다.
- Linux 의 `reveal` 은 대상 강조 없이 부모 디렉터리만 연다. 파일 관리자별 정식 강조가 필요해지면 D-Bus `org.freedesktop.FileManager1` 도입을 별도 결정으로 다룬다.
- Remote 표면에는 이 동작이 없다. desktop 과 Remote 의 path-link 동작 차이가 하나 더 늘어나며(디렉터리 CWD 이동에 이어 OS 열기), 그 비대칭은 권한 경계에 따른 의도된 결과다.
- 설정 키 두 개가 늘어난다. ADR-0004·0032 계약에 따라 `settings.json` 스키마, `describe_settings` 메타데이터, `validate_settings` 커버리지를 함께 갱신하고, Settings UI Terminal 섹션과 i18n 문구를 추가한다.
- 후속 문서 작업: `docs/architecture/data-flow.md` §8.6(클릭 분기·#352 수정자 범위)과 `docs/architecture/api-contracts.md` 설정 스키마 절을 같은 PR 에서 갱신한다.
- 테스트는 수정자→액션 매핑과 확인 필요 판정을 순수 함수 단위 테스트로 덮고, 백엔드는 모드별 인자 구성과 경로 해석 재사용을 검증한다. Windows 탐색기 실동작(UNC 경로에서의 `reveal` 포함)은 실기 확인으로 다룬다.
