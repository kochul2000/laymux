# 0255. 지연된 Codex 조회도 실행 범위가 유효하면 관측을 복구한다

- Status: Accepted
- Date: 2026-09-17
- Source: 사용자 Windows Codex 진행 중 완료 표시 제보, Codex 조회 지연 회귀 테스트, architecture/data-flow.md §9, architecture/api-contracts.md §15.6
- Amends: [ADR-0248](0248-codex-turn-lifecycle-activity.md)의 단일 진행 중 조회, [ADR-0250](0250-terminal-task-state-and-notification-transitions.md)의 지연 관측 복구

## Context

Codex의 턴 조회는 여러 pane의 native·WSL 프로세스 및 파일 관측을 한 요청으로 수행한다. 프론트는 6초가 지나면 마지막 유효 작업을 지연 상태로 보존하지만, 같은 요청에서 이후 반환된 정상 결과도 무조건 버린다. 모든 조회가 6초보다 느리면 재시도도 성공할 수 없어, 시작 전의 완료가 계속 남거나 작업이 끝나도 진행 표시가 유지된다. 실제 조회가 돌아왔는데도 스스로 복구를 금지하는 문제다.

일반 Windows 연속 요청과 30초 도구 대기는 dev에서 정상 진행을 관측했다. 느린 조회는 별도로 지연을 주입해 검증한다. 사용자 release의 실제 조회 지연은 측정하지 않았으므로 이 경로가 제보의 유일한 원인이라고 단정하지 않는다.

범위는 기존 조회의 지연 처리다. 타이틀·출력·제출 문장을 작업 시작이나 완료로 합성하지 않으며, 세션 식별·rollout 파서·IPC 필드·호출 간격을 바꾸지 않는다.

## Decision

**6초는 진행 중인 조회의 지연을 표시하는 기준이며, 동일 실행 범위에서 돌아온 정상 응답을 폐기하는 기한으로 사용하지 않는다.**

- 지연 타이머는 마지막 유효 작업과 알림 이력을 보존한 `stale` 관측을 전달한다. 요청은 계속 한 개만 진행한다.
- 응답이 돌아오면 지연 시간과 관계없이 구독 생존, pane 등록 epoch, 앱 종류·task epoch, 제출 입력 시점, 현재 PTY generation을 기존 규칙대로 검사한다. 범위가 바뀌면 계속 폐기한다.
- 유효 응답은 원래 source·turnId를 통해 공통 작업 계산기에 전달한다. 같은 작업의 종료 전이만 한 번 알리고, 최초 복원·반복 종료·실패·다른 세션의 이력을 재생하지 않는다.
- 실제 오류나 `unknown` 응답은 계속 지연/미확인으로 남긴다. 응답이 없는 요청과 정상 응답이 늦은 요청을 구분하며, 요청을 겹쳐 보내지 않는다.

## Alternatives Considered

- 6초 제한을 더 큰 상수로 변경: 임계보다 느린 환경에서 같은 고정 현상이 재발한다.
- 만료 때마다 다른 요청을 병렬로 시작: 느린 native·WSL I/O를 더 쌓고 응답 순서 역전을 만든다.
- 지연 중 출력이나 타이틀로 이전 완료를 진행으로 바꾸기: Astra의 장식 출력과 사용자 타이틀 설정에 다시 의존한다.
- 지연 타이머 제거: 응답이 없는 동안 이전 성공이 확인된 현재 상태로 남는다. 지연 관측은 보존해야 한다.

## Consequences

느린 정상 조회도 완료→진행과 진행→종료를 복구한다. 다만 상태 반영 지연 자체는 줄이지 않으며, 영원히 반환하지 않는 요청의 I/O 중단은 이 변경의 범위가 아니다. 단일 요청에는 상태 전이 전체 이력이 없으므로 poll 사이에 끝난 짧은 턴을 놓칠 수 있는 한계도 유지한다.

회귀 테스트는 두 번 이상 느린 조회, 반환 전 지연 표시, 복구 후 완료 알림 한 번, 지연 중 새 입력·generation·앱 변경·구독 해제를 포함한다. dev에서는 실제 Codex 도구 실행 중 지연을 주입해 API 반환과 화면 상태를 대조하고, 최종 코드의 일반 속도 실기도 별도로 확인한다. 지연 주입 코드는 출하하지 않는다.

실측 결과와 재현 조건은 [Codex 상태 재현 기록](../codex-task-status-repro-2026-09-17.md)에 둔다.
