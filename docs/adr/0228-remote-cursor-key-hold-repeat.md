# 0228. Remote 커서 키는 누르는 동안 자동 반복하고, 나머지 소프트 키는 1회 입력을 유지한다

## Context

Remote 의 소프트 키는 전부 `click` 1회 = 시퀀스 1회다. 커서 키(`↑↓←→`, Home/End)와 4방향 flick 패드(`dpad`)도 예외가 아니어서, 긴 명령줄에서 커서를 20칸 옮기려면 탭을 20번 해야 하고 flick 패드는 손가락을 방향에 올려 둬도 `pointerup` 에서 단 한 번만 보낸다. 하드웨어 키보드와 모바일 OS 키보드 모두 길게 누르면 반복하므로, 사용자는 이 화면에서만 반복이 없다는 사실을 결함으로 인식한다.

제약은 두 가지다.

1. **모든 키를 반복시키면 안 된다.** 같은 툴바에 `^C`·`Enter`·`^U`·사용자 등록 키가 함께 있다. 손가락이 잠깐 머무는 것만으로 인터럽트가 연발되거나 명령이 두 번 제출되는 편이, 반복이 없는 것보다 훨씬 나쁘다.
2. **flick 패드의 두 인스턴스는 성격이 다르다.** `dpad` 는 바이트를 쓰는 커서 키지만, `navPad` 의 방향은 pane 전환·알림 점프라는 컨트롤러 액션(ADR-0039)이다. 후자를 60ms 간격으로 반복하면 빨라지는 게 아니라 통제 불능이 된다.

범위는 Remote 소프트 키 툴바의 입력 활성화 제스처다. 시퀀스 정의, 키 배치·등록(ADR-0213), 포커스 계약(ADR-0028), 데스크톱 xterm 의 물리 키 반복(브라우저/OS 소관)은 비목표다.

## Decision

**커서 시퀀스를 쓰는 키(`KEY_DEFS` 의 `cursor` 속성)와 `dpad` flick 패드만 누르고 있는 동안 자동 반복한다. 초기 지연 400ms, 반복 간격 60ms. 나머지 소프트 키·사용자 키·`navPad` 는 1회 입력을 유지한다.**

### 1. 반복 대상은 `cursor` 속성이 정한다

반복 여부는 키 목록에 손으로 적은 예외가 아니라 `cursor` 속성에서 파생된다. 커서 이동은 한 번의 탭으로 목적을 끝내지 못하는 경우가 있는 유일한 부류이고, 반복해도 파괴적일 수 없는 부류이기도 하다. Home/End 는 한 탭으로 끝나지만 반복이 멱등이라 예외를 파 두지 않는다 — 예외 목록을 만드는 순간 새 커서 키마다 판단이 필요해진다. 새 커서 키가 생기면 자동으로 반복하고, 새 제어 키가 생겨도 반복하지 않는다.

### 2. 1회 입력 경로는 `click` 하나로 유지하고, 반복은 그 위에 얹는다

반복은 기존 활성화 경로를 대체하지 않는다. 탭·클릭·키보드·보조기술은 전과 똑같이 `click` 에서 정확히 1회 전송하고, 누르고 있는 동안 지연 뒤 시작되는 스트림만 추가된다. 따라서 짧은 탭의 결과는 변경 전과 바이트 단위로 동일하고, 누르는 총량은 "반복 n회 + 릴리스 1회"로 예측 가능하다.

대안이던 "`pointerdown` 에서 첫 전송 + 뒤따르는 합성 `click` 삼키기"는 합성 `click` 을 판별할 수단이 없어 폐기했다. `detail` 은 브라우저·입력 합성 경로마다 달라(Chromium 의 CDP 터치 합성은 `detail === 0` 으로 온다) 키보드 활성화와 구분되지 않으며, 대신 플래그를 두면 릴리스가 키 밖에서 일어나 `click` 이 오지 않을 때 다음 키보드 활성화가 삼켜진다. 포커스 계약(ADR-0028)도 그대로다 — `mousedown`·`pointerdown` 양쪽의 기본 동작은 계속 막는다.

`setPointerCapture` 로 손가락이 키 밖으로 미끄러져도 짝이 맞는 `pointerup` 을 받고, `pointercancel`(시스템 인터럽트)은 릴리스와 같게 스트림을 멈춘다. 롱프레스가 플랫폼 컨텍스트 메뉴를 띄우지 않도록 `contextmenu` 기본 동작도 막는다.

반복하는 키는 flick 패드와 같은 이유로 제스처를 통째로 소유한다(`touch-action: none`). 키 행은 가로로 스크롤되므로 `touch-action: manipulation` 인 채로는 엄지가 몇 px 흐르는 것만으로 브라우저가 터치를 팬으로 가져가 `pointercancel` 을 쏘고, 반복이 조용히 끊긴다(Chromium 모바일 에뮬레이션에서 20px 드리프트로 재현). 대가는 반복 키 위에서 시작한 드래그로는 키 행을 스크롤할 수 없다는 것이고, 이는 기존 flick 패드가 이미 지고 있는 비용이다.

### 3. flick 패드는 "머무는 방향"이 반복 단위다

`dpad` 는 방향이 확정된 채(임계 18px 초과) 400ms 유지되면 그 방향을 반복한다. 방향이 바뀌면 지연을 처음부터 다시 잰다 — 천천히 그은 flick 이 지나온 방향까지 흘리면 안 되기 때문이다. 릴리스는 커서 키와 같게 기존 1회를 그대로 보낸다. 반복하지 않는 flick 패드(`navPad`)의 동작은 이전과 완전히 동일하다.

### 4. 전송 경로는 그대로다

반복 1회는 기존 `enqueueInput` → `/remote/v1/terminals/{id}/write` 1회다. 새 endpoint·파라미터가 없고, 60ms 간격은 입력 병합 창(12ms)보다 충분히 커서 각 반복이 개별 write 로 도착한다.

## Alternatives Considered

- **모든 소프트 키 반복** — 구현은 더 짧지만 `^C`·`Enter`·사용자 키가 손가락 체류만으로 연발된다. 반복이 없는 불편보다 비용이 크다.
- **반복 지연·간격을 설정으로 노출** — 설정 키 2개가 늘고 Desktop·Remote 양쪽 스키마에 파급된다. 값을 바꿔야 할 근거가 아직 없으므로 상수로 둔다. 요구가 생기면 그때 `KEY_DEFS` 의 키별 플래그나 설정으로 확장한다.
- **서버 측 반복(`write` 에 repeat 수 전달)** — 릴리스 시점은 클라이언트만 알기 때문에, 왕복을 줄이려면 손을 뗄 때까지 전송을 미뤄야 한다. 화면 반응이 릴리스까지 지연되므로 반복의 목적 자체를 잃는다.
- **롱프레스로 반복 모드 진입 후 손을 떼도 계속** — 멈추는 제스처를 따로 만들어야 하고, 오작동 시 커서가 계속 달린다.

## Consequences

- 반복 중에는 초당 약 16개의 write 가 나간다. 링크가 느리면 큐가 밀려 손을 뗀 뒤에도 잔여 이동이 도착할 수 있다 — 이는 기존 입력 큐의 성질이며, 반복이 새 실패 모드를 만들지는 않는다.
- 활성화 경로가 그대로라 탭 1회의 동작과 기존 테스트는 바이트 단위로 불변이다. 대신 400ms 이내의 짧은 누름은 여전히 릴리스에서야 입력이 나가며(변경 전과 동일), 반복의 첫 원소는 눌린 순간이 아니라 400ms 지점이다.
- `installDirectionalFlick` 이 `repeatable` 인자를 받는다. 호출자는 두 곳(arrow pad, nav pad)뿐이고 기본값은 비반복이다.
- 재검토 조건: Backspace/Delete 반복 요구가 나오거나, 반복 속도를 사용자가 조절하고 싶어 할 때. 전자는 `cursor` 파생 규칙을 키별 `repeat` 플래그로 바꾸는 변경이 되므로 새 ADR 로 다룬다.
