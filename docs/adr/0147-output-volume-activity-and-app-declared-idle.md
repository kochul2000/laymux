# 0147. 출력 볼륨을 앱 협조 없는 활성 신호로 인정하고, 앱이 선언한 유휴는 추론된 활성을 이긴다

- Status: Proposed
- Date: 2026-08-12
- Source: architecture/data-flow.md §outputActive 감지("ANY PTY 출력 기반 판단 금지" 규칙 정정), [ADR-0005](0005-display-state-raw-separation-compute.md), 사용자 보고("Claude 가 working 인데 ⏳ 대신 ✓ 로 뜬다", "shell 에 출력이 계속되고 있으면 working 이어야 한다")

## Context

pane 이 "일하는 중"(⏳)인지의 판정은 `outputActive` 와 activity handler 의 타이틀 해석 두 갈래로만 이루어져 왔다. 실제 신호원은 세 개였고, 셋 다 **앱이 특정 방식으로 협조해야만** 성립한다.

1. **DEC 2026h 버스트** — window(기본 2초) 안에 프레임 마커 threshold(기본 6)회. 프레임 cadence 가 초당 여러 번이라는 전제.
2. **OSC 133 C/D** — 셸 명령의 running 상태. lx 통합 셸에서만.
3. **타이틀 스피너 문자** — Claude/Codex 가 OSC 0/2 타이틀 앞에 붙이는 특정 문자 집합의 하드코딩 목록.

이 구조는 사용자 보고 시점에 세 갈래가 **동시에** 무너졌다. Claude Code 2.1.228 은 타이틀 스피너를 `◐`/`◑`(U+25D0/25D1) 로 바꿨고(이전은 별표류·Braille), 애니메이션 주기가 960ms 다. 하드코딩 목록에 없는 문자이므로 3번은 죽고, 프레임이 2초에 두 장뿐이므로 1번도 threshold 에 못 미치고, TUI 이므로 2번은 애초에 대상이 아니다. 결과는 오래 도는 툴 호출 내내 pane 이 유휴(✓)로 표시되는 것이었다.

문자 목록만 갱신하면 이번 증상은 사라진다. 그러나 **판정의 신뢰성이 외부 앱의 렌더링 세부에 종속된다**는 구조는 남는다. 같은 결함은 Claude 가 문자나 주기를 다시 바꿀 때, `CLAUDE_CODE_DISABLE_TERMINAL_TITLE` 이나 타이틀 rename 으로 스피너 접두어가 사라질 때, DEC 2026 을 쓰지 않는 임의의 TUI 에서 그대로 재발한다. 반대로 pane 이 초당 수십 KB 를 토해내는 동안 "유휴" 라고 말하는 표시는 어떤 앱 사정으로도 정당화되지 않는다.

living doc 의 기존 규칙은 이 방향을 명시적으로 금지하고 있었다: _"ANY PTY 출력 기반 판단 금지 — `output_buffer.last_output_at` 같은 '뭐라도 출력되면 active' 방식은 셸 프롬프트 리드로에도 false positive 를 유발한다."_ 이 규칙이 막으려 한 것은 옳다. 다만 규칙이 실제로 배제해야 하는 대상은 **출력의 유무**이고, 규칙은 그것을 **출력의 양** 전체로 확대해 금지했다.

범위는 활성(⏳) 판정의 신호원과 우선순위다. 비목표: activity 종류(어느 앱이 사는가) 판정 — 그 권위는 프로세스 트리이며 [ADR-0009](0009-process-tree-interactive-app-liveness.md)/[ADR-0134](0134-wsl-guest-interactive-app-liveness.md) 가 소유한다. `outputActive` 의 소유권이 프론트엔드 Zustand 단일 소스라는 [ADR-0005](0005-display-state-raw-separation-compute.md) 의 결정도 바꾸지 않는다.

## Decision

**출력 볼륨을 앱 협조가 필요 없는 네 번째 활성 신호로 인정한다. 그리고 앱이 명시적으로 선언한 유휴는 볼륨에서 추론한 활성을 이긴다.**

1. **볼륨 신호는 유무가 아니라 양의 임계다.** PTY 콜백이 슬라이딩 윈도 안의 누적 출력 바이트를 재고, 임계를 넘을 때만 기존 `terminal-output-activity` 이벤트를 발행한다. `last_output_at` 류의 "출력이 있었나" 판정은 계속 금지한다 — 정정하는 것은 금지의 경계이지 금지 자체가 아니다. living doc 의 해당 규칙을 이 경계로 다시 쓴다.

2. **임계는 사람의 타이핑이 도달할 수 없는 높이로 잡는다.** 볼륨 경로가 배제해야 하는 false positive 는 프롬프트 리드로·포커스 리드로·키 입력 에코이며, 셋 다 상한이 있는 양이다(리드로 한 프레임, 키당 한 프레임). 기본값은 window 2초 / 64KiB 이고 `terminal.outputActivityBurst` 에서 조정한다. 이 계산은 pane 하나가 지속적으로 ~32KiB/s 를 내는 상태만 활성으로 인정한다.

3. **볼륨 신호는 다른 세 신호를 대체하지 않는다. 네 신호는 서로의 사각을 덮는다.** 조용히 오래 기다리는 작업(네트워크 대기, `sleep`)은 볼륨이 못 보고 타이틀/OSC 133 이 본다. 타이틀 접두어가 없거나 목록에 없는 앱은 타이틀이 못 보고 볼륨이 본다. 어느 하나가 단독 권위가 아니며, 이후 어떤 신호가 깨져도 나머지가 남는 것이 이 결정의 목적이다.

4. **앱이 선언한 유휴가 추론된 활성보다 강하다.** Claude 의 `✳`(U+2733) 유휴 타이틀처럼 앱이 "나는 입력을 기다린다" 고 명시한 신호는, 볼륨·DEC 2026 처럼 출력에서 **추론한** 활성보다 높은 우선순위를 갖는다. 이 역전이 없으면 응답 flush 직후의 잔여 청크가 유휴 pane 을 ⏳ 로 되돌리고, 유휴 상태로도 프레임을 다시 그리는 임의의 TUI 는 영구히 활성으로 굳는다. 이미 최상위인 input-pending(권한 모달) 우선순위는 그대로다.

5. **타이틀 문자 목록은 신뢰의 근거가 아니라 편의다.** 목록은 계속 유지·갱신하되(이번에 `◐`/`◑` 추가), 그 목록의 정확성에 판정의 정확성이 걸리지 않는 상태를 불변식으로 삼는다. Rust `claude_activity.rs` 와 프론트 `claude-activity-handler.ts` 두 곳의 목록이 같아야 한다는 기존 동기화 의무도 유지한다.

## Alternatives Considered

- **타이틀 문자 목록만 갱신(핫픽스).** 증상은 즉시 사라지고 비용이 가장 낮다. 기각 이유는 재발 구조를 그대로 남긴다는 것 하나다. 외부 앱의 렌더링 세부가 바뀔 때마다 같은 버그가 사용자 눈에 먼저 발견되는 상태를 설계로 인정하는 셈이다. 이번 증상 수정은 이 ADR 안에 포함하되 결정의 본체로 삼지 않는다.

- **DEC 2026 threshold 를 낮춘다(예: 2회).** 960ms cadence 를 통과시킬 수 있다. 기각: threshold 는 원래 리드로·키 에코를 거르기 위한 값이고, 낮추면 그 false positive 가 정확히 되돌아온다. 앱의 프레임 주기라는 관측 불가능한 값에 맞춘 튜닝이므로 다음 주기 변경에 또 깨진다.

- **프레임 주기를 학습해 threshold 를 적응시킨다.** cadence 종속을 자동화로 가린다. 기각: 상태와 실패 모드가 늘어나는데 얻는 것은 여전히 "앱이 프레임을 그린다" 는 전제 안의 정확도다. 전제 자체를 벗어나는 볼륨 신호가 더 적은 복잡도로 더 넓은 범위를 덮는다.

- **볼륨 계산에서 사용자 입력 직후의 출력을 제외한다(입력 상관 억제).** 타이핑 에코를 원리적으로 배제할 수 있어 임계를 낮게 잡을 수 있다. 기각: PTY 콜백이 마지막 입력 시각을 알아야 하므로 상태와 락이 늘고, 임계를 높게 두는 것만으로 같은 false positive 가 이미 배제된다. 임계를 낮춰야 할 근거가 생기면 그때 재검토한다.

- **프로세스 트리(CPU 사용률)로 활성을 판정한다.** 앱 협조가 전혀 필요 없다. 기각: WSL pane 에서는 호스트 스냅샷이 게스트 프로세스를 못 보고(ADR-0134), 폴링 주기가 표시 반응성에 직접 들어오며, "CPU 를 쓰지 않고 기다리는 작업" 을 유휴로 오판한다. 활성 판정의 주 신호로 쓸 수 없다.

## Consequences

- 활성 판정이 외부 앱의 스피너 문자·프레임 주기·타이틀 정책에 대한 종속을 잃는다. 앱이 어떻게 바뀌어도 "많이 출력하는 pane 은 working" 이 성립한다.
- 임계 이하로 조용히 도는 작업은 여전히 타이틀·OSC 133 에 의존한다. 볼륨 신호는 사각을 줄이지만 없애지 않는다 — 이 점을 living doc 에 신호별 커버리지 표로 남긴다.
- 기본 임계(2초/64KiB)는 계산으로 정한 값이고 실측으로 검증한 값이 아니다. 재검토 조건: 타이핑·프롬프트 리드로에서 ⏳ 가 관측되면 임계를 올리거나 입력 상관 억제를 도입한다. 반대로 명백히 바쁜 pane 이 유휴로 남으면 임계를 내린다. 두 방향 모두 설정 키로 즉시 완화 가능하다.
- 4번의 우선순위 역전은 `outputActive` 가 참인데 표시가 ✓ 인 상태를 만든다. `isTerminalWorking`(sleep prevention, ADR-0114)이 같은 계산 함수를 읽으므로 이 역전은 절전 억제에도 그대로 적용된다 — 유휴를 선언한 Claude pane 은 화면을 깨워두지 않는다. 이는 의도된 결과다.
- living doc 의 "ANY PTY 출력 기반 판단 금지" 규칙이 이 ADR 로 경계를 좁혀 다시 쓰인다. 이후 이 규칙을 인용하는 리뷰는 정정된 형태를 근거로 삼아야 한다.
- 볼륨 검출은 PTY 콜백의 뜨거운 경로에 들어가므로 청크당 상수 시간(누적 덧셈 + Instant 비교)을 넘지 않아야 한다. 바이트 내용을 다시 훑는 구현은 허용하지 않는다.
