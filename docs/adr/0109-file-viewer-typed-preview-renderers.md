# 0109. 파일 뷰어 preview 는 타입별 렌더러로 갈라지고 신뢰 경계가 렌더 방식을 정한다

- Status: Proposed
- Date: 2026-08-01
- Source: 사용자 요구(개발자가 자주 여는 파일 타입 확대), architecture/api-contracts.md §13.2 FileViewer preview 정책(#404/#446), [ADR-0031](0031-extension-viewer-profile-path-conversion.md), [ADR-0042](0042-remote-file-viewer-secret-capability.md)

## Context

내장 파일 뷰어는 `read_file_for_viewer` 가 돌려주는 `text | image | binary` 세 갈래와, 경로 확장자가 정하는 `html | markdown` 두 갈래의 preview 만 안다. 그 밖의 모든 파일은 흑백 `<pre>` 한 덩어리이거나 `Binary file (N KB)` 한 줄이다.

이 뷰어를 쓰는 사람은 개발자이고, 개발자가 하루에 여는 파일은 대부분 그 "그 밖" 에 있다 — 소스 코드, `package.json`, unified diff, CSV, 에이전트가 남긴 JSONL 트랜스크립트와 ANSI 로그, zip. 뷰어가 이들을 읽을 수 있게 만들면 외부 에디터로 나갈 일이 줄어든다.

문제는 "렌더러를 몇 개 더 추가한다" 로 끝나지 않는다는 것이다. 지금 preview 경로는 단 하나뿐이고, 그 하나가 **신뢰할 수 없는 파일 내용을 HTML 로 해석하는** 경로다. HTML/Markdown 은 그래야만 의미가 있으므로 sanitizer + 제한 CSP + `sandbox` iframe 이라는 값비싼 방어를 세워 두었다. 새로 붙일 렌더러 대부분(JSON 트리, CSV 표, diff, 로그)은 파일 내용을 **문서가 아니라 데이터로** 다루므로 그 방어가 필요 없다. 필요 없는 방어를 관성으로 재사용하면 두 가지를 잃는다. sanitizer 를 통과시키려고 태그·속성 allowlist 를 계속 넓히게 되고(방어가 실제로 약해진다), iframe CSP 가 `script-src 'none'` 이라 접기·정렬 같은 상호작용을 아예 만들 수 없다.

동시에 정반대 실수도 가능하다. 데이터 렌더러를 만들면서 편의상 HTML 문자열을 조립해 `innerHTML` 로 넣으면, sanitizer 없는 새 XSS 경로를 조용히 여는 셈이 된다. 문법 하이라이터 라이브러리 대부분이 정확히 이 모양(하이라이트된 HTML 문자열 반환)이라 유혹이 실재한다.

세 번째 force 는 Remote 다. Remote/Cloud 뷰어(`remote_server/viewer_page.js`)는 React 가 아니라 Rust 에 임베드된 순수 JS 자산이고, 데스크톱과 렌더러를 공유할 수 없다. 8 MiB 터널 응답 상한도 있다. 그리고 `read_file_for_viewer` 는 데스크톱과 Remote 가 **같이 쓰는** 커맨드라, 응답 스키마를 넓히면 Remote 가 먼저 깨진다.

범위: 데스크톱 내장 뷰어의 표시 능력. 비목표 — 편집, 파일 내부 검색, 아카이브 항목 추출, Remote 뷰어의 렌더러 확장.

## Decision

**preview 렌더러는 신뢰 경계로 두 계열로 나뉘고, 계열이 렌더 방식을 강제한다. 파일 내용을 문서로 해석해야 하는 것만 sanitizer+CSP+iframe 을 타고, 데이터로 다루는 것은 React DOM 으로만 렌더하며 어떤 경우에도 HTML 문자열을 만들지 않는다.**

### 계열과 불변식

- **document 계열** (`html`, `markdown`) — 파일이 곧 문서다. 기존 sanitizer → `buildPreviewDocument` → 제한 CSP → `sandbox="allow-same-origin"` `srcdoc` iframe 경로를 그대로 탄다. 이 경로는 이번 결정으로 넓어지지 않는다. 새 태그·속성·URL 스킴을 allowlist 에 추가하는 것은 이 ADR 의 범위가 아니며 별도 결정을 요구한다.
- **structured 계열** (`json`, `jsonl`, `diff`, `csv`, `log`, `code`) — 파일은 파싱 대상 데이터다. **순수 함수가 텍스트를 값(토큰·행·셀·노드)으로 파싱하고, React 가 그 값을 렌더한다.** 이 계열의 코드 경로에는 `dangerouslySetInnerHTML`, `innerHTML`, `insertAdjacentHTML`, `DOMParser`, HTML 문자열 조립이 존재하지 않는다. 이것이 불변식이며, sanitizer 가 없는 이유이자 없어도 되는 이유다.

파싱과 렌더는 분리한다. 파서는 DOM 을 모르는 순수 모듈(`ui/src/lib/preview/`)이고, 컴포넌트(`ui/src/components/ui/preview/`)는 파서 출력만 그린다. 파서가 순수해야 엣지 케이스(따옴표 안의 개행, 깨진 JSONL 한 행, 행 간 SGR 상태)를 DOM 없이 단위 테스트로 못박을 수 있다.

문법 하이라이팅은 이 불변식에 맞는 API 를 쓴다 — 하이라이터는 **토큰 배열을 반환하는 모드로만** 호출하고, 하이라이트된 HTML 을 반환하는 API 는 쓰지 않는다. 이는 편의가 아니라 계열 불변식의 직접적 귀결이다.

### 분류의 소유권

파일이 어느 렌더러로 가는지는 **두 축**이 정하고, 축마다 소유자가 다르다.

- **내용 종류(`kind`)는 Rust 가 소유한다.** 바이트를 읽어야만 알 수 있거나(UTF-8 여부), 바이트를 구조로 풀어야 하는 것(아카이브 중앙 디렉터리)은 백엔드 책임이다. `FileViewerContent` 에 `pdf` 와 `archive` 를 추가한다.
- **preview 종류는 프론트엔드가 경로 확장자로 소유한다.** `kind: "text"` 안에서 JSON 인지 CSV 인지는 바이트가 아니라 이름이 정한다. 내용 스니핑으로 추측하지 않는다 — 추측은 틀렸을 때 조용히 잘못된 표를 그린다.

두 축의 우선순위는 기존과 같다. `settings.fileExplorer.extensionViewers` 의 외부 터미널 뷰어 매핑이 있으면 내장 렌더러보다 **먼저** 이긴다. 사용자가 `.json → jq` 를 걸어 뒀다면 내장 JSON 트리가 그것을 빼앗지 않는다.

### 확장자 테이블은 렌더러보다 앞선 게이트다

Rust 의 텍스트 확장자 목록은 표시 힌트가 아니라 **분류 게이트**다. 목록에 없는 확장자는 크기 상한을 넘는 순간 `binary` 가 되어 프론트엔드 preview 경로에 도달조차 못 한다. 따라서 새 렌더러를 붙일 때 대응 확장자를 이 목록에 넣는 것은 선택이 아니라 필수다.

### 상한은 항상 보이게 한다

렌더러는 전부 표시량 상한을 갖는다(행 수·레코드 수·바이트). **상한에 걸려 잘렸으면 화면에 그 사실과 전체 개수를 표시한다.** 조용한 절단은 "전부 보고 있다" 는 거짓 신호를 주므로 금지한다. 하이라이팅처럼 상한 초과 시 기능을 끄는 경우(plain 소스로 폴백)도 마찬가지로 이유를 표시한다.

### 실패는 폴백이지 에러가 아니다

파싱 실패는 뷰어 실패가 아니다. 깨진 JSON, 손상된 아카이브, 로드에 실패한 하이라이터는 모두 **원문 표시로 폴백**하고 사유를 함께 보여준다. 파일을 열려던 사람에게 "열 수 없다" 대신 "이만큼은 보여주고, 나머지는 이래서 안 된다" 를 준다. 손상된 바이너리를 파싱하다 panic 하는 것은 허용하지 않는다.

### Remote 계약은 확장하지 않는다

Remote 는 이번 결정의 대상이 아니다. `render` 응답에서 **`previewDocument` 를 만들 수 있는 것은 document 계열뿐**이며, structured 계열은 Remote 에서 지금과 똑같이 원문 텍스트로 내려간다. 프론트엔드의 데스크톱 분류기와 Remote 분류기를 **서로 다른 함수로 분리**해 structured 종류가 sanitizer 경로로 새는 것을 타입 수준에서 막는다.

새 `kind`(`pdf`/`archive`)는 공유 커맨드가 돌려주므로 Remote 에도 도달한다. Remote 뷰어는 이들을 **렌더하지 않고 플레이스홀더로 표시**한다 — 알 수 없는 응답으로 터지는 것만 막고, 렌더러는 복제하지 않는다.

### PDF 는 호스트 엔진에 위임한다

PDF 는 자체 렌더링하지 않고 WebView 엔진의 내장 뷰어에 맡긴다. 전달 방식은 blob URL 을 `<iframe>` 에 싣는 것이다 — `<object>` 는 fallback 슬롯이 공짜로 딸려 와 더 나아 보였지만 **WebView2 가 `<object>` 로는 PDF 를 렌더하지 않는다는 것을 실측으로 확인**했고(`type` 유무 무관), 같은 blob 을 iframe 에 실으면 Chromium 뷰어가 그대로 뜬다. iframe 에는 fallback 슬롯이 없으므로 외부 열기는 상시 노출 버튼으로 제공한다.

엔진에 PDF 뷰어가 없는 플랫폼(Linux WebKitGTK)에서는 프레임이 비고 그 버튼이 유일한 출구다. **플랫폼 간 렌더 동등성은 이 결정의 목표가 아니다** — 동등성을 보장하려면 PDF 엔진을 번들해야 하고, 그 비용은 이 기능의 가치를 넘는다. 렌더 실패를 프로그래밍으로 감지할 방법이 없다는 점도 이 결정의 일부다. iframe 의 `load` 는 성공·실패 양쪽에서 발화하므로 "이 플랫폼은 못 그린다" 는 안내를 조건부로 띄울 수 없고, 그래서 버튼을 조건 없이 항상 보여준다.

## Alternatives Considered

**모든 렌더러를 기존 iframe 경로로 통일** — 신뢰 경계가 하나뿐이라 단순해 보였다. 기각 이유는 두 가지다. 첫째, CSP 가 `script-src 'none'` 이라 접기·정렬·행 점프가 원천적으로 불가능해 JSON 트리와 CSV 표가 성립하지 않는다. 둘째, 데이터 렌더러를 HTML 로 표현하려면 sanitizer allowlist 를 계속 넓혀야 하는데, 그 allowlist 는 신뢰할 수 없는 HTML 문서를 막으려고 좁게 유지해 온 것이다. 편의를 위해 방어를 약화시키는 교환이라 받지 않았다.

**모든 렌더러를 React 로 통일(iframe 폐기)** — 반대 방향의 단순화. Markdown 을 React 로 렌더하려면 `marked` 출력 HTML 을 React 트리로 다시 변환하는 계층이 필요하고, `github-markdown-css` 를 앱 전역 스타일에 섞어야 한다. 이미 검증된 sanitizer/CSP 경계(api-contracts.md §13.2)를 버리고 새 경계를 만드는 비용이 명백히 크다.

**하이라이트된 HTML 문자열을 sanitize 해서 사용** — 하이라이터 라이브러리의 일반적 사용법이고 구현이 가장 짧다. 기각. structured 계열 전체를 "HTML 안 만든다" 로 못박는 편이 지킬 수 있는 규칙이다. "sanitize 했으니 괜찮다" 는 예외를 한 번 허용하면 다음 렌더러도 같은 논리로 예외가 되고, 결국 계열 구분이 사라진다.

**preview 종류를 내용 스니핑으로 판별** — 확장자 없는 파일이나 잘못 붙은 확장자를 구제할 수 있었다. 기각. 오탐이 조용하다 — JSON 처럼 생긴 로그를 트리로 그리면 사용자는 뷰어가 틀렸다는 것을 알 방법이 없다. 확장자는 예측 가능하고, 사용자가 이름을 바꿔 교정할 수 있다.

**Remote 뷰어에도 렌더러 이식** — 기능 동등성은 매력적이다. 기각. `viewer_page.js` 는 프레임워크 없는 임베드 자산이라 6종 렌더러를 두 번째 언어로 다시 쓰고 두 벌을 계속 동기화해야 한다. Remote 의 현재 폴백(원문 텍스트)은 이미 유용하며, 동등성은 Remote 클라이언트를 React 로 옮기는 별도 결정 이후에 다시 볼 문제다.

**PDF 엔진 번들** — 모든 플랫폼에서 동일하게 보인다. 기각. 번들 크기가 이번에 추가하는 나머지 전부를 합친 것보다 크고, entry chunk 는 이미 크기 경고 한계 근처다. 데스크톱 앱이므로 외부 열기라는 정상적인 대안이 항상 존재한다.

**아카이브 항목 내용까지 열람** — 자연스러운 다음 요구. 이번 범위에서 제외. 목록은 압축을 풀지 않고 메타데이터만 읽지만, 항목 열람은 압축 해제 + zip bomb 방어 + 중첩 아카이브 정책 + 가상 경로 모델을 요구한다. 별도 결정으로 다룬다.

## Consequences

내장 뷰어가 개발자 일상 파일 대부분을 읽을 수 있게 되고, 렌더러를 하나 더 붙일 때 "어느 계열인가" 만 답하면 나머지 규칙이 따라온다. 파서가 순수 모듈이라 엣지 케이스는 DOM 없이 테스트로 고정된다.

비용도 분명하다. 렌더러가 늘어난 만큼 표면이 늘고, 각자의 상한과 폴백을 갖는다. `FileViewerContent` 는 Rust enum 과 TS union 을 수기로 맞추는 곳이라 variant 를 늘릴수록 어긋날 여지가 커진다 — 지금은 코드젠도, parity 테스트도 없다. 아카이브 파싱은 신뢰할 수 없는 바이너리를 다루는 새 코드 경로이므로 손상 입력에 대한 폴백 테스트가 방어의 전부다. 하이라이터는 지연 로드되는 첫 무거운 의존성이라 청크 그룹을 명시적으로 관리해야 하고(의존성 재귀가 꺼져 있다), 방치하면 entry chunk 로 샌다.

데스크톱과 Remote 의 표시 능력 격차는 이 결정으로 **의도적으로 벌어진다**. 그 격차는 부채로 남으며, Remote 클라이언트가 React 로 통합되면 재검토한다. `pdf`/`archive` 를 Remote 에서도 실제로 보고 싶다는 요구가 나오면, 렌더러 복제가 아니라 클라이언트 통합 쪽을 먼저 검토하는 것이 이 결정의 입장이다.

재검토 조건: structured 계열 렌더러가 HTML 문자열을 만들어야만 하는 사례가 나타나면 계열 구분 자체를 다시 본다. 아카이브 항목 열람, Remote 렌더러 동등성, PDF 플랫폼 동등성은 각각 별도 ADR 을 요구한다.
