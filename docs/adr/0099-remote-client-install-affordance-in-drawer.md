# 0099. Remote 클라이언트의 설치 권유는 내비게이션 드로어의 버튼 하나로만 한다

- Status: Proposed
- Date: 2026-07-31
- Source: 사용자 요구("터미널 페이지에서 메뉴 오픈 했을 때 버튼으로 추가하자, pwa 상태면 숨기는 버튼으로"), [ADR-0091](0091-remote-client-standalone-web-app-manifest.md)

## Context

ADR-0091 이 `/remote/` 에 web app manifest 와 launcher 아이콘을 붙여 설치를 **가능하게** 했다. 그러나 설치 경로는 브라우저 메뉴 안쪽(Chrome "앱 설치", iOS "공유 → 홈 화면에 추가")에 숨어 있어 사용자가 그 기능의 존재를 모른다. 주소 표시줄을 없애는 이득이 가장 큰 폰 사용자가 정작 발견하지 못한다.

작용하는 force:

- **터미널 표시 행 수가 이 surface 의 희소 자원이다.** ADR-0091 이 해결한 문제가 브라우저 chrome 이 세로 공간을 먹는 것이었다. 상시 배너로 권유하면 없애려던 문제를 우리 손으로 다시 만든다.
- **설치 가능 여부는 브라우저가 판정한다.** Chromium 은 설치 기준을 만족했을 때만 `beforeinstallprompt` 를 발생시킨다. iOS/iPadOS Safari 는 이 이벤트가 없고 설치는 공유 시트를 통한 수동 조작뿐이다.
- **Direct Remote Mode 는 평문 HTTP** 라 secure context 가 아니고 설치가 성립하지 않는다(ADR-0091 Context). 그 경로에서 권유는 실행 불가능한 안내다.
- **이미 설치된 창에서는 권유가 무의미하다.** 홈 화면 실행은 `display-mode: standalone`(iOS 구 경로는 `navigator.standalone`)으로 식별된다.
- **service worker 는 두지 않는다**(ADR-0091 Decision). 설치 권유가 SW 를 요구해서는 안 된다.

범위: `/remote/` 클라이언트가 설치를 **권유하는 UI 의 위치·표시 조건·플랫폼별 동작**. 비목표: manifest·아이콘 계약 변경(ADR-0091 그대로), 오프라인 동작, 설치 완료율 측정/텔레메트리, 데스크톱 앱(`ui/`) UI, 공개 오리진(대시보드) 의 설치 권유 — 그 origin 은 laymux-server 소유다.

## Decision

**설치 권유는 내비게이션 드로어 안의 버튼 하나이며, 설치가 지금 실제로 가능할 때만 나타난다.**

- 위치는 드로어(`#navigationPanel`) 최하단의 자체 섹션이다. 헤더·터미널 영역·상시 배너를 쓰지 않는다 — 터미널 행을 먹지 않고, 사용자가 메뉴를 연 시점에만 보이므로 dismiss 상태를 저장할 필요도 없다.
- 버튼의 기본 상태는 `hidden` 이다. 다음 중 하나라도 해당하면 계속 숨긴다: 이미 standalone 실행 중(`matchMedia("(display-mode: standalone)")` 또는 `navigator.standalone`), `window.isSecureContext` 가 거짓(HTTP direct mode), 그리고 아래 두 경로 어느 것도 성립하지 않는 브라우저.
- **Chromium 경로:** `beforeinstallprompt` 를 받아 기본 동작을 막고 이벤트를 보관한 뒤 버튼을 드러낸다. 이벤트 수신 자체가 "브라우저가 설치 가능하다고 판정했다"는 증거이므로 별도 판정을 하지 않는다. 클릭은 보관한 이벤트의 `prompt()` 를 호출하고, 결과와 무관하게 이벤트를 버리고 버튼을 숨긴다 — 같은 이벤트는 재사용할 수 없다.
- **iOS/iPadOS 경로:** `beforeinstallprompt` 가 없으므로 이벤트를 기다리지 않고, iOS Safari 로 식별되면 버튼을 바로 드러낸다. 클릭은 존재하지 않는 API 를 부르는 대신 "공유 → 홈 화면에 추가" 한 줄 안내를 토글한다.
- `appinstalled` 이벤트를 받으면 섹션을 숨긴다. 이 신호는 Chromium 경로에만 온다 — iOS 는 공유 시트 설치에서 이 이벤트를 발생시키지 않으므로, 그 브라우저 탭의 섹션은 다음 방문 때 standalone 판정으로만 사라진다. 탭은 여전히 설치 전 문맥이므로 이를 결함으로 보지 않는다.
- 설치 프롬프트를 자동으로 띄우지 않는다. 사용자 제스처 없는 `prompt()` 는 Chromium 이 거부하고, 열지도 않은 메뉴 대신 화면을 가로채는 동작은 이 결정이 피하려는 것이다.

## Alternatives Considered

- **상시 배너 / 첫 방문 자동 안내.** 발견율은 가장 높지만 터미널 행을 먹고, 없애려던 세로 공간 문제를 되살린다. dismiss 상태 저장·동기화 부채도 생긴다.
- **헤더에 버튼 추가.** 드로어보다 눈에 띄지만 헤더는 status·입력 모드·PC 버튼이 이미 경쟁하는 좁은 영역이고, 설치는 한 번 하면 끝나는 행위여서 상시 자리를 줄 값어치가 없다.
- **모든 브라우저에서 버튼을 항상 표시.** 코드가 단순해지지만 설치가 불가능한 HTTP direct mode 나 미지원 브라우저에서 눌러도 아무 일이 없는 버튼이 남는다 — 실행 불가능한 UI 는 없는 것보다 나쁘다.
- **`beforeinstallprompt` 없이 플랫폼 스니핑으로만 판정.** 이벤트를 안 기다리면 버튼을 더 일찍 보여줄 수 있으나, 브라우저의 설치 기준 판정을 우리가 흉내내야 하고 manifest·아이콘 문제로 설치가 막힌 상태를 감지할 수 없다. iOS 는 대안이 없어 스니핑을 쓰지만 Chromium 은 이벤트를 정본으로 둔다.
- **설치 유도 문구를 대시보드에 두기.** 대시보드는 공개 오리진(laymux-server 소유)이고 그 origin 의 설치는 별 앱이다(ADR-0091 §비목표). 이 리포로 해결되지 않는다.

## Consequences

- 폰 사용자가 메뉴를 열면 설치 경로를 발견한다. 이미 설치했거나 설치가 불가능한 경우에는 UI 가 늘지 않는다.
- **`beforeinstallprompt` 는 비표준 Chromium 전용이다.** Chromium 이 제거하면 그 경로의 버튼이 조용히 안 뜨게 된다 — 기능 회귀는 아니지만(브라우저 메뉴 경로는 남는다) 재검토 대상이다.
- **iOS 경로는 UA 스니핑에 의존한다.** iPadOS 가 데스크톱 UA 를 보내는 구성에서는 버튼이 안 뜬다. 안내 문구 한 줄이 목적이라 실패 비용은 낮다.
- 실제 설치·프롬프트 표시는 자동 테스트로 검증할 수 없다(ADR-0091 과 동일한 한계). 자동 테스트는 마크업·표시 조건·이벤트 배선의 계약까지만 담보하고, 프롬프트 실물은 실기(Android Chrome, iOS Safari) 확인 항목이다.
- 재검토 조건: `beforeinstallprompt` 의 표준화 또는 제거, iOS 가 프로그램적 설치 경로를 제공하는 경우, 발견율이 낮다는 실사용 근거가 나오는 경우(그때 비용을 알고 배너를 재검토한다).
