# 0105. 위젯 배치는 설정의 슬롯 배열이 소유하고 status line 은 슬롯 영역 하나일 뿐이다

- Status: Proposed
- Date: 2026-08-01
- Source: 사용자 요구(상단 바·하단 status line 에 사용량 위젯 배치); `docs/architecture/api-contracts.md` §10 Settings·§15 UI 코드 설계 원칙; [ADR-0004](0004-settings-vs-ui-state-separation.md), [ADR-0005](0005-display-state-raw-separation-compute.md), [ADR-0032](0032-llm-settings-introspection-and-safe-mutation.md), [ADR-0102](0102-claude-usage-probe-headless-pty.md), [ADR-0104](0104-codex-usage-app-server-probe.md)
- Extends: [ADR-0103](0103-usage-view-visible-rows.md) — `usage.*.visibleRows` 의 적용 범위를 UsageView 에서 사용량을 그리는 모든 표면으로 넓힌다. 행 선택의 SoT 가 전역 설정이라는 결론 자체는 유지한다.

## Context

Claude·Codex 사용량은 pane 을 하나 차지하는 `UsageView` 로만 볼 수 있다. 사용량은 상시 곁눈질하는 값이라 pane 하나를 계속 내주는 비용이 크고, 터미널 활동 수·미읽음 알림·현재 CWD 같은 다른 상시 지표도 같은 문제를 갖는다.

상단 바(`GridEditToolbar`)에는 창 드래그용으로만 쓰이는 가로 공백이 이미 있고, 하단에는 아무 표면도 없다. 두 자리 중 어디에 무엇을 놓을지는 사용자의 화면 폭·작업 습관에 따라 갈리므로 앱이 고정할 수 없다.

결정이 필요한 지점은 네 가지다. (1) 상시 지표를 담는 표면을 몇 개 두고 그 배치의 SoT 를 어디에 둘 것인가. (2) 그 표면이 기존 dock·workspace 격자와 어떤 계층 관계를 갖는가. (3) 폭이 모자랄 때 무엇을 버릴지 누가 정하는가. (4) 사용량 위젯이 기존 사용량 설정의 소유권([ADR-0103](0103-usage-view-visible-rows.md))과 어떤 관계인가.

제약과 force:

- 상단 바의 가로 공백은 창 드래그 영역이다. 위젯이 이를 잠식하면 창을 옮길 수 없다.
- 상단 바는 한 줄 높이(`--bar-h`)이고 좌우 고정 폭(로고·레이아웃 컨트롤·창 버튼)을 뺀 나머지만 쓸 수 있다. 창을 좁히면 폭이 먼저 고갈된다.
- 사용량 probe 는 수요 기반이고 표시는 최대 조회 간격만큼 낡을 수 있다([ADR-0102](0102-claude-usage-probe-headless-pty.md)). 상시 표시되는 표면은 probe 수요를 영구화하므로 조회 간격 정책을 새로 만들 유혹이 생기고, 한 줄짜리 표면에는 실패·대기를 적을 자리가 없어 실패를 삼킬 유혹도 생긴다.
- `settings.json` 은 사용자가 의도적으로 편집·공유하는 구성만 담고([ADR-0004](0004-settings-vs-ui-state-separation.md)), 쓰기는 허용값 위반을 조용히 보정하지 않고 거부한다([ADR-0032](0032-llm-settings-introspection-and-safe-mutation.md)).

범위는 위젯이라는 표시 단위, 그것을 담는 슬롯 영역, 배치 설정 계약, 초기 위젯 5종이다. 비목표: 사용자 정의 위젯 플러그인, 원격 웹 클라이언트로의 위젯 노출, pane 별 위젯 배치, 위젯 전용 데이터 수집기 신설.

## Decision

**위젯 배치의 단일 진실원은 `settings.widgets` 의 슬롯별 순서 배열이며, status line 은 켤 수 있는 슬롯 영역 하나일 뿐 고유 기능을 갖지 않는다.**

### 배치 계약

- 슬롯은 네 개다 — `widgets.topBar.left`, `widgets.topBar.right`, `widgets.statusLine.left`, `widgets.statusLine.right`. 각 슬롯은 `WidgetInstance` 의 순서 배열이고, 배열 순서가 화면 순서다. 좌·우 붙임은 어느 슬롯에 넣었는지로만 표현한다. 네 슬롯의 기본값은 모두 빈 배열이다 — 첫 실행에 사전 배치되는 위젯은 없다.
- `WidgetInstance` 는 `{ id, type, options }` 다.
- 상단 바 슬롯 영역은 항상 존재한다. 비어 있으면 폭 0 이다. `widgets.statusLine.enabled`(기본 `false`)는 **하단 영역의 존재만** 결정하며 상단 바 위젯에 관여하지 않는다. 하단이 꺼져 있어도 `statusLine.left/right` 배치는 보존되고 Settings 에서 계속 보인다 — 끄기는 삭제가 아니다.
- `widgets.overflow` 는 폭 부족 시의 정책이며 현재 허용값은 `"collapse"` 하나, 기본값도 `"collapse"` 다. 다른 정책(예: 완전 숨김)을 여는 것은 새 결정으로 다룬다.

### 검증과 실패 정책

`type` 은 프론트 위젯 레지스트리가 정의하는 이름이며 `settings.json` 에 나타나는 **외부 계약**이다. 등록된 이름의 정본 목록은 Rust 상수에 두어 backend 가 검증할 수 있게 한다.

- **쓰기 경로는 [ADR-0032](0032-llm-settings-introspection-and-safe-mutation.md) 를 그대로 따른다.** MCP/Automation 이 미등록 `type` 이나 중복 `id` 를 새로 만들면 `errors` 로 거부한다. 값을 다른 값으로 조용히 보정하지 않는다. 이미 디스크에 있던 같은 위반은 `existingIssues` 로 보고하며 무관한 patch 를 막지 않는다.
- **디스크 로드 복구는 위젯 인스턴스를 제거하지 않는다.** 프론트 스토어가 다음 저장 때 디스크에 그대로 쓰이므로, 로드 시점에 버린 인스턴스는 사용자가 다른 설정을 저장하는 순간 영구 삭제된다. 따라서 미등록 `type` 은 값을 보존하고 렌더만 건너뛴다. `type` 조차 없는 항목은 배치를 담고 있지 않으므로 위젯이 아니다.
- `id` 는 `widgets` **전역에서 유일**하다. 생성 주체는 Settings UI 이고 손편집도 허용한다. 슬롯 간 이동에도 `id` 는 유지된다. 비어 있거나 중복된 `id` 는 배치가 아니라 장부이므로, 로드 시 **위치에서 파생한 결정적 id 로 복구**하고 인스턴스는 그대로 둔다 — 삭제하면 위 규칙과 모순된다.
- `widgets` 의 apply mode 는 `live` 다. 저장 즉시 화면에 반영된다.

### 계층과 표면 소유

- status line 은 dock 격자 **바깥**, 창 하단에 전체 폭으로 놓인다. 따라서 bottom dock 보다 아래이며 dock 의 분할·포커스·리사이즈 계약을 상속하지 않는다. dock 은 view 컨테이너이고 status line 은 위젯 슬롯 영역이다 — 둘은 별개 표면이다.
- 상단 바에서 위젯은 창 드래그 영역을 잠식하지 않는다. 레지스트리는 위젯마다 상호작용 여부를 선언하고, 비대화형 위젯은 드래그 영역 속성을 유지한 채 렌더된다. 대화형 위젯은 이를 갖지 않는다.

### 폭 부족 시의 우선순위

1. **슬롯 사이 순수 드래그 영역의 최소 폭이 위젯 표시보다 우선한다.** 위젯을 다 접어야 최소 폭이 확보된다면 접는다.
2. 남은 폭은 좌·우 슬롯이 각자의 요구 폭에 비례해 나눠 갖고, 각 슬롯은 자기 예산 안에서 독립적으로 접는다. **슬롯이 요구하는 폭은 배치와 설정에서만 나오며 현재 그려진 내용에서 나오지 않는다** — 그리는 것에 맞춰 크기를 정하면 접힘이 상자를 줄이고 줄어든 상자가 더 접는 되먹임이 생겨 접힘이 되돌아오지 못한다.
3. **접히는 순서의 유일한 소유자는 사용자의 배열이다.** 각 슬롯은 화면 가장자리에서 **먼 쪽부터** 접는다 — `left` 슬롯은 배열 뒤쪽부터, `right` 슬롯은 배열 앞쪽부터. 앱이 소유하는 우선순위 값은 두지 않는다. 사용자가 가장자리에 붙여 놓은 것이 마지막까지 남는다.
4. **위젯은 원자적 단위다.** 폭이 모자라도 위젯 내부를 부분 표시하지 않는다. 사용량 위젯이 `visibleRows` 개수만큼의 막대를 담지 못하면 행을 골라 버리는 대신 위젯 전체를 접는다 — 행 선택은 위젯의 소유가 아니기 때문이다.
5. 접힌 위젯은 오버플로 팝오버로 들어가며, 접힘이 일어났다는 표시는 항상 화면에 남는다. 의미를 잃는 말줄임표보다 명시적 접힘을 택한다.

### 데이터 소유

- **위젯은 데이터의 SoT 를 새로 만들지 않는다.** 기존 store 와 probe 구독 경로를 그대로 재사용하고, 표시는 원시 상태에서 도출한다([ADR-0005](0005-display-state-raw-separation-compute.md)).
- 사용량 위젯이 **어떤 한도 행을 보이는지는 위젯이 소유하지 않는다.** 전역 `usage.claude.visibleRows` / `usage.codex.visibleRows` 를 그대로 따른다. 이 결정은 [ADR-0103](0103-usage-view-visible-rows.md) 의 적용 범위를 UsageView 에서 사용량을 그리는 모든 표면으로 넓히되, 행 선택의 SoT 가 전역 설정이라는 결론은 유지한다.
- 위젯 `options` 가 소유하는 것은 **표현 방식과 인스턴스 대상**뿐이다. 값 도메인도 `settings.json` 에 드러나는 외부 계약이므로 위젯마다 허용값을 못박는다 — 사용량 위젯의 `display` 는 `"bar" | "number" | "both"`(기본 `"both"`), `claudeUsage.configDir` 는 `usage.claude.configDirs` 와 기본 config dir 중 하나, `terminalActivity.scope` 는 `"workspace" | "all"`(기본 `"workspace"`).
- 사용량 색은 위젯이 따로 갖지 않고 공통 `usage.colors` 를 쓴다. 표시 규칙은 한 곳에 둔다.
- **위젯은 실패를 삼키지 않는다.** 한 줄 표면에도 실패·미기동·최초 대기를 축약된 형태로 구분해 보이며, 이 상태를 마지막 성공값으로 대체하지 않는다([ADR-0102](0102-claude-usage-probe-headless-pty.md) 의 "실패는 표시되고 삼켜지지 않는다" 불변식이 위젯에도 그대로 적용된다). 상세 사유는 툴팁 등 축약 표면 밖에서 확인할 수 있어야 한다.

### probe 수요 정책

위젯은 `UsageView` 와 **동일한 구독 경로로 수요를 등록**하고 조회 간격은 `usage.*.refreshSeconds` 를 공유한다. 위젯 전용 저빈도 티어를 두지 않는다. 위젯만 켜져 있어도 probe 는 살아 있어야 하므로 수요 등록 자체는 반드시 하되, 같은 데이터가 화면마다 다른 시각을 보이는 상태는 만들지 않는다.

두 provider 의 수집 방식이 다르므로 "동일한 구독 경로"의 구현도 다르다. Claude 는 backend probe 가 수요를 세고 스냅샷을 방송하므로 구독만 하면 된다([ADR-0102](0102-claude-usage-probe-headless-pty.md)). Codex 는 호출마다 app-server 를 새로 띄우는 단발 읽기이므로([ADR-0104](0104-codex-usage-app-server-probe.md)) **프론트에 계정별 단일 폴러를 두고 모든 표면이 그것을 공유한다** — 표면마다 폴링하면 프로세스가 표면 수만큼 뜨고 위상이 갈려 같은 계정이 화면마다 다른 시각을 보이게 된다.

**접힌 위젯도 수요를 유지한다.** 폭 부족으로 접힌 위젯은 언마운트하지 않고 위치만 바꾼다. 언마운트하면 마지막 구독자가 사라져 probe 가 회수되므로, 창 폭을 접힘 임계 근처에서 오가는 것만으로 headless `claude` 가 반복 기동·종료된다.

### 조작 표면

배치·표시 조작은 Settings 의 위젯 섹션 한 곳만 소유한다. 상단 바에 배치 조작용 팝오버 버튼을 두지 않는다.

### 초기 위젯

`claudeUsage`(`configDir`, `display`), `codexUsage`(`display`), `terminalActivity`(`scope`), `notifications`, `cwd`. 새 위젯 추가는 레지스트리 항목 하나를 늘리는 일이며 슬롯·설정 계약을 바꾸지 않는다.

## Alternatives Considered

- **커스터마이즈 없는 고정 status line.** 구현은 가장 싸지만 지표를 하나 추가할 때마다 어떤 자리를 뺏을지 매번 협상해야 하고, 좁은 창에서 무엇을 버릴지 사용자가 정할 수 없다.
- **상단 바만 쓰고 하단 표면을 만들지 않음.** 표면 하나로 끝나 단순하지만 상단 바는 좌우 고정 요소와 드래그 영역 때문에 실사용 폭이 좁다. 사용량 위젯 두 개를 넓게 놓으면 드래그 영역이 남지 않는다.
- **status line 을 다섯 번째 dock 으로 구현.** 배치 코드를 재사용할 수 있지만 dock 은 view 컨테이너로서 분할·포커스·리사이즈·persistState 계약을 갖는다. 위젯 한 줄에 그 계약 전부를 상속시키면 의미 없는 상태 조합(위젯 슬롯 분할, 포커스 링)이 생긴다.
- **위젯 인스턴스가 표시 행(`rows`)을 소유.** 슬롯별 폭 예산에 맞춰 세밀하게 고를 수 있지만 같은 provider 의 표시 선택 SoT 가 둘로 갈린다. [ADR-0103](0103-usage-view-visible-rows.md) 이 pane 별 override 를 기각한 이유가 그대로 적용된다.
- **레지스트리가 접힘 우선순위를 소유.** 앱이 "덜 중요한" 위젯을 알고 있다는 가정인데, 무엇이 중요한지는 사용자가 배치로 이미 말했다. 두 소유자를 두면 사용자가 맨 앞에 놓은 위젯이 먼저 사라지는 상태가 정상인지 결함인지 판정할 근거가 없어진다.
- **폭이 모자랄 때 사용량 위젯의 행을 부분 표시.** 화면을 더 채울 수 있지만 위젯이 행 선택을 사실상 소유하게 되어 전역 `visibleRows` 와 경쟁한다.
- **상단 바 팝오버로 배치 조작.** 접근은 빠르지만 조작 SoT 가 둘이 되고, 이미 경합 중인 상단 바 폭을 조작 UI 가 더 먹는다.
- **위젯 전용 저빈도 probe 티어.** 상시 표시의 비용을 줄이지만 조회 간격 SoT 가 이중화되어 같은 계정의 위젯과 `UsageView` 가 서로 다른 시각의 숫자를 보이게 된다.
- **위젯 배치를 localStorage 인스턴스 오버라이드에 저장.** UI 상태로 보면 자연스럽지만 배치는 사용자가 의도적으로 구성하고 기기 간 공유하고 싶은 값이므로 [ADR-0004](0004-settings-vs-ui-state-separation.md) 의 경계상 `settings.json` 이 맞다.
- **미등록 `type` 을 로드 시 제거.** 설정이 항상 유효해지지만 앱을 잠깐 되돌리거나 브랜치를 오가는 것만으로 사용자의 배치가 영구 소실된다.

## Consequences

- 새 지표 추가 비용이 레지스트리 항목 하나로 떨어진다. 슬롯·설정·오버플로 정책은 재협상 대상이 아니다.
- `settings.json` 에 `widgets` 섹션이 늘고 `type` 이름이 외부 계약이 된다. 이름을 바꾸면 사용자의 배치가 렌더되지 않으므로 개명은 새 결정으로 다룬다. 등록 목록이 Rust 상수와 프론트 레지스트리 두 곳에 나타나므로 둘의 일치를 테스트로 고정해야 한다.
- 상단 바의 창 드래그 영역이 사용자 배치에 따라 줄어든다. 최소 폭 보장과 비대화형 위젯의 드래그 속성 유지가 회귀 지점이므로 테스트로 고정한다.
- 오버플로 팝오버라는 UI 표면이 새로 생긴다. 접힌 위젯이 사용자에게 보이지 않는 상태가 되지 않도록 접힘 표시가 항상 남아야 한다.
- `statusLine.enabled` 를 켜면 workspace 세로 픽셀이 그만큼 줄어든다. 기본값은 꺼짐이며 사용자가 명시적으로 켠다.
- 사용량 위젯을 배치하면 해당 provider 의 probe 수요가 상시 1 이상이 된다. Claude 는 headless PTY 가 상주하고 Codex 는 간격마다 app-server 를 띄운다. 비용이 문제가 되면 저빈도 티어가 아니라 `refreshSeconds` 상향으로 대응한다.
- 미등록 `type` 은 쓰기 경로에서는 거부되고 로드 경로에서는 보존된다. 두 경로의 처리가 다르므로 어느 쪽인지 헷갈리지 않도록 검증 메시지와 Settings 표시가 이유를 밝혀야 한다.
- 후속 문서 작업: `api-contracts.md` §10 에 `widgets` 스키마와 `describe_settings` 메타데이터를 추가하고, `visibleRows` 를 "모든 UsageView 가 공유"로 서술한 문장을 위젯을 포함하도록 정정한다. `overview.md` §3 레이아웃 구조에 status line 이 dock 격자 밖 최하단이라는 계층을 반영한다.
- 재검토 조건: 원격 웹 클라이언트에도 위젯이 필요해지면 슬롯 이름을 데스크톱 표면 이름에서 일반적인 영역 이름으로 확장해야 한다. 사용자 정의 위젯을 허용하게 되면 `type` 네임스페이스와 `options` 스키마 검증을 다시 정한다.
