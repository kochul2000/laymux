# 0281. 릴리스 버전은 변경의 호환성과 기능 추가 여부로 결정한다

- Status: Accepted
- Date: 2026-09-29
- Source: 사용자 요구(기능이 들어가면 minor 증가), [ADR-0190](0190-update-release-channels.md), [architecture/api-contracts.md §업데이트 채널 설정](../architecture/api-contracts.md#업데이트-채널-설정)
- 관계: ADR-0190의 버전 문법·채널 계약에 버전 증가 기준을 추가한다.

## Context

기존 발행 절차는 버전 문자열, 앱과 태그의 일치, 채널의 전진성을 검사하지만 변경 종류별 증가 기준은 정하지 않았다. 기능 추가도 patch만 올릴 수 있어 사용자가 버전으로 변경 규모를 구분하기 어렵다. 선택형 에이전트 훅은 새로운 사용자 기능이며, 기본값이 꺼져 있다는 이유로 버그 수정과 같은 증가를 적용하면 안 된다.

이번 결정은 릴리스 번호 선택과 리뷰 절차를 정한다. 기존 태그 수정, 변경 내용의 자동 분류, 채널·업데이터 프로토콜 변경은 범위 밖이다.

## Decision

**직전 정식 릴리스 이후 포함된 변경 중 가장 높은 수준에 따라 호환성 파괴는 major, 호환되는 기능 추가는 minor, 기능 추가 없는 수정은 patch를 올린다.**

- major는 기존 사용자 동작이나 공개 API·CLI·설정·복원 데이터 계약을 호환되지 않게 바꾸는 경우다. minor와 patch를 0으로 초기화한다.
- minor는 새로운 사용자 기능, 선택 옵션, 지원 환경 또는 호환되는 공개 계약의 확장이다. 기본 비활성 기능도 포함하며 patch를 0으로 초기화한다.
- patch는 기능 추가 없이 기존 동작을 바로잡는 버그 수정, 보안·안정성·성능 개선이다. 내부 리팩터·문서·테스트만 바꾸면 독립 릴리스를 요구하지 않는다.
- 분류 단위는 마지막 정식 이후 실제 릴리스에 포함될 변경 전체다. PR마다 버전을 올리거나, 마지막 커밋의 종류만 보고 patch를 선택하지 않는다.
- 각 PR은 변경 수준과 이유를 남기고, 발행 전 누적 변경을 다시 판정한다. 자동 검사는 기존 문법·버전 일치·채널 전진성을 검증하며 의미적 분류는 작성자와 리뷰어가 책임진다.
- beta는 목표 정식 버전을 먼저 결정한 뒤 기존 `x.y.z-beta.N` 규칙을 따른다. 같은 목표의 beta 승격은 접미사를 제거하며 minor를 다시 올리지 않는다.
- 앱의 버전 원본·태그·서명·플랫폼별 발행 범위·Android versionCode·Remote 호환성 버전 계약은 유지한다. 이미 공개한 버전과 태그는 소급 변경하지 않는다.

## Alternatives Considered

- 모든 릴리스에서 patch만 증가: 운영은 단순하지만 사용자가 기능 추가와 수정을 구분하지 못한다.
- 커밋 접두사만으로 자동 결정: 여러 PR의 누적 영향과 선택형 기능, 공개 계약의 호환성을 접두사만으로 신뢰성 있게 판단할 수 없다.
- PR마다 minor 증가: 하나의 릴리스에 포함되는 기능 수에 따라 불필요하게 번호가 뛰고 병렬 작업에서 충돌한다.

## Consequences

기능 도입과 수정 릴리스가 버전으로 구분된다. 작성자와 리뷰어에게 변경 수준을 판정하는 책임이 추가된다. `1.0.26` 다음 선택형 훅 기능 릴리스는 중간에 다른 릴리스가 없다면 `1.1.0`이다. 내부 설정의 마이그레이션을 만들지 않는 개발 규칙이 사용자 계약의 호환성 파괴를 patch로 분류할 근거가 되지는 않는다. 운영 절차와 사례는 [릴리스 정책](../release-policy.md)에 유지한다.
