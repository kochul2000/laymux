# 0116. settings.json 타입 오류는 경로 단위로 드롭해 부분 복구한다

- Status: Proposed
- Date: 2026-08-02
- Source: issue #701, PR #699 리뷰 P2, [ADR-0101](0101-active-workspace-weighted-parser-admission.md) Alternatives, [api-contracts.md §10](../architecture/api-contracts.md)

## Context

`settings.json` 의 값 **하나**에 타입 오류가 있으면 사용자 설정 전체가 사라진다. `serde_json::from_str::<Settings>` 가 첫 타입 불일치에서 실패하고, 로더는 그 실패를 파일 전체의 실패로 간주해 `Settings::default()` 로 기동한다. 프로필·워크스페이스·키바인딩·Remote 설정이 모두 기본값이 된다.

`#[serde(default)]` 는 **누락**만 채우므로 타입 오류에는 관여하지 않는다. 필드별 `sanitized()` 와 프론트엔드 sanitizer 는 역직렬화가 성공한 뒤에야 돌기 때문에 이 경로에서는 한 번도 실행되지 않는다. 구조 복구를 담당하는 `validate_and_repair` 도 도달하지 못한다. 즉 현재 파이프라인에는 **"값 하나만 버리고 나머지는 살린다"** 는 단계가 아예 없다.

ADR-0101 이 `terminal.parserAdmission` 을 Settings UI 없이 파일 직접 편집만으로 조정하는 튜닝 knob 으로 추가하면서 이 비용이 커졌다. 손으로 편집하는 필드가 늘면 오타 확률이 늘고, 오타 하나의 대가가 파일 전체다. ADR-0101 은 그 필드만 관용 파싱하는 안을 "계약이 필드마다 갈린다"는 이유로 기각했고, 문제를 전역 로딩 정책으로 넘겼다. 이 ADR 이 그 정책이다.

작용하는 force:

- **손실 최소화** — 살릴 수 있는 값은 살려야 한다. 오타 하나로 워크스페이스 레이아웃을 잃게 하면 안 된다.
- **계약 단일성** — "이 필드는 관용, 저 필드는 엄격" 이 되면 필드를 추가할 때마다 계약이 늘어난다.
- **기본값 SoT** — 각 필드의 기본값은 이미 `#[serde(default)]`/`Default` 구현에 한 곳씩 있다. 복구 경로가 두 번째 기본값 테이블을 만들면 안 된다.
- **조용한 손실 금지** — 부분 복구는 "사용자가 쓴 값이 말없이 기본값으로 바뀌는" 위험을 새로 만든다. 사용자가 알기 전에 원본 파일이 덮여서는 안 된다.

비목표: JSON **구문** 오류(닫히지 않은 괄호 등)의 부분 복구, 값 보정(`"2"` → `2` 같은 타입 강제 변환), 설정 스키마 마이그레이션.

## Decision

**타입 오류가 난 JSON 경로만 값 트리에서 제거하고 다시 역직렬화한다. 제거된 필드는 자신의 `#[serde(default)]` 로 채워지고, 제거 사실은 경로별 경고로 보고되며, 사용자가 복구 모달을 확인하기 전에는 `settings.json` 에 아무것도 쓰지 않는다.**

### 로딩 계약

로더는 다음 순서를 따른다.

1. 파일을 `serde_json::Value` 로 읽는다. 여기서 실패하면 **JSON 구문 오류**다 — 살릴 구조가 없으므로 `ParseError` (현행 동작 유지).
2. `Value` 에서 `Settings` 로 역직렬화한다. 성공하면 기존 마이그레이션 → `validate_and_repair` 흐름을 그대로 탄다.
3. 실패하면 오류가 난 **경로**를 얻어 그 경로를 `Value` 에서 제거하고 2로 돌아간다. 제거할 때마다 `ValidationWarning { path, repaired: true }` 를 남긴다.
4. 경로를 제거할 수 없거나(루트 자체가 잘못된 타입) 제거 횟수 상한을 넘으면 `ParseError`.

제거 단위는 값의 위치가 정한다. 객체 필드는 그 **키**를, 배열 원소는 그 **원소**를 제거한다. 배열 원소 제거는 이미 `validate_and_repair` 가 좌표가 깨진 pane 을 제거하는 정책과 같은 결이다.

**값을 보정하지 않고 제거만 하는 이유가 이 결정의 핵심이다.** 제거는 그 필드의 기본값을 `#[serde(default)]` 한 곳에서 그대로 재사용한다. 복구 경로는 어떤 필드가 존재하는지, 기본값이 무엇인지 알 필요가 없다. 필드를 추가해도 복구 코드는 손대지 않는다.

필수 필드(기본값이 없는 필드)를 제거하면 다음 시도에서 "missing field" 로 부모가 실패하고, 그 부모가 다시 제거된다. 매 반복마다 값 트리가 엄격히 작아지므로 종료가 보장되며, 손실은 항상 안쪽에서 바깥쪽으로 최소 범위부터 확대된다.

손실이 부모로 번지는 원인은 두 가지다. 하나는 위의 **기본값 없는 필수 필드**이고, 다른 하나는 **`#[serde(flatten)]`** 이다. flatten 된 컨테이너는 내부적으로 버퍼링된 맵으로 역직렬화되기 때문에 오류 경로가 그 안쪽 키까지 해상되지 않고 컨테이너 단위에서 끊긴다. 따라서 flatten 을 쓰는 타입(`WorkspacePaneView`)은 하위 필드 하나가 틀려도 최소 손실 단위가 그 컨테이너다. 새 설정 타입에 flatten 을 넣을 때는 이 비용을 함께 판단한다.

반복 횟수에는 상한을 둔다. 상한은 **종료 보장용이 아니다**(트리 축소가 종료를 보장한다). 매 재시도가 트리 전체를 다시 역직렬화하므로 크게 망가진 파일의 비용이 O(드롭 수 × 크기)가 되는데, 그 작업량을 자르는 장치다. 상한에 닿으면 돌려줄 부분 결과가 없으므로(트리가 아직 파싱되지 않는다) 파일 전체가 실패로 떨어진다 — 이 결정이 막으려는 바로 그 결과다. 그래서 상한은 손으로 편집한 파일이 도달할 수 없는 값으로 크게 잡는다.

### 적용 범위

**`Settings` 트리 전체에 균일하게** 적용한다. "손편집 전용 knob" 같은 필드 부분집합에만 적용하지 않는다. 어떤 필드가 손편집 대상인지는 시간에 따라 변하고, 부분집합 정책은 "여기는 되고 저기는 안 되는" 계약을 사용자와 코드 양쪽에 남긴다.

### 손실 정책

- 타입 오류 드롭이 한 건이라도 있으면 로드 결과는 `Ok`/`Repaired` 와 구별되는 **`Recovered`** 상태다. 이 상태는 **드롭된 경로와 구조 복구 경고를 서로 다른 목록으로** 싣는다. 드롭은 사용자가 쓴 값을 잃은 것이고 복구 경고는 로더가 구조를 고친 것이라, 둘을 한 목록으로 합치면 "N개 항목이 제거됨" 개수가 복구까지 손실로 센다.
- `Recovered` 상태에서 프론트엔드는 **설정 저장을 차단**한 채 기동하고, 복구 모달을 띄운다. 사용자가 모달을 확인하면 그때 차단을 푼다. 확인 전에는 세션 지속(레이아웃 변경 등)도 저장되지 않는다 — 원본 파일 보존이 세션 편의보다 우선한다.
- 로더는 어떤 경우에도 복구 결과를 자동으로 디스크에 다시 쓰지 않는다. 파일 쓰기는 사용자 행동(모달 확인 후의 저장, 명시적 초기화)에서만 일어난다.
- 모달은 드롭된 **경로 전부**를 나열한다. "N개 항목이 복구됨" 같은 개수 요약만으로는 사용자가 어떤 값을 잃었는지 알 수 없다.

`ParseError` 의 손실 정책은 바뀌지 않는다 — 저장은 계속 영구 차단이고, 사용자는 파일을 직접 고치거나 초기화한다.

## Alternatives Considered

**필드별 `deserialize_with` 로 잘못된 값만 기본값 처리.** 오류가 난 값만 정확히 대체할 수 있고 구현이 국소적이다. 기각 이유: 관용성이 필드 단위 opt-in 이 되어 "어떤 필드가 관용적인가" 가 새 계약이 된다. 필드를 추가할 때마다 그 판단을 반복해야 하고, 빠뜨리면 그 필드만 파일 전체를 날리는 옛 동작으로 되돌아간다. 기본값도 `#[serde(default)]` 와 `deserialize_with` 두 곳에 생긴다. 리포에 선례도 없다.

**타입 강제 변환(`"2"` → `2`, `2.0` → `2`).** 사용자 의도를 더 많이 보존한다. 기각 이유: 변환 규칙이 타입마다 갈리고(문자열→불리언에서 `"false"` 는? 소수→정수는 반올림인가 절사인가) 그 규칙 자체가 문서화해야 할 계약이 된다. 의도 추측이 틀리면 조용한 오동작이 되어, 값을 잃는 것보다 나쁘다.

**현행 유지 + 실패 경로만 정확히 표시.** 구현 비용이 가장 낮고 손실이 조용하지 않다. 기각 이유: 진단이 좋아질 뿐 오타 하나에 설정 전체를 잃는 비용 자체는 그대로다. 다만 "실패 경로를 정확히 보여준다"는 이 안의 좋은 부분은 채택안에 흡수했다 — 드롭 경고가 곧 경로별 진단이다.

**복구 결과를 즉시 디스크에 다시 써서 파일을 정상화.** 다음 기동부터 깨끗하다. 기각 이유: 사용자가 모달을 보기도 전에 원본 값이 사라진다. 손으로 편집하는 파일에서 되돌릴 수 없는 손실을 앱이 먼저 저지르는 셈이다.

**드롭 시 `.bak` 백업 후 정상 저장 허용.** 세션 지속성을 유지하면서 원본을 보존한다. 기각 이유: 백업 파일의 수명·회전·정리라는 새 책임이 생긴다. 저장을 잠깐 미루는 쪽이 관리할 상태가 없다.

## Consequences

- 오타 하나의 대가가 파일 전체에서 그 필드 하나로 줄어든다. ADR-0101 이 UI 없는 knob 을 추가하며 남긴 위험이 해소되고, 앞으로 추가되는 손편집 필드도 별도 조치 없이 같은 보호를 받는다.
- 필드 추가·삭제·타입 변경 시 복구 로직을 손댈 필요가 없다. 복구는 스키마를 모른다.
- 새 로드 상태 `Recovered` 가 백엔드→프론트엔드 계약에 추가된다. 이 상태를 모르는 소비자는 복구를 조용한 성공으로 오인할 수 있으므로, 상태를 분기하는 지점(복구 모달, 세션 지속 훅)을 모두 갱신해야 한다.
- 필수 필드가 깨지면 손실이 그 필드에 머물지 않고 부모로 번진다. 예를 들어 pane 의 `view.type` 이 잘못된 타입이면 그 pane 하나가 통째로 사라질 수 있다. 손실 범위를 사용자가 알 수 있도록 모달의 경로 나열이 필수인 이유다.
- 복구가 일어난 세션은 사용자가 모달을 확인할 때까지 레이아웃 변경이 저장되지 않는다. 모달을 무시하고 작업하면 그 세션의 변경이 유실될 수 있다 — 의도된 트레이드오프다.
- 반복 역직렬화는 실패한 파일에서만 일어나고 정상 경로는 1회다. 상한을 두어 병리적 입력에서도 유한 시간에 끝난다.
- 테스트는 "타입 오류 한 건이 있어도 나머지 설정이 살아남는다"를 Rust 단위 테스트로, 저장 차단을 UI 테스트로 고정한다. `api-contracts.md §10` 의 타입 오류 서술은 이 결정으로 대체된다.
- 재검토 조건: 드롭이 부모로 번지는 사례가 실사용에서 잦아지면(필수 필드가 늘면) 필수 필드에 한해 기본값 주입을 검토한다. 사용자가 값 보정을 반복 요구하면 좁은 범위에서 강제 변환을 다시 논의한다.
