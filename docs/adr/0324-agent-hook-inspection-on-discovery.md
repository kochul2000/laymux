# 0324. 훅 설치 검사는 대상 발견과 명시적 관리에만 수행한다

- Status: Proposed
- Date: 2026-10-14
- Source: 사용자 요구(설치 검사는 최초 실행·업데이트 이후 한 번, 새 환경·폴더와 명시적 관리 시 갱신), PR #1189, architecture/api-contracts.md 에이전트 훅 관리
- 관계: ADR-0289의 주기 검사 정책을 대체하고 ADR-0283의 설치 상태 검증 시점을 확장한다.

## Context

작업 상태 조회는 2초 후속 poll마다 설치 관리의 전체 status를 호출했다. 이 status는 설정·등록 명령·helper 존재뿐 아니라 동봉 바이너리와의 전체 바이트 비교도 수행하고, WSL에서는 새 프로세스를 실행한다. 같은 폴더의 결과 재사용은 한 번의 조회 안에 한정됐다. 별도의 갱신 안내 검사도 시작·포커스·60초 주기에 반복되어 터미널이 많은 환경에서 작업 감지와 무관한 I/O를 발생시켰다.

설치 최신성은 작업 phase와 수명이 다르다. 파일 내용을 매번 읽는 대신 앱 실행 동안 확인 결과를 재사용하고, 실제 작업 귀속은 현재 프로세스·대화·PTY generation·제목 및 훅 수신 기한으로 계속 검증한다. 자동 설치, 설정 영속 형식 변경, 실제 훅 이벤트 전송 방식 변경은 범위 밖이다.

## Decision

**훅 설치·갱신 검사는 앱 시작과 새 대상 발견, 명시적 관리에 수행하고 작업 상태 조회는 프로세스 수명의 검사 결과를 재사용한다.**

- 설치 검사 결과의 단일 소유자는 Rust AppState다. provider·WSL 배포판·설정 폴더별 성공과 오류, 기본 폴더의 해석된 별칭을 메모리에 보관하며 재시작 때 비운다. Windows native 경로는 조회 키의 구분자·대소문자를 정규화하고 Linux/WSL 경로는 대소문자를 보존한다. 정규화한 키를 실제 I/O 경로로 사용하지 않는다. 발견 요청의 원본 경로와 성공 status의 원본 configDir를 별도 보존해 훅 명령 문자열의 소유권 판정에 사용한다.
- 최초 자동 검사에서 native와 실행 중인 사용자 WSL의 기본 폴더를 확인한다. 이후 자동 검사는 수신 메타데이터에서 처음 발견한 설정 대상만 확인한다. WSL의 새 대상을 검사할 때 현재 실행 중인지 확인하며 정지한 배포판을 자동으로 시작하지 않는다. 포커스 복귀·주기 타이머는 설치 검사를 실행하지 않는다.
- get_agent_hook_updates의 optional automatic=true는 이미 시도한 대상을 재검사하지 않는다. 기존 IPC 호출과 REST updates 조회는 명시적 전체 재확인이며 새 검사를 수행한다. 설치·갱신·제거·Settings status의 결과도 같은 캐시를 갱신한다. 관리 이후 안내 조회는 결과를 재사용한다.
- 검사·관리 I/O는 공용 gate로 직렬화한다. 작업 상태 조회와 이벤트 수신은 gate를 기다리지 않고 짧은 결과 락만 사용한다. 결과 락을 파일·프로세스 I/O 동안 보유하지 않는다.
- 명시적 재검사·관리 시작 전에 대상의 이전 설치 증거를 무효화한다. 최대 512개 대상을 보관하고 초과 대상은 설치 증거로 사용하지 않으며 오류로 알린다.
- 알려지지 않은 대상이나 실패한 검사는 설치 완료로 합성하지 않는다. 실패도 한 번의 자동 시도로 보관하며 수동 재확인 또는 명시적 관리로 갱신한다. 외부에서 바꾼 CLI 설정·helper는 수동 확인이나 앱 재시작으로 반영한다.
- 새 대상 발견과 명시적 관리 결과의 안내 갱신 힌트는 내용·토큰·대화 ID를 전달하지 않는다. 관리 결과 힌트는 캐시의 안내만 갱신하고 이미 검사한 대상을 재검사하지 않는다. 수신 메타데이터는 검사 위치의 발견 근거이며 현재 pane 대화의 증거가 아니다. 작업 감지는 현재 프로세스·대화·generation·제목을 계속 검증하고 phase 60초 만료와 프런트 검증 lease를 유지한다. 설치 캐시로 작업 관찰의 유효기간을 연장하지 않는다.
- 결과 재사용은 자동 설치·재설치나 CLI 신뢰·전체 비활성 설정의 변경을 허용하지 않는다. 명시적 관리는 기존 백업·원자 교체·사용자 훅 보존 계약을 따른다.

## Alternatives Considered

- 60초 제한만 적용: 포커스 폭주를 줄이지만 작업 조회의 전체 비교와 주기 WSL 실행은 계속 발생한다.
- 작업 상태 조회에서 바이트 비교만 생략: 반복 WSL 실행과 설치 설정 읽기는 남는다.
- 모든 결과에 짧은 TTL 적용: 만료마다 다시 설치 검사를 수행하므로 요청한 한 번 검사 정책과 맞지 않는다.
- 설치 결과를 디스크에 저장: 앱 업데이트 후 구버전 결과의 무효화·영속 스키마가 필요하다. 앱 수명 메모리 캐시로 충분하다.
- 이벤트 수신만으로 설치·대화 검증을 생략: 공유 서버와 오래된 이벤트가 현재 pane에 잘못 연결될 수 있다.

## Consequences

같은 대상의 작업 poll에서 설치 파일 읽기·전체 바이너리 비교·WSL helper 실행을 제거한다. 대신 앱 수명의 검사 결과와 새 대상 힌트 처리가 필요하며 외부 파일 변경은 즉시 자동 반영되지 않는다. 첫 검사 오류는 자동 재시도로 반복되지 않고 명시적 확인을 요구한다. 새 대상의 단발 검사에는 기존 20초 예산과 WSL 제한·한 번의 timeout 재시도를 적용한다. native/WSL의 한 번 검사·새 대상·오류·수동 갱신·동시 관리·현재 대화 검증과 dev 부하를 검증한다. 기존 기능의 성능·반복 경고 수정이므로 버전 영향은 patch다.
