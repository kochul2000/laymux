# 0140. 분할로 생긴 pane 은 분할한 그 pane 의 CWD 에서 첫 세션을 시작한다 (0003·0130 확장)

- Status: Accepted
- Date: 2026-08-09
- Source: 사용자 요구("워크스페이스 안에서 terminal 을 split 할 때 split 버튼을 누른 바로 그 pane 과 같은 cwd 여야 한다"), [ADR-0003](0003-cwd-single-source-syncgroup.md)(CWD 단일 출처=SyncGroup), [ADR-0130](0130-spawn-time-cwd-seed.md)(스폰 시점 CWD 시딩), [ADR-0113](0113-workspace-clear-activity-owned.md)(재시작 요청 store 소유)

## Context

pane 을 분할하면 새 pane 은 `EmptyView` 로 태어나고, 사용자가 프로파일을 고르는 순간 `TerminalView` 가 되어 PTY 를 띄운다. 이때 시작 디렉터리는 프로파일 기본값(또는 홈)이다 — 방금 `/repo/ui` 에서 작업하다 옆에 하나 더 띄우면 새 셸은 프로젝트와 무관한 곳에서 시작하고, 사용자가 매번 `cd` 를 다시 친다. tmux·wezterm 등 동종 터미널은 분할 시 그 pane 의 CWD 를 상속한다.

기존 CWD 경로는 이 요구를 덮지 못한다.

- **SyncGroup 전파(ADR-0003)** 는 *변경* 을 밀어내는 채널이다. 새 pane 은 세션을 만든 뒤에야 그룹에 들어오고, 그룹은 누가 새로 들어왔다고 해서 현재 CWD 를 다시 방송하지 않는다. `cwd_receive` 를 끈 pane 도 있다.
- **`lastCwd`** 는 "이 pane 이 지난번에 있던 곳"이라는 **설정에 저장된 값**이고, 세션 생성에서 프로파일의 `restoreCwd` 스위치로 게이트된다. 새 pane 에는 지난번이 없고, 상속을 `restoreCwd` 에 묶으면 그 스위치를 끈 사용자에게는 기능이 사라진다. 상속은 복원이 아니다.
- **스폰 시점 시딩(ADR-0130)** 은 백엔드가 *실제로 적용한* 시작 디렉터리를 SoT 에 반영하는 규칙이지, 그 디렉터리를 누가 정하는지에 대한 결정이 아니다. 이 ADR 이 정하는 것은 그 앞 단계 — "새 pane 의 시작 디렉터리를 무엇으로 요청하는가" 다.

범위는 워크스페이스 그리드의 분할이다. Dock 분할과 워크스페이스 신규 생성은 비목표다(각각 고정 표면·빈 레이아웃이라 상속할 원본이 정의되지 않는다). 이미 돌고 있는 터미널의 CWD 를 나중에 따라가게 만드는 것도 비목표다 — 그것이 SyncGroup 전파의 일이다.

## Decision

**분할은 새 pane 의 첫 터미널 세션이 시작할 CWD 를 그 시점에 결정해 "다음 세션은 이 CWD 로 새로 시작하라" 요청으로 실어 보낸다. 기준은 오직 분할한 그 pane — 사용자가 split 버튼을 누른 pane — 이다.**

- **CWD 해석은 `lib/pane-cwd.ts` 한 곳이 소유한다.** `resolvePaneCwd(pane)` 는 살아 있는 세션이 보고한 CWD(`terminalStore`, 백엔드 SoT 의 프론트 미러)를 먼저 보고, 없을 때만 저장된 `lastCwd` 로 내려간다. 사용자 재시작(`Restart View`)이 쓰던 `getTerminalRestartCwd` 는 같은 규칙의 터미널 전용 사본이었으므로 이 함수로 흡수해 제거했다 — 같은 질문("이 pane 은 지금 어디에 있나")에 답이 둘일 이유가 없다.
- **기준 pane 은 하나뿐이고 폴백은 없다.** 분할한 pane 에 CWD 가 없으면(Memo 처럼 CWD 개념이 없거나 세션이 아직 CWD 를 못 받았으면) 시드 없이 기존 동작(프로파일 기본 디렉터리)이다. 다른 pane 의 CWD 로 우회하지 않는다 — "누른 pane 과 같은 곳" 이라는 규칙이 상황에 따라 다른 pane 을 가리키기 시작하면 사용자가 결과를 예측할 수 없다. 포커스 상태도 보지 않는다: 분할은 어느 pane 을 눌렀는지로 완전히 결정된다.
- **시드는 재시작 요청 버스(`terminal-restart-store`)에 싣는다.** payload(`cwd`)와 수명(첫 세션 생성에서 소비, pane 제거에서 폐기, 기동 시 `gcStale`)이 사용자 재시작과 동일하고, 소비 지점(`TerminalView` 의 `isFreshRestart ? restartCwd : …`)이 이미 **`restoreCwd` 설정과 무관하게** 이 값을 적용한다. 새 pane 은 `EmptyView` 로 태어나므로 요청은 사용자가 터미널을 고를 때까지 그대로 기다린다. store 의 소유 문장을 "이 pane 의 **다음 터미널 세션**을 이 CWD 로 새로 시작하라" 로 넓히고, 생산자가 둘(재시작·분할 시드)임을 명시한다.
- **명시값이 상속을 이긴다.** Automation `split_pane` 이 `cwd` 를 주면 그 값으로 시드를 덮어쓴다. 덮어쓰지 않으면 상속 시드가 세션 생성에서 이겨 호출자가 요청한 디렉터리가 조용히 무시된다. 반대로 `cwd` 를 주지 않은 Automation 분할은 UI 분할과 같은 상속을 받는다 — 한 동작에 두 가지 의미를 두지 않는다.
- **시드는 요청일 뿐 사실이 아니다.** 그 디렉터리가 사라졌으면 PTY 는 상속된 CWD 에서 뜨고, SoT 는 ADR-0130 대로 *실제로 적용된* 값으로만 시딩된다. 프론트가 시드를 CWD 로 미리 기록하는 일은 없다.

## Alternatives Considered

- **직전에 포커스한 pane 을 기준으로 삼는다.** 마우스 분할에서는 컨트롤바 클릭의 mousedown 이 그 pane 을 포커스하므로 결과가 같지만, 포커스가 CWD 없는 pane 에 있거나 Automation 처럼 포커스가 옮겨가지 않는 경로에서 기준이 갈린다. 사용자가 확정한 규칙은 "누른 pane" 이고, 눈에 보이는 것(어느 pane 의 버튼을 눌렀는가)이 기준이어야 결과를 예측할 수 있다.
- **분할한 pane 에 CWD 가 없을 때 다른 pane(포커스·최근 활동)으로 폴백한다.** 커버리지는 넓어지지만 규칙이 둘이 된다 — Memo pane 을 분할했는데 새 터미널이 옆 pane 의 디렉터리에서 뜨는 것은 설명하기 어려운 동작이다. CWD 가 없으면 상속할 것이 없다는 결론이 정직하다.
- **`view.lastCwd` 에 상속값을 써 넣는다.** 코드가 제일 짧지만 두 가지가 깨진다. `lastCwd` 는 설정에 영속되는 값이라 상속 CWD 가 그 pane 에 영구히 박히고, 소비가 `restoreCwd` 로 게이트되어 그 스위치를 끈 사용자에게는 상속이 아예 동작하지 않는다. "복원"과 "상속"은 수명도 게이트도 다른 사실이다.
- **분할 시 새 pane 을 곧바로 `TerminalView` 로 만든다(cwd 포함).** 상속만 놓고 보면 단순해지지만, 분할 후 view 를 고르는 현재 UX 를 바꾼다. 이 요구는 CWD 에 대한 것이지 분할이 무엇을 만드는지에 대한 것이 아니다.
- **새 pane 이 세션을 만든 뒤 SyncGroup 이 CWD 를 밀어준다.** 셸이 이미 다른 곳에서 뜬 뒤에 `cd` 를 흘리는 것이라 프롬프트에 그 흔적이 남고, `cwd_receive` 를 끈 pane 은 받지 못한다. 시작 디렉터리는 스폰 인자로 정해야 화면에 군더더기가 남지 않는다.
- **시드 전용 store 를 새로 만든다.** 이름은 정직해지지만 payload·수명·소비 지점이 재시작 요청과 완전히 같은 store 가 하나 더 생긴다. `TerminalView` 는 "첫 세션을 이 CWD 로 새로 시작" 하나만 알면 되고, 그 요청을 누가 넣었는지는 알 필요가 없다.

## Consequences

- 분할로 만든 터미널이 분할한 pane 과 같은 디렉터리에서 시작한다. `restoreCwd` 를 꺼 둔 프로파일에서도 동작한다 — 상속은 복원 스위치와 독립이다.
- 규칙이 하나여서 예측 가능하다. 대신 Memo·Settings 처럼 CWD 없는 pane 을 분할하면 옆 터미널이 아무리 좋은 디렉터리에 있어도 상속은 없다. 이 경우 사용자는 터미널 pane 쪽에서 분할하면 된다.
- 재시작 요청 store 의 생산자가 둘이 되었다. `requests[paneId]` 는 이제 "재시작 눌렀음" 만이 아니라 "새 pane 이 시드를 갖고 있음" 도 뜻하므로, 이 store 를 읽는 새 코드는 그 pane 이 이미 돌고 있었다고 가정하면 안 된다.
- 시드는 `EmptyView` 로 남은 pane 에서 소비되지 않고 기다린다. 분할 후 한참 뒤에 터미널을 고르면 그때는 오래된 디렉터리일 수 있다. pane 이 사라지면 `forgetRestart`/`gcStale` 이 정리하므로 누수는 없다.
- `isFreshRestart` 경로를 타므로 새 pane 의 첫 세션은 출력 캐시 복원과 Claude/Codex 세션 resume 을 건너뛴다. 갓 만든 pane 에는 복원할 캐시도 세션 id 도 없으므로 관측되는 차이는 없다.
- Automation `split_pane` 의 동작이 넓어졌다 — `cwd` 없이 부르면 이제 분할 대상 pane 의 CWD 를 상속한다. 기존 디렉터리를 원하는 호출자는 `cwd` 를 명시하면 되고, 명시값은 항상 상속을 이긴다. REST `POST /api/v1/panes/split` 도 MCP 와 같은 `profile`/`cwd` 를 받도록 맞췄다(그전에는 두 필드를 버렸다).
- Dock 분할은 상속하지 않는다. Dock 에 같은 요구가 오면 `resolvePaneCwd` 를 그대로 쓰면 된다.
- 재검토 조건: CWD 없는 pane 을 분할할 때도 어딘가에서 상속해 달라는 요구가 반복되면 폴백 규칙을 그때 정한다. 상속 자체를 끄고 싶다는 요구가 나오면 그때 설정 축을 만든다 — 지금은 기본 동작 하나만 둔다.
