# 0265. PC·Remote의 첫 사용 기본 구성을 정한다

- Status: Accepted
- Date: 2026-09-24
- Source: 사용자 요구(현재 Remote 구성을 기본으로 사용하되 `u-p1-mg` 제외, 양쪽 플로팅 활성, 기존 110% 크기를 새 100% 기준으로 사용, PC pane의 pinned 기본과 우측 GitHub View 추가), [issue #1075](https://github.com/kochul2000/laymux/issues/1075), [api-contracts.md §13.4](../architecture/api-contracts.md#134-terminal-control)
- 관계: ADR-0209의 기기 로컬 소유권을 유지하고, ADR-0237의 패드 초기 비활성 기본값만 대체한다. ADR-0239의 이동·불투명도 계약은 유지한다.

## Context

첫 화면에서 기능을 발견하기 어렵지만 필수 시작 모달은 즉시 터미널을 사용하려는 흐름을 막는다. 사용자는 실제 사용 중인 Remote 구성을 새 기기의 기본으로 지정했다. 양쪽 플로팅 패드와 Composer를 바로 사용할 수 있어야 하며 개인 작업용 `u-p1-mg` 버튼은 배포 기본에서 제외한다.

PC 물리 키보드와 Remote 터치 입력은 사용 조건이 다르다. Remote 선호를 PC 설정에 복사하거나 기존 기기의 선택을 덮으면 입력 동작과 배치가 예고 없이 달라진다. 런타임과 MCP 스키마의 기본값이 다르면 에이전트가 설명하는 상태와 실제 화면도 어긋난다.

PC의 minimized 컨트롤 바는 pane 조작의 존재를 숨기며, 우측 Memo와 파일 탐색기만으로는 GitHub View를 발견하기 어렵다. 사용자는 pane 컨트롤 바를 기본 pinned로 두고 우측 기본 구성에 GitHub View도 추가하도록 지정했다.

범위는 Remote 기본 구성과 저장값 정규화, PC와 Remote의 기본값 경계다. 워크스루(#1076), 문맥 안내(#1077), PC 위젯의 새 기본 배치 선정, 에이전트 설치 자동화는 별도 작업이다. PTY/OSC, 세션 복원, 인증·allowlist·lease 정책은 변경하지 않는다.

## Decision

**PC는 pinned 컨트롤 바와 우측 Memo·파일 탐색기·GitHub를 갖춘 직접 입력 터미널로, 새 Remote는 Composer와 양쪽 플로팅 패드를 갖춘 구성으로 시작하며 유효한 저장값을 우선한다.**

- PC는 기존 Direct 기본값을 유지한다. Remote의 미설정 입력 모드는 포인터 종류와 관계없이 Composer다. 초기 모드 선택만 바꾸며 모바일/데스크톱 레이아웃의 Enter·전송 제스처는 유지한다.
- PC `controlBar.defaultMode`의 기본값은 `pinned`다. workspace와 dock pane 모두 기존 모드 결정 경로를 사용하며 개별 pane override, 명시적으로 저장된 `hover`·`minimized`·`pinned`가 우선한다. 설정 항목이 없을 때만 새 기본을 사용한다.
- 새 PC의 우측 dock에는 위부터 MemoView, FileExplorerView, GitHubView를 세로 3등분해 배치한다. 왼쪽 WorkspaceSelector와 중앙 터미널, 숨겨진 상·하단 dock은 유지한다. 저장된 dock 구조에는 GitHub pane을 소급 삽입하지 않는다. GitHub View의 저장소 탐색·CWD·인증은 기존 기능을 사용하며 개인 저장소를 기본으로 지정하지 않는다.
- Remote 메인 행은 `^C · Q · Esc · /clr`와 `Keyboard · Keys · Send`다. Q는 내장 액션을 재사용하고 `/clr`는 고정 ID `u-defaultclear`, `/clear`, `submit:true`의 편집 가능한 사용자 키로 제공한다. 기존 입력 경로와 활성 조건을 사용하며 설정 로드만으로 명령을 실행하지 않는다.
- 탐색·알림 패드는 왼쪽, 방향 패드는 오른쪽 중간 높이에 기본 활성화한다. 크기·불투명도·위치는 기기 로컬이며 개별/전체 끄기와 중앙 길게 누르기 이동을 유지한다. 임의 플로팅 버튼 목록은 비어 있다.
- 표시 기본은 버튼 100%, Composer 대기/포커스/사용 중 불투명도 50/70/100%, 탐색 너비 300px, 초기 checkpoint 요청 8 KiB다. 버튼의 새 100%는 기존 110%의 실제 크기이며 Main·Keys 행의 글자·아이콘·높이·너비·안쪽 여백에 같은 기준을 적용한다. 설정·기본값 복원·MCP의 배율은 이 기준에 대한 80~160%, 10 단위 값이다. 서버 상한은 유지한다. 세부 값과 설정 경로는 living doc에서 관리한다.
- 유효한 저장값은 새 기본보다 우선한다. 명시적 `false`, `direct`, 빈 사용자 키 배열, 완전한 빈 행 배치, 커스텀 순서와 좌표를 보존한다. 누락·잘못된 필드는 기존 정규화 방식으로 새 기본을 적용한다. 잘못된 행 shape를 기본 배치로 대체할 때도 현재 사용자 키 목록에 없는 액션은 제거한다. 완전한 정상 배치에 새 액션을 자동 추가하지 않는다.
- 기기 설정의 SoT와 저장 키를 유지한다. PC의 호스트 연결·보안 정책이나 다른 기기의 선호를 변경하지 않는다. 개인 client ID, 토큰, pane/workspace 제외 목록은 배포 기본에 포함하지 않는다.
- 내부 개발 단계의 무마이그레이션 정책에 따라 저장된 버튼 배율 숫자를 자동 환산하지 않는다. 저장된 110은 새 기준의 110%로 해석하며, 기존 110%의 실제 크기를 사용하려면 100%를 선택하거나 기본값 복원을 사용한다. 이 기준 변경은 Main·Keys 행에만 적용하고 플로팅 패드·헤더·Composer editor 크기로 전파하지 않는다.
- 런타임, MCP 공유 스키마의 `default`, CSS 초기값과 해당 설정의 기본값 복원 동작을 일치시킨다. Windows·Linux 호스트와 같은 문서를 사용하는 브라우저/Android 표면에 동일하게 적용한다.

## Alternatives Considered

- **시작 마법사에서 모든 기능을 선택한다.** 사용자가 시작 모달을 거부했고 터미널 사용을 지연한다. 실습과 문맥 안내는 후속 작업으로 다룬다.
- **PC와 Remote에 같은 입력·표시 기본을 적용한다.** 물리 키보드 직접 입력과 작은 터치 화면의 요구가 달라 채택하지 않는다.
- **기존 기기에 기준 구성을 일괄 덮어쓴다.** 명시적 비활성·사용자 배치를 잃으므로 채택하지 않는다. 별도 마이그레이션은 만들지 않는다.
- **개인 설정 JSON을 그대로 내장한다.** 개인 ID·작업별 제외 목록과 불필요한 명령이 섞인다. 액션 의미와 표시 선호만 채택한다.
- **MCP 스키마만 변경한다.** 실제 UI가 다른 기본으로 열려 설정 조작의 기준이 어긋난다. 런타임과 스키마 양쪽을 검증한다.

## Consequences

새 Remote는 설정 탐색 없이 양쪽 패드와 Composer를 쓸 수 있고 `/clr`를 편집·제거할 수 있다. PC 입력 습관과 기존 기기 선택은 유지된다. 과거의 부분 설정에서 누락 필드는 새 기본을 상속하므로 새 패드가 나타날 수 있다. 사이트 데이터를 지우면 새 기본으로 돌아간다.

플로팅은 출력을 일부 가리고 버튼 배율은 좁은 화면의 가로 스크롤을 늘릴 수 있다. 새 기본 100%의 실제 크기는 이전 기본 110%와 같지만, 이미 배율 숫자를 저장한 기기는 새 기준 적용으로 버튼이 이전보다 10% 커진다. 자동 변환 없이 사용자가 배율을 조절하거나 기본값 복원으로 새 100%를 선택한다. 8 KiB 최초 요청은 이전 4 KiB보다 전송량이 늘어난다. `/clr`는 현재 터미널로 명령을 보내므로 에이전트 종류를 추측해 자동 실행하거나 의미를 바꾸지 않는다.

새 기본·명시적 빈 목록·꺼진 패드·Direct·손상된 배치의 초기화, 실제 키 전송, MCP 스키마와 생성 자산의 일치를 회귀 검증한다. dev PC와 모바일 크기 Remote의 화면도 확인한다. PC 위젯 기본 배치와 기능 발견성은 #1075~#1077에서 계속 다룬다. 실제 기기에서 가림·오입력 문제가 확인되면 위치·배율·기본 활성 범위를 재검토한다.
