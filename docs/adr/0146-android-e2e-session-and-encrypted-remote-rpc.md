# 0146. Android 데이터 평면은 생체 승인 세션과 순차 AEAD RPC를 사용한다

## Context

ADR-0145까지 Android와 desktop은 relay가 모르는 32바이트 pairing seed의 공동 소유를 확인하지만 terminal 목록·입력·출력은 여전히 browser Remote API의 평문 relay 경로만 가진다. APK에 고정된 WebView 코드가 있더라도 secret 또는 복호화된 payload를 JavaScript에 넘겨 네트워크를 직접 열면 네이티브 키 경계가 약해지고, 기존 browser cookie나 Direct Remote token을 Android에 추가하면 pairing seed와 별도 권한 수명주기가 결합된다.

AES-GCM은 같은 key에서 nonce가 재사용되면 보안이 무너지므로 세션별 방향 key와 단조 sequence의 소유자를 한 곳에 둬야 한다. 모바일 네트워크에서는 응답 유실과 재전송이 정상이고 relay는 지연·삭제·재정렬·재전송할 수 있으므로, 단순히 "이전 sequence는 모두 거부"하면 성공한 입력의 응답만 사라진 경우 안전하게 복구할 수 없다. 세션을 장기 pairing seed와 같은 수명으로 유지하면 한 번의 생체 승인이 앱 background 이후에도 키 사용 권한으로 남는다.

기존 terminal output WebSocket은 relay가 header와 payload를 해석해 재조립한다. 이를 그대로 암호화하려면 relay·desktop tunnel·Android socket 세 곳의 streaming protocol을 동시에 확장해야 한다. 최초 데이터 평면은 기능을 실제 사용할 수 있으면서도 bounded request/response로 실패·재시도 경계를 고정하는 편이 작고 검증 가능하다.

HKDF는 [RFC 5869](https://datatracker.ietf.org/doc/html/rfc5869), AES-GCM은 [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)를 따른다. Android 구현은 API 23에서 제공되는 `AES/GCM/NoPadding`과 `GCMParameterSpec`을 사용한다. 범위는 세션 handshake, 방향별 key derivation, ciphertext envelope, nonce/replay/rotation, encrypted Remote RPC와 APK 내장 terminal UI다. 여러 Android 기기, ratchet/forward secrecy, background push, 고처리량 encrypted WebSocket은 비목표다.

## Decision

**확정된 pairing seed는 생체 승인 뒤 메모리 전용 세션의 방향별 AES-256-GCM key로만 파생하고, foreground에서 성공한 암호화 RPC마다 15분 비활성 timeout을 갱신하며, Android와 desktop은 exact sequence·한 요청 in-flight·동일 요청의 직전 응답 재현을 강제하는 암호화 RPC로 Remote terminal을 제어한다.**

- WebView는 계속 `connect-src 'none'`이고 key, session key, 평문 network response를 직접 fetch하지 않는다. Kotlin native transport만 저장된 endpoint의 고정 Android E2E route를 호출하고, APK에 서명된 bridge에는 세션 열기·닫기와 allowlisted Remote 동작 요청만 노출한다. 복호화된 terminal 데이터는 표시를 위해 로컬 WebView에 전달할 수 있지만 secret과 방향 key는 전달하지 않는다.
- 사용자가 "보안 세션 열기"를 누를 때마다 pairing wrapping key 사용을 승인한다. 기본 정책은 `BIOMETRIC_STRONG` auth-per-use이며 명시적 `keystoreOnly` opt-out만 예외다. pairing seed는 handshake와 HKDF가 끝나는 즉시 지우고 방향 key만 Kotlin 메모리에 남긴다. foreground에서 인증·처리가 성공한 암호화 RPC마다 desktop session과 Android local key의 15분 비활성 deadline을 갱신하므로 계속 사용하는 동안 세션을 끊지 않는다. 앱이 background로 가면 poll·heartbeat·새 RPC를 중지하고 현재 deadline을 상한으로 고정해 session key와 pending ciphertext를 메모리에 보존한다. 전환 중 이미 전송된 pending RPC가 desktop에서 뒤늦게 성공해도 복귀 시 그 응답으로 고정한 background deadline을 늘리지 않으며 transport는 각 재시도 직전에 suspend를 다시 확인한다. 15분 동안 성공한 RPC가 없거나 pairing을 삭제·교체하거나 명시적으로 disconnect하면 key·로컬 lease handle·output poll 상태를 폐기한다. background 동안 desktop lease는 기존 heartbeat timeout으로 회수된다. 15분 안에 foreground로 돌아오면 생체 인증 없이 같은 E2E session을 재개하되 pending exact request를 먼저 확정한다. 기존 lease heartbeat가 성공하면 그 lease를 재사용하고, 이미 만료됐다면 복귀 시점에 캡처한 E2E deadline 안에서 controller claim 충돌을 재시도한 뒤 새 output snapshot을 받는다. deadline이 지났다면 seed를 다시 복호화하므로 기본 정책에서 생체 인증을 다시 요구한다.
- handshake는 replay된 과거 open proof가 새 세션을 만드는 일을 막기 위해 challenge와 establish 두 단계다. Android는 매 시도마다 OS CSPRNG 16바이트 `clientSessionNonce`를 만든다. `POST /api/android/e2e/session/challenge`는 `{version:1,instanceId,pairingId,clientNonce,clientSessionNonce}`를 받고 desktop의 16바이트 `challengeId`·32바이트 `serverNonce`·60초 `challengeExpiresAt`과 seed HMAC proof를 반환한다. Android는 echo와 `laymux.android-e2e.challenge.response.v1` proof를 확인한다.
- `POST /api/android/e2e/session/establish`는 challenge echo와 `clientProof`를 받는다. client proof는 `laymux.android-e2e.establish.request.v1` domain에 pairing·instance·client nonce·client session nonce·challenge id·server nonce·challenge expiry를 length-prefix framing한 HMAC-SHA-256이다. desktop은 confirmed pairing과 exact owner nonce, unconsumed challenge, proof를 확인하고 16바이트 `sessionId`와 desktop 기준 최초 15분 비활성 deadline인 `expiresAt`을 반환한다. response는 같은 필드에 session id·expiry를 더한 `laymux.android-e2e.establish.response.v1` HMAC으로 인증한다. 현재 여러 Android 기기는 비목표이므로 같은 pairing revision의 새 establish가 성공하면 이전 desktop E2E session을 revoke·remove해 단일 활성 session으로 교체한다. Android는 transport 실패 시 challenge/establish의 exact body를 한 번 재전송하며, 성공한 establish 응답은 challenge 수명 동안 같은 exact request에만 재현하고 challenge는 다른 session 생성에 재사용하지 않는다. Android의 로컬 key deadline은 인증된 desktop expiry와 응답 수신 시점+15분 중 이른 값으로 제한한다.
- HKDF-SHA-256의 input key material은 pairing seed다. salt는 `laymux.android-e2e.hkdf.salt.v1` domain과 pairing id·instance id·client nonce·client session nonce·server nonce·session id를 같은 length-prefix framing한 bytes의 SHA-256이다. info는 Android→desktop에 `laymux.android-e2e.a2d.v1`, desktop→Android에 `laymux.android-e2e.d2a.v1`을 사용하고 각각 독립된 32바이트 key를 expand한다.
- ciphertext envelope는 `{version:1,instanceId,sessionId,sequence,ciphertext}`다. `sequence`는 0부터 시작하는 JSON safe integer 범위의 `u64`이고 한 session에서 Android가 단독 증가시킨다. 96비트 GCM nonce는 방향별 key마다 `0x00000000 || sequence-u64-big-endian`으로 결정한다. key가 방향과 session마다 다르므로 같은 key/nonce 쌍은 재사용되지 않는다. AAD는 방향 domain과 version·instance id·session id·sequence를 고정 binary framing한 값이며 128비트 tag를 사용한다. binary 값은 RFC 4648 padding 없는 base64url이다.
- Android는 session당 요청 하나만 in-flight로 보낸다. desktop은 요청을 복호화하기 직전에 현재 비활성 deadline을 검사하고 exact next sequence만 처음 처리한다. 처리가 성공하면 deadline을 그 요청의 인증 시각+15분으로 갱신하고 plaintext 응답을 `{version:1,expiresAt,response}`로 감싸 AEAD로 인증하며, Android는 인증된 `expiresAt`과 응답 수신 시각+15분 중 이른 값으로 로컬 deadline을 갱신한다. desktop은 암호문 digest와 이 암호화된 응답 하나를 cache한다. 응답이 유실돼 Android가 동일 sequence와 동일 ciphertext를 다시 보내면 cached response와 당시 deadline을 그대로 재현하며 deadline을 다시 늘리지 않는다. Android는 일시적 transport 실패에 새 요청을 만들지 않고 이 exact ciphertext를 로컬 비활성 deadline까지 재시도한다. background는 retry를 suspend하고 pending ciphertext를 보존하며, 명시적 close와 15분 만료는 session을 closed로 표시하고 key를 지운다. Android OS가 background timer를 지연해도 resume과 모든 새 요청은 `now >= expiresAt`을 먼저 검사하므로 deadline 뒤 key 사용은 불가능하다. 같은 sequence의 다른 ciphertext, 이미 지난 sequence, gap, tag 오류는 처리하지 않는다. sequence가 JSON safe integer 한계에 닿거나 key/nonce 생성·검증이 실패하면 session을 닫고 새 생체 승인 세션을 요구한다.
- relay public origin은 cookie 없는 고정 route 세 개만 추가한다: challenge, establish, rpc. 각 route는 exact schema, bounded body/response limit, IP·instance rate/concurrency limit를 적용한다. challenge/establish는 4 KiB request·8 KiB response, RPC는 2 MiB request·6 MiB response이며, 후자의 비대칭 상한은 최대 1 MiB renderer checkpoint와 전체 bounded output-ring suffix가 두 번의 base64 확장을 거쳐도 응답 가능한 값이다. caller가 바꿀 수 없는 desktop path로 해당 instance의 기존 WSS tunnel에 전달하며 desktop을 거친 E2E 응답은 `Cache-Control: no-store`다. challenge/establish는 body parsing 전부터 기존 낮은 인증 시도 제한을 사용하고, 120ms 정상 polling은 별도 bounded RPC limiter(기본 60초당 IP·instance 각각 1200회)를 사용한다. relay는 ciphertext 안의 Remote method, path, lease, terminal bytes를 해석·로그·영속하지 않으며 seed·proof authority·session key를 소유하지 않는다.
- 암호화 RPC plaintext는 versioned tagged union이다. `http` 동작은 desktop 내부 router에 재주입하되 Remote session status/claim/heartbeat/release, navigation/widgets/terminal list, terminal focus/write/input/resize의 exact method/path만 허용한다. caller header·cookie·Remote token과 e2e route 재귀는 금지하고 내부 요청에만 `TunnelAuthorized`를 붙여 ADR-0030의 enabled gate와 기존 controller lease 검사를 그대로 재사용한다.
- terminal output은 `terminalOutputOpen`과 `terminalOutputPoll` 동작을 사용한다. open은 기존 frontend render checkpoint로 만든 encrypted snapshot과 generation/source sequence를 반환하고, poll은 output ring의 exact `resume`으로 그 sequence 이후 delta·idle·reattach 중 하나를 반환한다. 매 요청 전 active lease를 다시 확인하며 generation 교체나 ring eviction에는 Android가 open부터 재부착한다. Android는 120ms 간격에서 앞 요청이 끝난 뒤에만 다음 poll을 보내므로 한 session의 exact request 순서를 깨지 않는다.
- Android UI는 repository의 기존 xterm 자산을 APK asset source로 포함해 로컬 origin에서만 실행한다. 세션 연결 뒤 controller lease를 claim하고 현재 최소 UI는 terminal 목록의 첫 terminal에서 encrypted snapshot/delta를 xterm에 쓰며, snapshot의 `modes.bracketedPaste`를 replay 직후 합성 DECSET으로 복원한다. xterm input·resize와 heartbeat도 같은 암호화 RPC를 사용한다. 기존 browser Remote 경로는 호환을 위해 유지되며 E2E 표시는 Android native session에만 적용한다.

## Alternatives Considered

- **pairing seed를 곧바로 모든 frame의 AES key로 사용.** key 수명과 nonce 공간이 pairing 폐기까지 이어지고 양방향 nonce 충돌 위험이 커진다. 짧은 session과 방향별 HKDF key로 key/nonce 소유권을 분리한다.
- **signed open 요청 한 번으로 세션을 만든다.** round trip은 적지만 relay가 보관한 과거 open proof를 desktop 재시작 뒤 재생해 zombie session을 만들 수 있다. 짧은 desktop challenge를 먼저 발급하고 establish proof에 묶는다.
- **랜덤 nonce를 envelope에 싣고 replay set을 유지한다.** 충돌 확률과 unbounded set 관리가 남는다. 단일 sender sequence에서 결정적 nonce를 만들고 strict order로 replay state를 상수 크기로 제한한다.
- **모든 replay를 즉시 거부한다.** 응답 유실 뒤 Android는 첫 요청이 실행됐는지 알 수 없고 terminal input 같은 비멱등 동작을 안전하게 재시도할 수 없다. 직전 exact request의 암호화 응답 하나만 재현한다.
- **기존 browser cookie·Remote bearer token을 Android에 전달한다.** E2E pairing과 web session 권한을 결합하고 relay가 application plaintext를 계속 보게 된다. 기존 lease 의미만 암호문 안에서 재사용한다.
- **첫 단계부터 encrypted WebSocket을 추가한다.** 출력 효율은 좋지만 relay stream, native tunnel, Android socket reconnect와 sequence를 한 번에 바꿔야 한다. bounded polling RPC로 실제 Remote 표면을 먼저 연결하고 측정 뒤 streaming transport를 별도 결정한다.
- **WebView Web Crypto가 key와 fetch를 소유한다.** 구현은 짧지만 bridge/XSS가 key를 직접 읽고 서버 공급 코드 차단만으로는 native key 경계를 유지하지 못한다. Kotlin이 key·sequence·network를 소유한다.

## Consequences

- relay는 instance/session/sequence와 ciphertext 길이·타이밍은 보지만 terminal 내용, 입력, lease token, terminal metadata는 읽거나 바꿀 수 없다. traffic analysis, 지연, 삭제, replay와 denial of service는 방어 범위 밖이며 AEAD 검증 실패는 fail closed한다.
- pairing seed는 장기 bootstrap secret이므로 이 설계는 과거 seed가 나중에 탈취될 때 녹화된 handshake의 forward secrecy를 제공하지 않는다. ECDH/ratchet 도입은 상호운용성과 Keystore 전략을 포함하는 후속 ADR 대상이다.
- foreground에서 정상 poll·heartbeat·입출력이 이어지면 key 수명도 계속 늘어나므로 절대 수명 상한은 없다. background에서는 네트워크를 중단해 deadline이 더 늘어나지 않으며 최대 15분만 복귀 유예를 준다. 프로세스·Activity가 OS에 의해 제거되거나 앱이 명시적으로 종료되면 그보다 일찍 key를 잃을 수 있다.
- 즉시 폐기 정책보다 background 프로세스 메모리에 key가 남는 공격 표면이 최대 15분 늘어난다. 이 비용은 사용자 요청에 따른 복귀 편의를 위해 수용하되 background network와 controller heartbeat는 유지하지 않으며, deadline 이후 어떤 resume/request도 key를 사용할 수 없게 한다.
- 120ms short-poll은 encrypted streaming보다 요청 overhead가 크다. 모바일 측정에서 battery/latency가 문제면 같은 generation/source-sequence 계약을 유지한 encrypted long-poll 또는 WebSocket으로 transport를 교체한다.
- 자동 검증은 Rust/Kotlin 공통 HKDF·HMAC·AES-GCM vector, exact-boundary expiry, nonce/AAD, tag 변조, gap/replay와 lost-response 재현, background suspend·pending exact resume, relay fixed-route/schema/body/rate limit, Android JVM session/RPC state, desktop router/output 통합을 포함한다. emulator/실기기의 BiometricPrompt·WebView/xterm·background suspend/resume와 실제 배포 origin 왕복은 장비가 준비될 때 수행한다.
- 기존 v2 pairing record는 그대로 사용하고 data session은 영속하지 않으므로 저장 schema migration은 없다. desktop 또는 Android 한쪽만 업데이트된 경우 handshake route가 실패하고 기존 browser Remote에는 영향이 없다.
