# 0102. Claude 사용량은 레지스트리 밖 headless probe PTY 가 소유한다

- Status: Proposed
- Date: 2026-07-31
- Source: 사용자 요구(외부 프로젝트 `kochul2000/claude-simple-usage` 기능의 laymux 내장), architecture/overview.md §6 View 시스템, architecture/api-contracts.md §12, [ADR-0001](0001-osc-rust-single-pass.md), [ADR-0005](0005-display-state-raw-separation-compute.md)

## Context

Claude Code 의 잔여 사용량(세션 / 주간 all models / 주간 모델별)은 **서버 사이드 값**이며, 로컬 파일이나 로그로부터 정확히 재구성할 수 없다. 유일한 정확한 원천은 Claude Code CLI 의 `/usage` TUI 화면이다. 외부 프로젝트 `ccu` 는 이 값을 얻기 위해 숨은 tmux 세션에서 `claude` 를 띄우고 `/usage` 를 보낸 뒤 `capture-pane` 으로 **렌더된 화면**을 긁어 파싱한다.

laymux 에 같은 기능을 넣을 때 작용하는 force:

- **tmux 를 쓸 수 없다.** laymux 는 Windows 1급 지원이고 tmux 는 없다. 반면 laymux 는 이미 자체 PTY 인프라(`pty.rs`, `portable-pty`)를 갖고 있다.
- **바이트 스트림으로는 TUI 를 파싱할 수 없다.** laymux 의 Rust 계층은 화면 셀 모델을 갖지 않는다 — PTY 바이트를 프론트 xterm.js 로 전달할 뿐이고, 셀 격자는 프론트에만 존재한다(그래서 셀 검증은 `*.screen.test.ts` 별도 계층이다, [ADR-0074](0074-xterm-cell-grid-screen-test-tier.md)). `/usage` TUI 는 커서 이동으로 같은 영역을 다시 그리므로, 스트림을 이어붙여 정규식을 걸면 옛 프레임과 새 프레임이 섞인다. **렌더된 화면 상태**가 필요하다.
- **속도 제한.** Anthropic 은 `/usage` 조회에 강한 rate limit 을 걸어 둔다. 갱신 주기는 하한을 갖고, 같은 계정을 보는 여러 소비자가 조회를 중복해서는 안 된다.
- **비용.** 이 기능은 `claude` 프로세스를 하나 상주시킨다. 기능을 쓰지 않는 사용자가 그 비용을 지불해서는 안 된다.
- **사용자는 이 표시를 자유 레이아웃 그리드의 pane 으로 놓고, 세로로도 가로로 길게도 임의 직사각형으로도 쓰기를 원한다.**

범위: 사용량 수집 소유권, 화면 모델, 갱신·공유 정책, 표시 계층의 책임 분리, 외부 계약. 비목표: 사용량 예측·추정·과거 이력 축적, Claude Code 외 다른 에이전트(Codex 등)의 사용량, 사용량 기반 자동 개입(모델 강제 전환 등).

## Decision

**Claude 사용량 수집은 Rust 의 `usage_probe` 가 소유한다. probe 는 터미널 레지스트리 밖의 headless PTY 를 직접 spawn 하고, 자체 vt100 화면 모델 위에서 `/usage` 를 파싱한다. `UsageView` 는 계산된 스냅샷의 표시만 담당한다.**

- **소유권 / SoT.** `AppState` 는 `usage_probe` 하나를 갖고, probe 는 **config dir 당 워커 1개**를 관리한다. 워커의 PTY 는 `state.terminals` 레지스트리에 등록되지 않는다 — 따라서 `list_terminals`·grid·세션 영속·OSC 훅·알림·워크스페이스 eviction 어디에도 나타나지 않는다. 이 PTY 는 사용자의 터미널이 아니라 probe 의 구현 수단이다.
- **화면 모델은 Rust 안에 둔다.** probe 워커는 PTY 출력을 자체 vt100 파서에 흘려 고정 크기(200×60) 화면을 유지하고, 파싱은 그 화면의 텍스트 스냅샷에서만 수행한다. 프론트의 xterm 셀 격자를 스크래핑용으로 재활용하지 않는다 — 그러면 PTY 소유권이 UI 마운트 수명에 묶이고, `UsageView` 가 언마운트되는 순간 갱신이 끊긴다. 파싱을 Rust 단일 패스에 두는 것은 OSC 를 Rust 전용으로 둔 것과 같은 이유다([ADR-0001](0001-osc-rust-single-pass.md)).
- **원시 상태와 표시 계산을 분리한다.** probe 는 `/usage` 에서 읽은 **원시값**(퍼센트, 리셋 시각 문자열, 캡처 시각, 파싱 성공 여부, 계정/플랜)만 스냅샷에 담는다. pace(청구 창 경과 %) 는 리셋 시각과 현재 시각에서 **도출**되는 값이므로 저장하지 않고 계산 함수로 얻는다([ADR-0005](0005-display-state-raw-separation-compute.md)). 시간이 흐르면 같은 스냅샷에서도 pace 는 달라진다.
- **pace 계산은 프론트 단일 구현으로 둔다.** 리셋 시각은 로컬 캘린더 문자열(`7pm`, `Mar 6, 12pm`)이고, 이를 창 경과율로 바꾸려면 로컬 타임존·월 이름·일자 롤오버 해석이 필요하다. Rust 계층은 이 저장소에서 시각을 unix millis 로만 다루고 로컬 캘린더 연산 전례가 없는 반면, 프론트는 이미 같은 형식의 리셋 시각을 해석한다(`lib/claude-session-limit.ts`). 따라서 pace 는 프론트 계산 함수 한 곳에만 존재하고, Rust 는 리셋 시각을 **해석하지 않고 원문 그대로** 전달한다. 같은 계산을 두 언어에 중복 구현하지 않는다.
- **갱신은 스냅샷 단위로 공유한다.** config dir 당 스냅샷은 하나이고 모든 소비자(여러 `UsageView` pane, Automation API, MCP)가 그것을 읽는다. 워커는 `next_query_at` 이전에는 다시 조회하지 않는다. 정상 갱신 간격의 하한은 **600 초**이며 설정으로 그 아래로 내릴 수 없다 — rate limit 은 사용자가 조정할 수 있는 취향이 아니라 외부 제약이다. 파싱 실패는 두 층으로 나눠 다룬다: 탭 이동이 어긋난 경우는 **같은 조회 안에서** 탭만 다시 옮겨 재캡처하므로 추가 조회를 발생시키지 않고, 그마저 실패한 경우에만 짧은 간격으로 **횟수 제한이 있는** 재조회를 하고 그 뒤에는 정상 간격으로 되돌아간다. 실패가 무한 빠른 재조회로 번지지 않는 것이 불변식이다.
- **수요 기반 생명주기.** 워커는 해당 config dir 을 보는 `UsageView` 가 하나 이상 존재할 때만 살아 있다. 수요 신호의 단위는 **구독 1건**이며, 구독 id 는 view 인스턴스가 아니라 **구독 시도마다 고유**해야 한다 — 같은 id 를 재사용하면 이전 시도의 해제가 현재 시도의 수요를 지워 마운트된 view 앞에서 probe 가 은퇴한다. 백엔드는 같은 id·같은 config dir 재구독을 no-op 으로 처리해 이 실수에 한 겹 더 견딘다. 수요가 0 이 되면 워커는 `claude` 를 종료하고 PTY 를 닫는다. 마지막 스냅샷은 캐시에 남겨 재구독 시 즉시 표시하고, `capturedAt` 으로 낡음을 표시한다. 앱 시작만으로 `claude` 를 띄우지 않는다.
- **실패는 표시되고 삼켜지지 않는다.** `claude` 미설치, 기동 타임아웃, trust 프롬프트 미통과, 파싱 실패, 서버 에러는 각각 구분되는 오류 종류로 스냅샷에 담기고 view 와 API 가 그대로 드러낸다. probe 실패는 앱의 다른 기능을 막지 않는다.
- **표시 형태는 컨테이너 종횡비에서 도출한다.** `UsageView` 는 pane 이 세로로 길거나 정사각에 가까우면 스택 레이아웃, 가로로 길면 side-by-side 레이아웃을 **자동으로** 고른다. 사용자는 인스턴스 오버라이드로 이 선택을 고정할 수 있다. 레이아웃을 위해 grid 에 새로운 크기 제약을 도입하지 않는다 — 임의 직사각형은 기존 자유 레이아웃이 이미 제공한다.
- **설정은 에이전트 축으로 나눈다.** probe 설정은 `usage.<agent>.{profile,refreshSeconds,configDirs}` 로 두고, 편집 UI 는 Settings 의 **Views** 그룹에 `사용량` 섹션 하나로 둔다. 셸·config dir·rate limit 하한은 모두 에이전트별이므로 공용 필드로 두면 한쪽 제약이 다른 쪽을 왜곡한다. Views 그룹인 이유는 이것이 `UsageView` 한 view 의 데이터 소스 설정이라는 것이다 — Integrations 의 Claude/Codex 섹션은 연동 *동작*(CWD 동기화, 세션 복원, status message)을 다루며 성격이 다르다. 두 번째 에이전트는 형제 키와 같은 섹션의 서브그룹으로 추가되어 나란히 비교된다. 이 ADR 의 구현 범위는 Claude 하나이며, Codex 사용량 수집 방식은 별도 결정으로 남긴다.
- **외부 계약.** Automation API 와 MCP 는 **원시 스냅샷**을 읽기 전용으로 노출한다(퍼센트·리셋 시각 원문·캡처 시각·상태). pace 는 표시 파생값이므로 계약에 넣지 않는다 — 필요한 소비자는 리셋 시각 원문에서 직접 도출한다. 조회는 probe 를 강제 기동시키는 부작용을 갖지 않는다(수요가 없으면 캐시 또는 "probe 없음"을 반환한다).

## Alternatives Considered

- **프론트에서 headless xterm + `addon-serialize` 로 화면을 얻는다.** 새 Rust 의존성이 필요 없고 셀 격자 재활용도 가능하다. 그러나 PTY 수명이 React 컴포넌트 수명에 매달려 `UsageView` 가 안 보이는 동안 갱신이 멈추고, 여러 pane 이 각자 화면을 유지하려 들며, 파싱이 프론트로 흩어진다. 수집을 백엔드 단일 소유로 두려는 이번 결정과 정면으로 충돌한다.
- **기존 사용자 터미널 pane 을 재활용해 `/usage` 를 보낸다.** 새 프로세스가 없어 가장 싸다. 그러나 사용자의 작업 세션에 입력을 주입해 화면과 대화 맥락을 오염시킨다. 받아들일 수 없다.
- **로컬 Claude Code 상태 파일·로그에서 사용량을 추정한다.** 프로세스가 전혀 필요 없다. 그러나 값이 서버 사이드 진실과 어긋난다. "Claude Code 가 보여주는 것과 동일한 숫자"라는 이 기능의 존재 이유를 잃는다.
- **터미널 레지스트리에 숨김 플래그를 가진 정식 터미널로 등록한다.** 기존 세션 관리·재부착·출력 전송 경로를 재사용할 수 있다. 그러나 그 경로 전체(전송 신용, 재부착 협상, eviction, 영속)가 probe 에는 불필요하며, 모든 소비자가 "이 터미널은 사람이 볼 것이 아니다"는 예외를 알아야 한다. 레지스트리 계약을 오염시키는 비용이 재사용 이득보다 크다.
- **갱신 주기를 사용자 설정으로 완전 개방한다.** 유연하다. 그러나 rate limit 위반은 사용자 계정에 영향을 주는 외부 제약이므로 하한을 설정 가능하게 두지 않는다.

## Consequences

- laymux 는 이 기능을 쓰는 동안 `claude` 프로세스를 하나 추가로 상주시킨다. config dir 별 모니터링을 켜면 그 수만큼 늘어난다. 사용자가 지불 시점을 통제할 수 있도록 수요 기반 생명주기가 필수 조건이 된다.
- Rust 에 vt100 화면 파서 의존성이 새로 들어온다. 용도는 probe 로 한정한다 — 사용자 터미널 렌더링 경로에 두 번째 화면 모델을 만들지 않는다. 만약 앞으로 다른 기능이 Rust 화면 모델을 요구하면, 그때 이 파서를 공용 계층으로 승격할지 여부를 새 결정으로 다룬다.
- `/usage` 는 Claude Code 의 TUI 이고 계약이 아니다. 상류 레이아웃·탭 순서·문구가 바뀌면 파싱이 깨진다. 이 위험은 제거할 수 없으므로 **깨짐이 조용한 오답이 아니라 명시적 파싱 실패로 드러나게** 하고, 화면 캡처 원문을 진단용으로 노출한다. 상류 변화 감지 비용은 지속적으로 발생한다.
- 이 위험은 가설이 아니다. 최초 구현은 `ccu` 를 따라 준비 판정을 모델명(Opus/Sonnet/Haiku)으로, 세 번째 행을 `Current week (Sonnet only)` 로 고정했는데, 실제 Claude Code v2.1.220 은 배너에 `Fable 5 · Claude Team` 을 찍고 세 번째 행을 `Current week (Fable)` 로 그려 둘 다 어긋났다. 그래서 **모델명 목록에 의존하지 않는 것**을 규칙으로 삼는다: 준비 판정은 배너의 제품명(`Claude Code`), 세 번째 행은 괄호 안 라벨을 그대로 읽는 모델 무관 행으로 다룬다. 같은 이유로 퍼센트는 `used` 가 있는 줄에서만 읽는다 — 패널이 같은 블록에 찍는 `+50% weekly limits promo` 같은 무관한 숫자가 사용량으로 잘못 들어가면 조용한 오답이 된다.
- 상류 변화는 unit 테스트만으로 잡히지 않으므로 `#[ignore]` 된 실기 테스트(`tests/usage_probe_live.rs`)를 둔다. 실제 `claude` 를 띄워 한 번 조회하고 캡처를 남기며, drive 시퀀스나 파서를 건드릴 때 손으로 돌린다.
- 표시는 항상 최대 10 분 낡을 수 있다. "지금 정확한 값"을 요구하는 용도(예: 자동 개입 판단)에는 부적합하며, 그런 용도가 생기면 이 결정을 재검토해야 한다.
- 최초 표시는 즉시 나오지 않는다 — `claude` 기동 + `/usage` 왕복이 필요하다. view 는 이 대기를 정직하게 표현해야 한다.
- 후속 작업: `docs/architecture/overview.md` §6 View 목록과 `data-flow.md` 에 probe 데이터 흐름 추가, `api-contracts.md` 에 설정 스키마와 Automation/MCP 계약 추가. 파싱은 실제 `/usage` 화면 캡처 fixture 로 테스트하고, pace 계산은 시각을 주입해 결정적으로 테스트한다.
- 재검토 조건: Anthropic 이 사용량 조회용 공식 API 또는 기계 판독 가능한 출력(`claude usage --json` 류)을 제공하면, TUI 스크래핑과 headless PTY 소유 전체를 폐기하고 새 ADR 로 대체한다.
