# 0384. PC와 Remote의 터미널 경로 링크는 셀 전경색 경계를 후보 추출에 사용한다

- Status: Proposed
- Date: 2026-11-19
- Source: 공백이 포함된 Windows 파일 경로 인식에 관한 사용자 요청, [현재 링크 흐름](../architecture/data-flow.md#86-링크-활성화-평문--osc-8--tui-우회)

## Context

Windows 터미널에 `docs\Release Notes.md`가 표시되면 공백에서 토큰이 나뉜다. 현재 공백 확장은 절대경로와 `~/` 앵커에서만 시작하고, 앵커당 최대 8개 공백 경계를 검사한다. `C:\Program Files (x86)` 자체를 가리키면 꼬리 정리가 유효한 닫는 괄호를 제거할 수 있다. 실제 xterm에 같은 텍스트를 ANSI 팔레트 색과 기본색으로 각각 흘렸을 때 경로 후보는 동일했다. 팔레트와 RGB 전경색은 파일명 내부의 공백과 한글, 자동 줄바꿈 양쪽의 실제 셀에서 확인했다. [xterm 공개 셀 API](https://xtermjs.org/docs/api/terminal/interfaces/ibuffercell/)

Codex CLI 0.170.0의 상호작용형 Markdown 렌더러는 인라인 코드와 로컬 파일 경로에 테마의 같은 전경색을 쓴다. 따라서 색 전환은 경로의 경계를 찾는 데 도움이 되고, 색상값 자체는 파일 경로의 뜻을 보장하지 않는다. 경로가 평문으로 표시되거나 강조 구간이 주변 텍스트까지 포함되는 출력에도 기존 탐색이 필요하다. [Codex CLI 0.170.0 렌더러](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/markdown_render.rs)

PC는 논리 줄에서 후보를 뽑고 호스트에서 존재 여부를 조회한다. Remote는 자신의 xterm 격자에서 복원한 텍스트를 보내 PC와 같은 파서와 호스트의 CWD·홈·파일시스템 조회를 사용한다. 두 표면에서 같은 경로를 찾으려면 Remote의 실제 셀에서 확인한 경계도 이 파서에 전달해야 한다.

Windows dev에서 PowerShell이 실제 임시 파일과 디렉터리의 경로를 ANSI 색으로 출력하도록 해 현재 동작을 확인했다. PC와 Remote 모두 파일명 안 공백에 전경색을 보존했다. 동일 파일의 공백이 있는 절대경로는 PC 호버와 Remote 유휴 스캔에서 검증됐다. 상대경로의 공백 위에서는 PC 호버와 Remote 터치 탭 모두 전체 파일을 찾지 못했고, Remote 유휴 스캔은 닫는 괄호로 끝나는 디렉터리를 놓쳤다.

## Decision

**PC와 Remote는 각자의 xterm 셀에서 전경색으로 구분된 논리 줄 범위를 구하고, 공통 경로 파서는 그 범위에서 완전한 경로 후보를 추가한다. 기존 호스트 조회로 존재가 확인된 후보만 링크가 된다.**

- **경계의 소유자.** 공통 논리 줄 복원기가 공개 `IBufferCell` 전경색 모드·값으로 연속 구간을 구하고 UTF-16 시작·끝 오프셋으로 표현한다. 색이 명시된 구간은 양쪽 끝이 실제 줄 끝 또는 색 전환으로 확인됐을 때 사용한다. 선택·문맥 상한으로 잘린 끝은 색 경계로 보지 않는다. 실제로 출력된 내부 공백은 보존하고 빈 패딩은 제외한다. 자동 줄바꿈과 기존 조건으로 복원된 명시적 줄바꿈은 논리 줄에서 처리한다. 같은 색만으로 별개 물리 줄을 새로 결합하지 않는다.
- **후보와 우선순위.** 내부 공백이 있고 절대·홈 경로, 경로 구분자, 파일 확장자 중 하나를 가진 구간만 추가 후보로 평가한다. URL·제어 문자와 구간 안의 별도 절대경로 앵커는 제외한다. 경계 안의 원문 경로를 먼저 보존해 이름 끝의 괄호를 포함한다. 대응하는 바깥 인용부호와 경로 끝의 `:line[:column]` 같은 장식은 기존 경로 규칙을 적용할 수 있도록 별도 후보에서 정리한다. 정규화와 좌표 매핑은 기존 경로를 사용한다. 검증된 범위가 겹치면 구간 원문 후보, 같은 구간에서 장식을 정리한 후보, 평문 후보 순으로 선택한다. 같은 우선순위에서는 기존 최장 경로 규칙을 적용한다. 색 범위가 없거나 그 후보가 존재하지 않으면 기존 평문 판정으로 이어진다.
- **트리거와 상한.** PC의 선택·포인터 탐색과 Remote의 선택·포인터 탐색·유휴 화면 스캔에 같은 규칙을 적용한다. 포인터 탐색은 지목한 셀을 포함하는 구간만 평가한다. 후보별 길이 설정, 선택의 기본 후보 상한과 전체 선택 거부 규칙, 화면 스캔의 앞부분 결과 정책을 따른다. 색 범위 후보는 추측으로 만든 공백 확장보다 먼저 같은 예산에 넣는다. 경로 중복을 제거하고 트리거당 `stat_paths` 한 번, 최대 64개 경로를 조회한다.
- **Remote 계약.** 기존 `POST /remote/v1/file-viewer/path-link` 요청에 선택적인 `foregroundRanges`를 추가한다. 각 원소는 `{lineIndex, startIndex, endIndex}`이고 기존 `lines`에 대한 0부터 시작하는 UTF-16 반개구간이다. 요청당 최대 64개를 줄·시작 오프셋 순으로 보내며 같은 줄의 구간은 겹치지 않는다. Rust는 개수, 정수, 순서, 줄 범위, 양 끝이 서로게이트 쌍을 가르지 않는지 검증한다. 필드가 없거나 유효하지 않으면 기존 텍스트 판정을 사용한다. 브라우저·Cloud·Android E2E가 같은 요청 필드를 사용한다. 호스트는 전달받은 원문 안에서 후보를 만들고 서버가 가진 CWD·홈을 사용한다. 응답 형태와 lease·FileViewer capability·Android E2E proof의 기존 권한 검사를 유지한다. 전경색 값과 물리 셀 좌표는 각 표면 안에 둔다.
- **재검증.** 요청 시점과 적용 시점의 안정 프레임에서 논리 줄 원문과 색 경계가 일치해야 한다. 이미 표시한 링크는 대상 범위에 닿는 색 구간의 시작·끝이 달라지면 같은 글자가 남아 있어도 폐기하고 다음 발견 트리거에서 다시 평가한다. 경계가 같고 색상값만 바뀌면 유효한 링크를 유지한다. Remote 유휴 화면 signature와 PC 포인터 재조회 억제에도 경계 변화를 반영한다. 기존 마커 이동, 리사이즈, DEC 2026 안정 프레임, 워크스페이스·lease·CWD 전환 규칙을 적용한다.

## Alternatives Considered

- **문자열 확장 범위를 모든 상대경로로 늘린다.** 평문도 더 발견할 수 있지만 일반 문장에서 후보가 빠르게 늘어난다. 터미널이 이미 보여 준 경계가 있는 경우만 확장하면 기존 배치 상한으로 더 정확한 대상을 먼저 확인할 수 있다.
- **특정 도구의 색이나 OSC 8 링크만 사용한다.** 테마에 따라 색이 바뀌거나 인라인 코드와 공유된다. OSC 8 링크는 프로그램이 목적지를 출력할 때만 존재하므로 현재 URL 처리 경로를 유지하고 셀 색 경계는 파일 후보의 단서로 사용한다.
- **Remote가 해석한 경로 문자열을 보내거나 호스트가 raw ANSI를 다시 재생한다.** 전자는 공통 파서와 원문 범위 검증을 우회하기 쉽다. 후자는 호스트가 클라이언트의 좁은 격자와 줄바꿈·재출력 상태를 복원해야 한다. 기존 논리 줄에 구간만 추가하면 화면의 경계와 호스트의 경로 검증을 함께 사용할 수 있다.

## Consequences

- 경로와 주변 문장이 다른 색으로 출력되면 Windows의 공백이 든 절대·상대경로와 닫는 괄호로 끝나는 이름을 통째로 확인할 수 있다. 여러 조각이 같은 색으로 연속 강조되거나 CLI가 좁은 폭에서 원래 구분 정보를 잃으면 기존 텍스트 후보에 의존한다. 실제 CLI 출력에서 그런 사례가 반복되면 구간 판정과 명시적 줄바꿈 기준을 재검토한다.
- 구현 PR에서 [링크 데이터 흐름](../architecture/data-flow.md)과 [Remote 요청 계약](../architecture/api-contracts.md)을 갱신한다. 새 설정이나 데이터 마이그레이션은 필요하지 않다.
- 실제 xterm 화면 테스트에 팔레트·RGB, 내부 공백·한글·서로게이트 쌍, 자동 줄바꿈, 색만 다시 그린 프레임, 같은 색 문장 및 URL을 포함한다. Remote route/bridge 테스트로 잘린 오프셋·개수 초과·필드 생략과 browser/Android E2E 권한 경계를 검증한다.
- 구현 검증은 Windows dev 포트 `19281`에서 작업 워크트리 신원을 확인한 뒤 수행한다. 같은 임시 파일·디렉터리와 ANSI 출력으로 PC의 호버·클릭·선택, Remote의 마우스·좁은 화면 탭·선택·유휴 스캔에서 밑줄 범위와 최종 열린 대상을 대조한다. 같은 경로가 담긴 Claude Code와 Codex의 실제 출력도 별도로 캡처해 테마와 폭에 따른 경계 차이를 확인한다.
