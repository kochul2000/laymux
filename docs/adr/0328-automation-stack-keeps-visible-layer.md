# 0328. Automation 스택 생성은 기존 표시 레이어를 유지한다

- Status: Proposed
- Date: 2026-10-15
- Source: 사용자 요구(MCP로 stack pane을 만들 때 새 레이어로 잠시라도 이동하지 않는다), [ADR-0324](0324-automation-never-navigates-user.md), [ADR-0297](0297-pane-stack-slot-layer-model.md), [data-flow.md 스택](../architecture/data-flow.md#스택)
- 관계: ADR-0297의 Automation 스택 생성 시 새 레이어를 표시하는 계약만 대체한다. ADR-0324의 탐색 상태 보존을 슬롯의 활성 레이어까지 구체화한다. UI 스택 생성과 명시적 레이어 활성화는 유지한다.

## Context

Automation 스택 생성은 슬롯의 포커스 인덱스를 유지하지만, 새 레이어를 활성 레이어로 삽입한다. 포커스된 슬롯에서 실행하면 화면이 새 터미널로 전환되고 DOM 포커스도 따라간다. 이후 원래 레이어를 복원해도 사용자는 이미 전환을 보게 된다. 슬롯 포커스 보존만으로는 사용자의 작업 화면을 보존할 수 없다.

비활성 스택 터미널은 이미 시작 큐의 대상이며 렌더러 없이 PTY를 준비할 수 있다. 새 터미널의 준비와 입력에 레이어 표시가 필요하지 않다. 사용자가 직접 누르는 PC/Remote Stack 버튼은 새 콘텐츠를 선택하는 의도이므로 Automation 생성과 구분한다.

## Decision

**Automation의 스택 생성은 기존 활성 레이어를 유지한 채 새 레이어를 삽입하며, 생성·준비·입력 도중 새 레이어를 활성화하지 않는다.**

- 슬롯과 활성 레이어의 SoT인 `workspace-store`가 삽입과 활성 레이어 보존을 하나의 상태 갱신으로 수행한다. 활성화 후 복원하지 않는다. 생성 호출부는 내부 옵션으로 활성화 여부를 지정한다.
- REST `POST /api/v1/panes/stack`과 MCP `stack_pane`은 같은 비활성 삽입 경로를 사용한다. 요청·응답 스키마, 기본 view, 프로파일, CWD 상속, 삽입 순서는 유지한다.
- 숨겨진 새 터미널은 기존 시작 큐와 readiness 대기를 사용한다. `write_to_terminal`은 화면을 바꾸지 않고 준비를 기다린 뒤 입력한다. 시작 동시성·PTY 수명·워크스페이스·grid/dock 포커스 정책은 변경하지 않는다.
- PC 버튼·단축키·Remote Stack 키는 기존대로 새 레이어를 표시하고 포커스한다. `activate_pane_layer`와 `focus_terminal`을 통한 명시적 탐색도 유지한다. MCP 설명은 생성이 화면을 바꾸지 않으며 표시하려면 명시적 활성화가 필요함을 알린다.

## Alternatives Considered

- **생성 후 원래 레이어 복원:** 중간 상태가 구독자와 DOM에 공개되어 깜빡임과 포커스 이동을 막지 못한다.
- **UI 스택 생성까지 모두 비활성화:** 사용자가 새 레이어를 선택하려는 직접 조작의 기존 의미를 바꾼다.
- **외부 API에 활성화 옵션 추가:** 현재 요구는 탐색 없는 생성이며, 표시가 필요하면 기존 명시적 활성화 API를 쓸 수 있다. 추가 계약 없이 내부 옵션만 사용한다.

## Consequences

기존 콘텐츠가 계속 보이고 전환 줄에 새 탭이 추가된다. 새 PTY는 보이지 않는 상태에서 시작하며, 화면으로 확인하려면 명시적으로 활성화해야 한다. 기존 API 이용자가 생성 직후 새 화면을 보리라 기대했다면 활성화 호출을 추가해야 한다.

테스트는 최종 슬롯 포커스뿐 아니라 상태 구독에 공개된 모든 활성 레이어와 실제 dev의 DOM 포커스·프레임을 확인한다. 숨겨진 터미널의 준비·입력 및 사용자 Stack 버튼의 활성화도 검증한다. 새 스키마나 기능 옵션을 추가하지 않는 ADR-0324의 탐색 부작용 수정이므로 버전 영향은 patch다. 렌더러 없이 시작하는 경로의 정책이 바뀌면 이 결정을 재검토한다.
