# 0123. 상단 바에서 창 버튼(최소화·최대화·닫기)은 다른 모든 점유자보다 우선한다

- Status: Accepted
- Date: 2026-08-03
- Source: 사용자 보고(창 폭을 줄이면 최상단 바의 최소화·최대화·닫기가 밀려 사라진다); `docs/architecture/overview.md` 상단 바 구조·`docs/architecture/api-contracts.md` §10 위젯 폭 부족 규칙
- Amends: [ADR-0105](0105-widget-slots-and-status-line.md) — "폭 부족 시의 우선순위"의 최상위 항목을 정정한다. ADR-0105 는 "좌우 고정 폭(로고·레이아웃 컨트롤·창 버튼)"을 줄지 않는 상수로 전제하고 드래그 최소 폭을 1순위로 두었다. 고정 폭의 합이 창 폭을 넘는 구간이 실제로 존재하므로, 그 전제를 버리고 창 버튼을 명시적 1순위로 올린다.

## Context

상단 바(`GridEditToolbar`)는 창 장식을 끈 상태(`decorations: false`)에서 창의 유일한 최소화·최대화·닫기 수단이다. 그 왼쪽에는 로고와 Export New, 위젯 슬롯 좌/우, 드래그 영역, dock 토글·레이아웃 모드·파일 뷰어·절전 방지·Remote Access·설정 버튼이 한 줄에 늘어선다.

창 폭을 줄이면 창 버튼 세 개가 화면 밖으로 밀려 사라진다. 원인은 우선순위가 아니라 우선순위의 부재다 — 좌측 앱 컨트롤 클러스터와 우측 액션 클러스터가 모두 `flex-shrink: 0` 이라 폭이 모자라도 한 픽셀도 내놓지 않고, 위젯 슬롯과 드래그 영역이 각자의 하한까지 줄고 나면 초과분은 flex 행의 **마지막** 항목 쪽으로 넘친다. 마지막 항목이 창 버튼이므로, 가장 포기해서는 안 되는 것이 가장 먼저 사라진다.

ADR-0105 는 폭 부족 시 "드래그 영역 최소 폭 > 위젯 표시" 를 정했지만, 창 버튼을 포함한 좌우 고정 폭은 애초에 줄어들지 않는 상수로 전제했다. 그 전제가 깨지는 구간(고정 폭 합 > 창 폭)에서 무엇을 버릴지는 어느 결정도 소유하지 않았고, 그래서 브라우저의 오버플로 기본 동작이 대신 정했다.

결정이 필요한 지점은 두 가지다. (1) 폭이 고갈될 때 창 버튼은 몇 순위인가. (2) 나머지 점유자는 어떤 방식으로 자리를 내놓는가 — 눌려서 작아지는가, 잘려서 사라지는가.

제약과 force:

- 창 장식이 없으므로 창 버튼이 사라지면 마우스로 창을 닫거나 최소화할 수단이 남지 않는다. 다른 점유자는 전부 대체 수단이 있다 — 설정은 `Ctrl+,`, 파일 뷰어는 `Ctrl+Shift+O`, dock 토글·위젯은 창을 넓히면 돌아온다.
- 창 버튼은 Windows 11 표준 히트 영역(46×32px)을 지킨다. 폭에 맞춰 눌러 줄이면 버튼은 보이지만 오조작이 늘고, 위젯 접힘과 달리 "접혔다"는 표시도 남지 않는다.
- 드래그 영역 최소 폭([ADR-0105](0105-widget-slots-and-status-line.md))은 창을 옮길 수단이므로 위젯보다 위에 남아야 한다.
- jsdom 단위 테스트는 레이아웃을 계산하지 않는다. 폭 우선순위는 클래스 문자열이 아니라 실제 박스 좌표로만 검증된다.

범위는 상단 바 한 줄의 가로 공간 배분이다. 비목표: 창 최소 크기 강제, 상단 바 항목의 접기 UI 신설, status line 의 배분 규칙 변경.

## Decision

**창 버튼(최소화·최대화·최대화 해제·닫기)은 상단 바의 다른 어떤 점유자보다 우선하며, 어떤 폭에서도 온전한 크기로 화면 안에 남는다.**

### 폭 부족 시의 우선순위 (ADR-0105 의 목록을 대체)

1. **창 버튼** — 줄지도, 잘리지도, 밀려나지도 않는다. 세 버튼은 항상 46px 폭을 유지하고 바의 오른쪽 끝에 붙는다.
2. **드래그 영역 최소 폭** — 창 버튼 다음이다. 창을 잡을 수단은 위젯 표시보다 위다([ADR-0105](0105-widget-slots-and-status-line.md)).
3. **앱 크롬 버튼과 위젯** — 남은 폭을 나눠 갖는다. 위젯은 기존대로 오버플로 팝오버로 접히고, 크롬 버튼 클러스터는 아래 규칙대로 잘린다.

### 크롬 클러스터가 자리를 내놓는 방식

- **버튼은 눌리지 않고 잘린다.** 클러스터는 줄어들되 그 안의 버튼은 각자 고유 폭을 유지하고, 넘치는 만큼 클리핑된다. 절반 크기의 버튼은 히트 영역을 거짓말하므로 만들지 않는다.
- **잘리는 끝은 화면 가장자리에서 먼 쪽이다.** 좌측 클러스터는 오른쪽 끝부터(로고가 마지막까지 남는다), 우측 클러스터는 왼쪽 끝부터(dock 십자가 먼저 사라지고 설정 톱니가 마지막까지 남는다) 잘린다. 방향은 컨테이너의 정렬이 소유한다 — 항목마다 우선순위 값을 부여하지 않는다. [ADR-0105](0105-widget-slots-and-status-line.md) 의 "가장자리에 가까운 것이 마지막까지 남는다" 와 같은 규칙이다.
- 잘린 크롬 버튼에는 오버플로 팝오버를 두지 않는다. 위젯과 달리 크롬 버튼은 전부 키보드 단축키나 다른 표면에서 도달할 수 있고, 좁은 바에 팝오버 트리거를 하나 더 놓는 것은 문제를 키운다.

### 불변식

- 상단 바가 존재하는 한 `window-minimize` / `window-maximize` / `window-close` 는 뷰포트 안에 온전히 있다. 검증은 실제 레이아웃을 계산하는 Playwright e2e(`ui/e2e/top-bar-window-controls.spec.ts`)가 소유하며, 여러 폭에서 세 버튼의 박스가 뷰포트를 벗어나지 않고 폭이 줄지 않았음을 잰다.
- 이 불변식이 성립하는 하한은 "창 버튼 3개(138px) + 드래그 최소 폭(80px) + 바 자체의 패딩·간격" ≈ 260px 다. 그보다 좁은 창은 상정하지 않으며, 창 최소 크기를 코드로 강제하지도 않는다.

## Alternatives Considered

- **창 버튼을 DOM 순서에서 앞으로 옮기고 시각 순서만 뒤집기** — flex 오버플로가 마지막 항목을 밀어내므로 순서를 바꾸면 증상은 사라진다. 그러나 그때는 대신 설정 톱니가 소리 없이 밀려나고, "무엇이 먼저 사라지는가"는 여전히 아무도 소유하지 않는다. 증상을 옮길 뿐이라 기각.
- **좁을 때 창 버튼을 제외한 항목을 숨기는 미디어 쿼리 / 폭 임계값** — 임계값이 위젯 배치와 폰트 크기에 따라 달라져 항상 틀린다. 하나의 하드코딩된 폭이 사용자 배치를 대신 결정하는 것은 [ADR-0105](0105-widget-slots-and-status-line.md) 의 "배치는 사용자 소유" 와 충돌한다.
- **창 버튼을 `position: absolute` 로 바 오른쪽에 띄우기** — 흐름에서 빼면 밀려날 수 없다. 그러나 다른 항목이 그 아래로 지나가며 겹치고, 드래그 영역이 버튼 밑까지 들어와 클릭을 삼킨다. 겹침을 막으려면 다시 오른쪽 여백을 손으로 맞춰야 해서 상쇄용 CSS 가 늘어난다.
- **버튼을 눌러 줄이기(`flex-shrink` 허용)** — 세 버튼이 다 보이긴 하지만 46px 히트 영역이 깨지고, 좁을수록 닫기 오조작 위험이 커진다.

## Consequences

- 좁은 창에서 창 제어가 항상 가능해진다. 대신 dock 토글·Export New 처럼 잘린 항목은 창을 넓히기 전까지 마우스로 도달할 수 없다 — 이들은 단축키나 Settings 로 대체 가능하다는 판단에 기댄 비용이다.
- 크롬 버튼이 잘려 사라지는 것에는 "잘렸다"는 시각 신호가 없다. 위젯의 `⋯` 같은 표시를 크롬에도 두자는 요구가 생기면 새 결정으로 다룬다.
- 상단 바에 항목을 새로 추가할 때는 클러스터 안 배치 순서가 곧 생존 순서라는 점을 지켜야 한다 — 중요한 것일수록 화면 가장자리 쪽에 둔다.
- 재검토 조건: 창 최소 크기를 강제하기로 하거나, 상단 바를 두 줄 이상으로 접을 수 있게 되면 이 결정의 하한 가정이 바뀐다.
