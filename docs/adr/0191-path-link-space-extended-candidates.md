# 0191. path-link 후보는 절대경로 앵커에서 공백을 넘어 확장한다

- Status: Proposed
- Date: 2026-08-23
- Source: 사용자 버그 신고("`G:/내 드라이브/Advisor/Advisor_0.1.0_x64-setup.exe` 가 경로로 인지되지 않는다"), [ADR-0148](0148-bounded-multi-path-selection-links.md), [ADR-0188](0188-path-link-ambient-detection-triggers.md)
- Extends: ADR-0148, ADR-0188

## Context

path-link 의 후보 문법은 **공백을 토큰 경계로** 쓴다. 후보 추출은 maximal-munch 토크나이저(`SELECTION_TOKEN_RE`, 공백·따옴표·괄호가 경계)가 만든 토큰 단위로만 이루어지고, 선택 기반의 단일 토큰 검사(`trimSelectionToPath`)도 공백이 끼면 즉시 거부한다.

그 결과 **이름에 공백이 든 경로는 어떤 트리거로도 발견되지 않는다.** Windows 에서 이런 경로는 예외가 아니라 일상이다 — `G:\내 드라이브\...`(Google Drive), `C:\Program Files (x86)\...`, `C:\Users\<이름>\My Documents\...`. 신고된 문자열 `G:/내 드라이브/Advisor/Advisor_0.1.0_x64-setup.exe` 는 `G:/내` 와 `드라이브/Advisor/...` 로 쪼개져 각각 stat 에 실패하고, 사용자가 경로 전체를 정확히 드래그해도 선택 문법이 공백에서 거부한다.

어려운 점은 **경로의 끝을 문법만으로 알 수 없다**는 것이다. `G:/내 드라이브/x.exe 를 실행하세요` 에서 경로가 어디까지인지는 텍스트만 봐서는 결정 불가능하다. 반면 이 기능은 처음부터(ADR-0148) "형태 휴리스틱은 느슨하게, **실존 검증(`stat_paths`)이 실질 게이트**"라는 설계 위에 서 있고, ADR-0188 이 트리거당 조회 비용을 상수로 묶는 계약을 확립했다. 즉 후보를 몇 개 더 만들어 stat 으로 판정하게 하는 것은 이 설계의 자연스러운 연장이며, 진짜 제약은 **트리거당 후보 수가 상수로 묶여야 한다**는 것뿐이다.

범위는 후보 추출 문법과 트리거별 후보 상한이다. 표시(데코레이션)·클릭 라우팅·Remote 계약 shape·`stat_paths` 백엔드는 비목표로 그대로 둔다. **상대경로의 공백 확장도 비목표다** — 앵커가 없으면 어떤 단어 쌍이든 후보가 되어 조회량이 문장 길이에 비례해 버린다.

## Decision

**공백을 포함한 경로는, 절대경로로 시작하는 앵커 chunk 에서 오른쪽으로 공백 경계(cut)마다 접두 후보를 만들어 stat 으로 판정한다. 존재하는 후보 중 겹치는 것은 가장 긴 것이 이긴다(longest-existing-wins). 앵커당 확장 cut 은 최대 8개로 묶는다.**

- **앵커**: 줄을 공백 단위 raw chunk 로 나눴을 때, 앞 장식(따옴표·괄호)을 뗀 텍스트가 절대경로(`/`, `X:\`·`X:/`, `\\`)로 시작하는 chunk. 상대경로는 앵커가 되지 않는다.
- **확장 후보**: 앵커 시작부터, 이어지는 chunk 들의 끝 위치마다 원문을 자른 접두 문자열. 인접 chunk 사이 간격이 스페이스(` `)만일 때 이어지고, 탭이 끼면 끊는다(표 정렬은 경로가 아니다). 각 후보의 꼬리는 단일 토큰과 같은 규칙(`:line:col`·닫는 괄호·문장부호 제거)으로 정리한다. chunk 는 토큰과 달리 괄호를 경계로 삼지 않으므로 `C:\Program Files (x86)\...` 도 원문 그대로 이어진다.
- **비용 상한**: 앵커당 확장 cut ≤ 8. 트리거별로는 —
  - `selection`: 기본 토큰 후보의 all-or-nothing 상한 16(ADR-0148)은 유지하고, 확장 후보는 그 **뒤에 best-effort 로 덧붙이되** 배치 총량 64(백엔드 `MAX_PATH_LINK_CANDIDATES`)에서 자른다. 확장은 발견을 더하는 것이므로 상한 초과가 기존 링크를 없애는 all-or-nothing 대상이 아니다.
  - `point`: 기본 토큰 1 + 지점(offset)을 덮는 확장 후보 ≤ 8, 배치는 여전히 트리거당 1회. ADR-0188 의 "후보 상한 1"은 "후보 상한 ≤ 9(상수)"로 정정된다. 지점이 공백 위여도 그 공백을 **덮는** 확장 후보는 평가한다(경로 내부의 공백 위 hover/클릭).
  - `screen`: 확장 후보도 기존 상한 64 안에서 읽기 순서대로 함께 센다. 상한 초과 시 뒤쪽을 버리는 부분 결과 semantics(ADR-0188)는 그대로다.
- **겹침 해소**: stat 이후, 존재하는(트리거별 linkable 한) 후보들 사이에서 같은 줄의 겹치는 범위는 **긴 것부터 greedy 로 채택**하고 겹치는 짧은 것을 버린다. `G:/내 드라이브`(디렉토리)와 `G:/내 드라이브/x.exe`(파일)가 모두 존재하면 파일이 이긴다. 겹치지 않는 후보들은 기존처럼 모두 표시한다.
- **실존 검증이 유일한 게이트**라는 원칙(ADR-0148)은 그대로다. `...x.exe 를 실행하세요` 같은 문장 꼬리가 붙은 cut 은 stat 에 실패해 자연히 떨어지고, 실제 경로 길이의 cut 만 남는다.

## Alternatives Considered

- **따옴표로 감싼 경로만 공백을 허용한다.** 문법이 단순하고 오탐이 없지만, 신고된 사례(터미널 출력의 비인용 경로)를 전혀 해결하지 못한다. 셸이 경로를 인용해 출력해 주는 경우는 드물다.
- **선택(드래그) 트리거만 공백을 허용한다.** 사용자가 범위를 명시하므로 모호성이 없고 구현이 가장 작지만, ADR-0188 이 방금 만든 hover·클릭·탭·유휴 화면 트리거에서 같은 경로가 여전히 죽는다. "드래그 없이 발견"이라는 0188 의 목적과 정면으로 어긋난다.
- **공백 이웃 토큰을 stat 해보고 실패하면 병합 재시도(반복 왕복).** 후보 폭발은 없지만 트리거당 IPC 가 가변 횟수가 되어 0188 의 "배치 1회" 계약이 깨진다. 접두 후보를 한 배치에 모두 실어 보내면 왕복 1회로 같은 결과를 얻는다.
- **상대경로에도 공백 확장을 허용한다.** `내 문서/파일.txt` 같은 상대경로도 잡히지만, 앵커 조건이 없어지는 순간 모든 단어 열이 후보가 된다 — 화면 스캔에서 후보 수가 문장 구조에 비례해 상한 64를 일상적으로 소진하고, 존재하는 파일명과 우연히 일치하는 문장 조각의 오탐 표면도 커진다. 절대경로 접두는 사람이 쓰는 문장에 우연히 나타나지 않는 강한 신호이므로 앵커로 삼는다.
- **greedy longest-existing 대신 존재하는 모든 접두를 표시한다.** 정보량은 많지만 같은 텍스트 위에 밑줄이 계층으로 겹쳐 클릭 대상이 모호해진다(hit-test 는 사각형 기반). 파일과 그 조상 디렉토리 중 사용자가 원하는 것은 거의 항상 더 구체적인(긴) 쪽이다.

## Consequences

- 신고된 `G:/내 드라이브/...` 를 포함해, 공백이 든 절대경로가 드래그·hover·클릭·탭·유휴 화면 모두에서 발견된다. `C:\Program Files (x86)\...` 처럼 괄호가 든 경로도 chunk 확장으로 잡힌다.
- 트리거당 stat 배치는 여전히 1회지만 배치 크기가 커진다 — `point` 는 1→최대 9, `selection` 은 16→최대 64, `screen` 은 64 유지. 실패 stat 은 `fs::metadata` 1회라 싸고, 백엔드 상한 64 는 그대로가 계약이다(프론트가 초과분을 자른다).
- 화면 스캔에서 절대경로 토큰 하나가 확장 후보 최대 8개를 더 만들므로, 경로가 밀집한 화면에서는 상한 64 가 더 일찍 소진되어 뒤쪽 줄의 링크가 빠질 수 있다. 부분 결과 semantics 는 0188 그대로이며, 이 트레이드오프는 의도된 것이다.
- 경로 끝 판정은 여전히 stat 의존이다. 존재하는 접두 디렉토리가 있고 전체 경로가 존재하지 않는 경우(오타 등) 접두에만 밑줄이 붙는 **부분 링크**가 생길 수 있다 — 틀린 표시가 아니라 실존하는 대상의 표시이므로 수용한다.
- 문장부호 정리 규칙의 한계로, 경로가 닫는 괄호로 **끝나는** 경우(`C:/Program Files (x86)` 자체가 대상)는 꼬리 정리가 괄호를 떼어 접두 디렉토리로 낮춰질 수 있다. 드문 경우이고 stat 게이트 안에서 안전하게 실패하므로 별도 문법을 만들지 않는다.
- 겹침 해소 규칙(longest-existing-wins)이 새 불변식이다 — 이후 트리거·표시를 바꿀 때 같은 줄 겹침 밑줄을 만들지 않아야 한다.
- ADR-0188 의 트리거별 후보 상한 표는 이 ADR 로 정정되며, living doc(`data-flow.md` §8.6)의 문법 서술을 함께 갱신한다.
- 재검토 조건: 상대경로 공백 확장 요구가 실사용에서 반복되거나, 화면 스캔의 상한 소진이 실제 불편으로 신고되면 앵커 조건·상한을 다시 판단한다.
