# 0110. GitHub 스냅샷은 만료돼도 마지막으로 알던 목록을 먼저 내려준다

- Status: Proposed
- Date: 2026-08-01
- Source: 사용자 요구(워크스페이스 전환 시 빈 목록), [ADR-0106](0106-github-list-view-repo-registry.md)(repo 단위 레지스트리) 확장, architecture/api-contracts.md §GitHub 이슈/PR 목록

## Context

[ADR-0106](0106-github-list-view-repo-registry.md) 은 `owner/repo` 레지스트리가 스냅샷과 10초 갱신 주기를 소유한다고 정했다. 다만 "만료된 스냅샷"의 처리는 정하지 않았고, 구현은 만료를 캐시 미스와 동일하게 취급했다 — 창 밖의 읽기는 `gh` 두 번(이슈·PR)이 끝날 때까지 반환하지 않는다.

그 결과 마지막 조회가 갱신 주기를 넘긴 뒤 처음 들어오는 pane 은 목록이 아니라 빈 화면을 본다. 프론트는 이 구간을 `loading` 으로 표시하고 아무 행도 그리지 않기 때문이다. 대기 시간은 네트워크와 `gh` 기동에 달려 있어 체감상 1~3초이며, 워크스페이스를 오랜만에 열 때마다 반복된다. 레지스트리는 이미 직전 결과를 인메모리로 들고 있는데도 그것을 쓰지 않는 것이 문제의 핵심이다.

범위는 `get_github_repo_snapshot` 의 서빙 정책 하나다. 스냅샷을 디스크에 영속하는 것, 뷰가 없을 때도 백엔드가 상시 폴링하는 것, 레지스트리 항목 만료·정리 정책은 비목표다.

## Decision

**만료된 스냅샷은 캐시 미스가 아니다. 레지스트리에 기억된 스냅샷이 있으면 갱신 주기를 넘겼더라도 즉시 그것을 반환하고, `gh` 재조회는 응답 뒤 백그라운드에서 돌린다(stale-while-revalidate).**

- **읽기의 답은 세 갈래다.** 주기 안이면 신선한 스냅샷, 주기를 넘겼지만 기억된 스냅샷이 있으면 그 stale 스냅샷 + 백그라운드 재조회 예약, 기억된 것이 전혀 없으면 기존대로 `gh` 를 인라인 실행한다. 프로세스 시작 직후 첫 조회만 기다림이 남는다.
- **`force` 는 stale 을 받지 않는다.** 사용자가 새로고침을 누른 것은 "지금 값을 다시 확인해 달라"는 뜻이므로 인라인 조회를 유지한다.
- **stale 응답의 `fetchedAtMs` 는 만들어 내지 않는다.** 반환값은 그때 저장된 스냅샷 그대로이며, 표시된 목록이 언제 것인지는 그 값이 말한다. 프론트는 stale 을 별도 상태로 구분하지 않고 평소처럼 렌더한다.
- **백그라운드 재조회도 single-flight 를 공유한다.** 재조회는 리포별 `fetch` 토큰을 `try_lock` 으로 잡는 기존 경로를 그대로 타므로, 폴링하는 pane 이 몇 개든 갱신 주기당 `gh` 실행 횟수는 [ADR-0106](0106-github-list-view-repo-registry.md) 과 같다. 응답을 보낸 뒤 별도 blocking 작업으로 띄우므로 명령 응답을 지연시키지 않는다.
- **조작 뒤 무효화는 그대로 유효하다.** 성공한 close/merge 는 스냅샷 자체를 비우므로, 다음 읽기는 stale 이 아니라 캐시 미스로 인라인 재조회한다. 방금 닫은 항목이 stale 응답으로 되살아나지 않는다.

## Alternatives Considered

- **프론트엔드에 마지막 스냅샷을 모듈 수준으로 캐시.** pane 재마운트는 살릴 수 있지만 캐시 소유자가 창 하나로 좁아지고, [ADR-0106](0106-github-list-view-repo-registry.md) 이 백엔드로 모아 둔 캐시 소유권이 두 곳으로 갈라진다. 백엔드에서 하면 pane·워크스페이스·CWD 표기 차이와 무관하게 `owner/repo` 단위로 한 번만 기억한다.
- **스냅샷을 디스크에 영속.** 앱 콜드 스타트의 첫 표시까지 없앨 수 있지만, 사용자가 명시적으로 인메모리 유지를 요구했고 목록은 몇 초면 다시 얻을 수 있는 휘발성 데이터다. 저장 위치·무효화·쓰기 시점이라는 새 계약이 이득보다 크다.
- **뷰와 무관하게 백엔드가 상시 폴링해 항상 신선하게 유지.** 뷰가 닫혀 있어도 rate limit 을 소모한다. [ADR-0106](0106-github-list-view-repo-registry.md) 이 이미 기각한 방향이다.
- **갱신 주기를 늘려 만료 자체를 드물게 만들기.** 목록이 그만큼 늦어질 뿐 "만료 직후 진입" 이라는 최악의 경우는 그대로 남는다.
- **프론트가 stale 을 흐리게 표시하거나 스피너를 얹기.** 상태 표시가 하나 늘고 10초 주기에서는 거의 항상 stale 이므로, 대부분의 시간을 "갱신 중" 으로 보이게 만든다.

## Consequences

- 레지스트리가 그 리포를 한 번이라도 조회한 뒤라면 pane 진입 시 빈 화면이 사라진다. 기억이 없는 첫 조회(앱 시작 직후, 처음 보는 리포)는 여전히 기다린다 — 인메모리만 쓰기로 한 결과다.
- 표시된 목록은 최대 한 폴링 주기만큼 과거일 수 있다. 폴링 주기와 갱신 창이 모두 10초이므로 정상 운용에서도 대부분의 응답이 stale 경로를 타며, 화면은 직전 주기의 목록을 보여주고 다음 주기에 따라잡는다.
- 실패도 기억된다. 마지막 조회가 `ghMissing`/`unauthorized`/`failed` 였다면 그 상태가 stale 로 다시 내려오고, 백그라운드 재조회가 성공하면 다음 주기에 정상 목록으로 바뀐다.
- 백그라운드 작업이 blocking 풀을 쓴다. 실행 횟수는 토큰으로 묶여 있으므로 리포당 동시 1개를 넘지 않는다.
- 재검토 조건: 콜드 스타트의 첫 표시까지 없애야 한다면 디스크 영속이 별도 결정으로 필요하고, stale 표기를 사용자에게 드러내야 한다면 프론트 상태를 하나 늘리는 결정이 필요하다.
