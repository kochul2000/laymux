# 0112. 색상 리터럴은 hex 색상 코드로 표기한다

- Status: Proposed
- Date: 2026-08-02
- Source: issue #713, architecture/api-contracts.md §15.1, AGENTS.md `color-mix()` 금지 규칙

## Context

laymux 는 색상을 두 가지 형태로 손으로 적어 왔다.

- 불투명 색상: `#89b4fa` 같은 hex 색상 코드
- 반투명 색상: `rgba(137, 180, 250, 0.5)` 같은 채널 3개 + 알파

`color-mix()` 는 html2canvas 가 파싱하지 못해 스크린샷 API 를 깨뜨리므로 금지돼 있다. 그 결과 알파 변형 토큰(`--accent-50`, `--green-15`, `--hover-bg` 등)은 모두 사전 계산된 `rgba()` 리터럴로 박혀 있고, 같은 색이 `ui/src/index.css` 와 remote 페이지(`src-tauri/src/remote_server/page.html`) 두 곳에 중복돼 있다.

문제는 편집 비용이다. `--accent` 를 바꾸려면 hex 한 번이 아니라 십진 채널 3개를 여섯 벌 다시 계산해 옮겨 적어야 한다. 색상 코드 하나를 그대로 붙여 넣을 수 없고, 디자인 도구·색상 선택기·기존 토큰 어디서 값을 가져와도 손으로 십진 변환을 거쳐야 한다. Rust 쪽 `claude_bullet.rs` 의 마커 색상도 같은 문제로, `(215, 135, 135)` 튜플 옆에 `= #d78787` 주석이 붙어 있는 형태였다.

범위는 **사람이 손으로 적는 색상 리터럴**이다. 프로토콜·픽셀 경계에서 채널이 형식 자체인 코드(SGR `38;2;R;G;B` 파싱, DIB/PNG 바이트 스위즐, OSC `rgb:` 응답)는 대상이 아니다. jsdom 이 계산값을 `rgb()` 로 직렬화해 그 형태로 단언할 수밖에 없는 테스트도 대상이 아니다.

## Decision

**색상은 hex 색상 코드로 적는다. 불투명은 `#rrggbb`, 반투명은 8자리 `#rrggbbaa` 를 쓰고, 손으로 적는 자리에 `rgb()`/`rgba()` 채널 표기를 남기지 않는다.**

- CSS·HTML(`ui/src/index.css`, `src-tauri/src/remote_server/page.html`, 인라인 `style`)의 색상 리터럴은 hex 만 쓴다. 알파는 `round(a * 255)` 로 양자화한 한 바이트로 표기한다.
- Rust 에서 손으로 적는 색상 상수는 `0xRRGGBB` 형태의 색상 코드로 적고, 채널이 필요한 비교·계산은 코드 안에서 언팩해서 한다. 즉 **저장·표기는 색상 코드, 채널은 파생값**이다.
- `color-mix()` 및 상대 색상 문법(`rgb(from …)`) 금지는 그대로다. html2canvas 가 못 읽는다는 근거가 바뀌지 않았고, 8자리 hex 는 html2canvas 1.4.1 의 `HASH_TOKEN` 경로가 그대로 지원한다.
- 이 규칙은 회귀 테스트로 강제한다. `index.css` 와 remote 페이지 HTML 에 `rgb(`/`rgba(` 리터럴이 없다는 것을 각각 `ui/src/lib/css-tokens.test.ts` 와 `page.rs` 테스트가 단언한다.
- 알파 변형 토큰이 베이스 색상과 값이 중복된다는 사실 자체는 이 결정이 해결하지 않는다. 알파 토큰은 여전히 앱 테마 전환(`useAppTheme`)을 따라가지 않으며, 그 문제는 별도 결정으로 남긴다.

## Alternatives Considered

- **`color-mix(in srgb, var(--accent) 50%, transparent)`** — 중복과 테마 미추종을 한 번에 없앤다. html2canvas 가 파싱하지 못해 스크린샷 API 가 깨지므로 이미 금지된 선택지다. 상대 색상 문법 `rgb(from var(--accent) r g b / 0.5)` 도 같은 이유로 기각.
- **`useAppTheme` 에서 알파 변형을 런타임 생성** — 테마 추종까지 해결되지만, 토큰의 소유권이 CSS 에서 JS 로 옮겨가고 remote 페이지는 별도 경로가 필요해 결정 범위가 커진다. 이번 이슈의 요구는 "표기를 색상 코드로" 이므로 분리한다.
- **`rgba()` 유지 + 주석에 hex 병기** — 지금 `claude_bullet.rs` 가 하던 방식이다. 편집할 때 실제로 고쳐야 하는 값이 여전히 십진 채널이라 문제가 그대로 남는다.
- **알파를 0–255 정수로 분리한 별도 토큰** — 채널 분리를 다시 들여오는 셈이라 기각.

## Consequences

- 색상 하나를 색상 코드 그대로 붙여 넣을 수 있게 된다. 색상 선택기·디자인 도구·기존 토큰 사이 왕복에 십진 변환이 사라진다.
- 알파가 `n/255` 로 양자화된다. 기존 값들의 이동폭은 최대 0.5/255 ≈ 0.2%p 로 육안 식별 불가지만, "정확히 0.06" 같은 값을 요구하는 자리에는 쓸 수 없다. `--bar-bg-overlay` 처럼 알파 상한을 단언하던 테스트는 hex 알파 바이트를 파싱하도록 바뀐다.
- `index.css` 와 `page.html` 두 곳의 토큰 중복은 남는다. 회귀 테스트가 표기 형식만 강제하므로, 두 파일을 계속 손으로 맞춰야 한다는 부담은 그대로다.
- 새 색상을 추가할 때 `rgba()` 를 쓰면 테스트가 실패한다. 알파가 정말 필요 없는 경우에도 8자리를 쓰라는 뜻은 아니며, 불투명 색상은 6자리 그대로다.
- 재검토 조건: html2canvas 를 걷어내거나 스크린샷 경로가 브라우저 네이티브 캡처로 바뀌면 `color-mix()` 금지가 풀리고, 그때는 알파 변형 토큰을 베이스 색상에서 파생시키는 쪽이 이 결정보다 낫다.
